# TASK SCOPE — ISSUE #184-recyclebin-lwc

## 1. Requirements Breakdown

- **Target Objective:** Build the `gtmRecycleBin` LWC — the front-end surface for the already-shipped `GTM_RecycleBinController` Apex class (merged in PR #189, part 2 of 5 of issue #184). The component must let a Content Manager/admin user:
  1. List every archived `GTM_Page_Section__c` and `GTM_Page_Content__c` row via `getArchivedItems()` (cacheable Apex, wired imperatively or via `@wire` — see gap note below) in a `lightning-datatable` (columns: record name, object type, offering key, archived date, archived by, "is offering tile" indicator).
  2. Restore a single row via a row-level action calling `restoreRecord(recordId)`.
  3. Select multiple rows and bulk-restore via `restoreRecords(recordIds)`, surfacing the per-record `RestoreResult.success`/`message` mix (a "partial success" toast/list, not a single pass/fail toast) since the controller explicitly supports mixed outcomes (e.g., a child row blocked because its parent tile is still archived or hard-deleted).
  4. Permanently delete ("Empty Trash") via a confirmation modal before calling `deleteRecord`/`deleteRecords`, following the same two-step confirm pattern already used in `gtmContentHome`'s own archive-confirm flow (`manageConfirmArchive`/`handleAskArchive`/`handleCancelArchive` — ask, then confirm, never a single destructive click).
  5. Refresh the list after any restore/delete action (`getArchivedItems` is `cacheable=true`, so a post-action refresh must either call `refreshApex` or re-invoke imperatively — implementer's choice, but must not show stale rows after an action succeeds).

- **System Component Impacted:** LWC (`force-app/main/default/lwc/gtmRecycleBin/`) only. No Apex, no metadata XML, no schema changes are in scope for this sub-issue.

- **Entry point / reachability gap (explicit, not to be silently assumed away):** `gtmContentHome.js`/`.html` currently has **no** reference to `gtmRecycleBin` anywhere in the codebase (`grep -rn "gtmRecycleBin"` returns nothing outside the not-yet-created component itself). `gtmContentHome` only exposes an inline archive/restore toggle per offering (`handleConfirmArchiveToggle` → `setOfferingArchived`) — it has no link, button, or route to a recycle-bin view at all. Per PR #189's own body this LWC is meant to be reached from that admin surface, but the actual click-path was never wired in the crash-fix (#186) or schema (#187) slices. **This sub-issue's scope therefore includes adding one navigation entry point** — the minimal, lowest-risk option is a "View Recycle Bin" / "Manage Archive" button in `gtmContentHome.html`'s existing manage-offering modal or header area that opens `gtmRecycleBin` as a standalone `lightning__Tab`/`lightning__AppPage` target (matching the `gtmReadoutApprovalSettings` convention of `<target>lightning__AppPage</target>` + `<target>lightning__Tab</target>` in its `.js-meta.xml`, opened via `NavigationMixin` `standard__component` page reference — `gtmContentHome` already extends `NavigationMixin`). Do NOT modify `gtmContentHome`'s archive/restore logic itself — only add the navigation affordance. If the Architect/Developer judges a full custom tab registration (App Builder page assignment, new Tab metadata) is needed to make this real without a manual admin step, call that out as a fork in the Architect step rather than resolving it here — a plain LWC-to-LWC navigation event is the safe minimal default.

- **Apex gap check (explicit, per instructions — do not silently assume the controller covers everything):** Reviewed `GTM_RecycleBinController.cls` and its test in full. `getArchivedItems()`, `restoreRecord`/`restoreRecords`, and `deleteRecord`/`deleteRecords` are all present, bulk-safe, and already return the exact per-row success/message shape a bulk-action UI needs. **No new Apex method appears necessary for the UI described above.** One soft gap worth flagging to the Architect: there is no server-side pagination/filtering on `getArchivedItems()` (hard `LIMIT 1000` per object, no offering-key filter param) — for this sub-issue's scope, the LWC should do client-side filter/search (e.g. by offering key or object type) over the full returned list, same as `gtmContentHome` already does client-side search over `getHomeSummary()`'s full payload. If real archived-row volume ever approaches 1000+, a follow-up Apex change (server-side filtering) would be needed, but that is out of scope here and must not be added preemptively.

- **Ambiguity flagged for the Architect (not resolved here):** Whether "Empty Trash" in the UI means (a) a single bulk-select-all-then-delete action re-using `deleteRecords`, or (b) a literal one-click "empty everything" action with no selection step. The issue title says "empty trash/permanent-delete confirmation modal," which reads as (a) built on top of the existing bulk-select checkboxes (consistent with `restoreRecords` already requiring an explicit id list — there is no `deleteAllArchived()` Apex method, and adding one is out of scope per the "no new Apex unless a genuine gap" instruction). This scope assumes (a): the modal confirms whatever rows are currently checked (which may be all of them if the user selects all), not a separate no-selection "nuke everything" button.

## 3. Plan Acceptance Criteria

- **Success Metric:** A new `gtmRecycleBin` LWC exists under `force-app/main/default/lwc/gtmRecycleBin/` that (1) lists all archived items in a `lightning-datatable` with row-level Restore and checkbox-driven bulk Restore/Delete actions wired to the four `GTM_RecycleBinController` methods (`getArchivedItems`, `restoreRecord`/`restoreRecords`, `deleteRecord`/`deleteRecords`), (2) shows a two-step confirmation modal before any permanent delete fires, (3) surfaces partial-success results from bulk operations distinctly from a full success/failure, (4) refreshes its list after any successful restore/delete, and (5) is reachable from `gtmContentHome` via one added navigation affordance (button/menu item using `NavigationMixin`) without altering `gtmContentHome`'s existing archive/restore business logic. Jest coverage exists for: initial load/render of archived rows, row-level restore success, bulk restore with a mixed success/failure result set, delete-confirmation modal open/cancel/confirm flow, and post-action list refresh.
- **Target Test Target:** `force-app/main/default/lwc/gtmRecycleBin/__tests__/gtmRecycleBin.test.js` (new Jest spec, run via `npm test` / `@salesforce/sfdx-lwc-jest`). No Apex test changes are expected or in scope — `GTM_RecycleBinControllerTest.cls` already passes and is not to be modified by this sub-issue.
