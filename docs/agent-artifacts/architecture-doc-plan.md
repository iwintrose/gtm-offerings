## 2. Research — documentation architecture frameworks, and the fit for this repo

### 2.1 The four frameworks reviewed

| Framework | What it's for | Verdict for this repo |
|---|---|---|
| **arc42** | A complete, numbered template (12 sections: constraints, context, solution strategy, building blocks, runtime, deployment, crosscutting concepts, decisions, quality, risks, glossary) for *architecture documentation specifically*. | Too heavyweight to adopt wholesale for a single-app SFDX repo of this size — arc42 is meant for systems with real architectural complexity across many services. But its section *vocabulary* (crosscutting concepts, runtime view, deployment view) is useful as a checklist for what `docs/architecture/overview.md` should cover, even without adopting the full 12-section template or its document-generation tooling. |
| **C4 model** (Simon Brown) | An abstraction-first *diagramming* notation — Context, Container, Component, Code — as a lightweight alternative to UML for visualizing structure. | Directly useful at the Container/Component level: this repo genuinely has containers worth drawing (the Experience Cloud guest-facing site, the two Lightning apps, Apex/LWC/CMDT layers) and components worth naming (the scoring engine, the approval-gated readout pipeline, the instrument YAML→CMDT build pipeline). Recommend **one C4-style Container diagram** (Mermaid, inline in `docs/architecture/overview.md` — see §5) as the single visual anchor for a cold reader; skip Component-level diagrams as unnecessary ceremony for a repo this size. |
| **ADRs (Michael Nygard format)** | A short, dated, numbered Markdown doc per *significant, hard-to-reverse* decision: context → decision → consequences. Never edited after acceptance; superseded, not amended. Convention confirmed by current research: `docs/adr/` (or `docs/architecture/adr/`) as a flat, sequentially-numbered directory is the dominant pattern in real repos today, exactly matching what `ma-migrator` (this org's own sibling project, visible in this session's system context) already does at `docs/architecture/adr/`. | **Directly adopted.** This repo has at least three genuinely load-bearing, hard-to-reverse decisions made tonight that deserve exactly this treatment (packaging strategy, the FLS-gap-pattern lesson as a *process* decision, the single-trigger-point convention) — see §5. |
| **Diátaxis** | Splits documentation into four modes by reader *need*, not by topic: tutorial (learning-oriented), how-to (task-oriented), reference (information-oriented), explanation (understanding-oriented) — the classic failure mode it names is a single doc trying to be all four at once and serving none of them well. | **Directly useful as a diagnostic**, not as a directory-naming scheme to bolt on top of what's already here. Applying its lens to the existing docs: `docs/runbooks/*.md` are **how-to** (task-oriented, "how do I rebuild this in a fresh org") — correctly shaped already, keep the name `runbooks/` rather than renaming to `how-to/`, since it's an established, understood term in this codebase and Diátaxis's contribution is the *shape*, not the *label*. `docs/specs/*.md` are closer to **reference** (though currently also carrying stale content, §1.3). Nothing in the repo is currently **explanation** (the "why" prose that isn't a decision record and isn't a task) — the new `docs/architecture/overview.md` fills exactly that gap. Nothing is **tutorial** (learn-by-doing) and nothing needs to be — this is an internal tool with a small user base, not a product needing onboarding tutorials; recommend explicitly *not* manufacturing a tutorial section just to complete the quadrant. |

### 2.2 CLAUDE.md/AGENTS.md conventions for AI-agent consumption

Current practice (2026): AGENTS.md has become the de-facto cross-tool standard (read by Codex CLI, Cursor, Aider, Devin, Gemini CLI, Windsurf, Amazon Q); Claude Code specifically still reads `CLAUDE.md`. The two commonly-cited best practices that matter most here:

- **Keep it short and load-bearing, not a wiki.** Recommended target is under ~250 lines; content should be *stable* project context (conventions, gotchas, pointers) rather than anything that changes weekly. Start minimal, add a section only when an agent keeps getting something wrong, remove a section when the convention changes. This directly argues for **not** copy-pasting the runbooks or `docs/backlog.md` into `CLAUDE.md` — it should *point to* them, not duplicate them.
- **Directory responsibilities, commands, and restricted files over generic advice.** The highest-value CLAUDE.md content, per current guidance, is exactly the category this repo has in abundance and needs written down for the first time: real command lines (`sf project deploy start ... --dry-run`, not `-c`), real file/class/tab names, and hard "don't do X" rules — which maps precisely to the systemic gotchas in the task brief.

This repo's sibling project `ma-migrator` (visible in this session's own system context, same organization) is itself a strong worked example of an AGENTS.md/CLAUDE.md symlink pair, sized appropriately, structured as: project overview → repo layout → stack → committed architectural decisions (with an ADR pointer) → agent team table → dispatch rules → **agent-led development principles** (numbered, each with a one-line rationale) → conventions reference → common commands → memory pointers → "what NOT to do." This repo doesn't need the subagent-team sections (it has no custom subagents, §1.5) but the **overall shape — overview, layout, stack, decisions-with-ADR-pointer, conventions, commands, "what NOT to do"** — is a proven, directly-applicable template from a project run by the same people. I'm citing it as structural precedent, not duplicating its content.

### 2.3 How comparable OSS projects structure docs/

Current convention for a project this size (a few hundred files, several subsystems): `docs/adr/` (or `docs/architecture/adr/`) holding one numbered file per accepted architectural decision, versioned with the code, never edited post-acceptance; a separate `docs/runbooks/` or `docs/operations/` for recurring operational procedures (deploy, migration, rollback) — explicitly *not* merged into the ADR format, because "ADRs capture decisions; runbooks capture operations" is the stated anti-pattern to avoid (treating ADRs as a universal documentation format). This is exactly the runbooks/ split this repo already has by accident (it already created `docs/runbooks/` before this planning pass) — the plan below formalizes and extends a pattern the repo had already started correctly, rather than inventing a new one.

### 2.4 Why this combination, concretely, for this repo

- **ADRs** for the handful of genuinely hard-to-reverse decisions (packaging, the FLS-gap lesson as a process rule, single-trigger-point). Small in number — I count 5 in §5, not 20 — because arc42/ADR literature is consistent that ADR sprawl (an ADR for every small choice) defeats the purpose.
- **One arc42-flavored `docs/architecture/overview.md`** with a C4-style container diagram, for the "explanation" content Diátaxis says is currently missing entirely.
- **`docs/runbooks/` kept exactly as named**, Diátaxis-shaped already (how-to), extended with the gotchas that are operational in nature (the CLI `-c` flag trap, duplicate-rule handling) rather than architectural.
- **`CLAUDE.md`**, sized and shaped per current agent-consumption best practice and this org's own proven `ma-migrator` template, as the single cold-start entry point that *points to* everything else rather than duplicating it.

### 5.2 ADRs

Each in the standard Nygard shape: Title, Status (Accepted), Context, Decision, Consequences. Numbered, never edited after acceptance — a later change supersedes with a new ADR.

- **ADR-0001 — Unpackaged SFDX now, unlocked package later.** Context/decision/consequences lifted and condensed from `DEPLOYMENT.md`'s "If this needs to go to *many* orgs" section and `docs/runbooks/fresh-org-deploy.md` §2's fuller reasoning (packages can't carry `ExperienceBundle`/profiles/org state, so packaging today would only move ~80% of the solution and still leave the hard 20% manual — the namespace decision is irreversible once made). Explicitly note it's an **unlocked** package under consideration, not managed — this is an internal accelerator, not ISV/AppExchange IP-hidden distribution.
- **ADR-0002 — Permission-set grants are part of a field/object/tab's definition of done.** Context: the 5-instance FLS gap pattern found and fixed in one night (name all 5 concretely: `GTM_Saved_Configuration__c`, `GTM_Content_Home` tab, `GTM_Readout__c`, `GTM_Readout_Version__c`, and the `GTM_Config_Manager`↔`Page_Content__c`/`Page_Section__c` gap found during the D6 cutover). Decision: any change that adds a field, object, or tab must include the matching permission-set grant(s) **in the same PR/change**, and `code-reviewer`-equivalent review (or, absent a dedicated review agent here, the human reviewer) must check for it. Consequences: slightly more permission-set diff noise per change; the alternative (discovering the gap by live-testing after deploy, as happened tonight, five times) is worse.
- **ADR-0003 — Single trigger point per side effect.** Context: a real double-send email bug from an Apex class and a Flow both reacting to the same DML. Decision: never let two independent automations (Apex trigger/class + Flow, or two Flows) both react to the same DML for the same side effect; pick one owner per side effect. Consequences: some automations that "could" be a quick Flow have to instead be added to existing Apex, or vice versa, to keep one owner.
- **ADR-0004 — Dynamic Apex schema access in the instrument/scoring layer.** Context: fields in this area get deleted and recreated as the instrument evolves (confirmed pattern from `docs/runbooks/assessment-instrument.md`'s description of the YAML→CMDT build pipeline). Decision: `Schema.getGlobalDescribe()`/string-built `Database.query()` is used deliberately in this layer instead of static field references, trading compile-time safety for deploy resilience. Consequences: this code is harder to refactor with an IDE's "find references," and typos in field API names fail at runtime, not compile time — scoped deliberately to the instrument/scoring classes, not a repo-wide pattern.
- **ADR-0005 — Assessment and readout scores are always recomputed server-side.** Context/decision drawn directly from `docs/runbooks/assessment-instrument.md`'s "Scoring is server-side, always" section — `GtmAssessmentRequestController` discards any client-supplied score/tier/basis. Elevate this from "a fact about one controller" to a standing rule: **any future feature that scores or bands an estate must recompute server-side and must not trust a client-supplied value**, because the guest questionnaire is anonymous and unauthenticated. Consequences: this rules out ever accepting a pre-computed score from the LWC layer as authoritative, even for legitimate-looking payloads.
