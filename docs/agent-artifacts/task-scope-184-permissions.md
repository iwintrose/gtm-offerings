# TASK SCOPE — ISSUE #184-permissions

## 1. Requirements Breakdown

- **Target Objective:** Grant action-level access control for the two recycle-bin operations exposed by `GTM_RecycleBinController` (`restoreRecord`/`restoreRecords` vs. `deleteRecord`/`deleteRecords`), so that: (a) Content roles (`GTM_Content_Manager`, `GTM_Content_Admin`) can reach the class at all — today nobody can, because the class was shipped in PR #189 with a header comment explicitly stating "Permission Set grants for these @AuraEnabled actions are explicitly NOT part of this slice"; and (b) permanent hard-delete is further restricted to Admin-only, never available to `GTM_Content_Manager`/`GTM_Offering_User`, and never via org-wide Modify/View All Data, per CLAUDE.md §6.

  Investigation of the actual codebase (not just the PR description) confirms this is Content Manager's domain, not Offering's: PR #187 already granted `Archived__c`/`Archived_Date__c` field permissions on both `GTM_Page_Section__c` and `GTM_Page_Content__c` to `GTM_Content_Manager` and `GTM_Content_Admin` only. `GTM_Offering_User.permissionset-meta.xml` carries an explicit in-file comment confirming `Archived__c`/`Archived_Date__c` were deliberately withheld from that set ("reps do not directly toggle archive state"). So the correct target permission sets for this slice are `GTM_Content_Manager` (restore only) and `GTM_Content_Admin` (restore + permanent delete) — **not** `GTM_Offering_User`/`GTM_Offering_Admin`.

  Because Salesforce's `classAccesses` grant is class-level, not method-level, and `GTM_RecycleBinController` contains both the restore methods and the delete methods in one class, a plain `classAccesses` grant alone cannot separate "can restore" from "can permanently delete" within the same class. This codebase already has a reusable, in-production pattern for exactly this shape of problem: `GtmAnalyticsTeamController.hasTeamAccess()` runs a live `SELECT ... FROM PermissionSetAssignment WHERE AssigneeId = :UserInfo.getUserId() AND PermissionSet.Name = 'GTM_Offering_Admin'` check to gate a capability inside a class that both admin and non-admin callers can reach. The equivalent fix for this class is:
  1. Grant `classAccesses` for `GTM_RecycleBinController` to `GTM_Content_Manager` and `GTM_Content_Admin` (this alone unblocks restore, list, and tile-status reads for both).
  2. Add an in-code admin check at the top of `deleteRecord`/`deleteRecords` (mirroring the `PermissionSetAssignment` query pattern above, checked against `PermissionSet.Name = 'GTM_Content_Admin'`) that throws the class's existing `handledException(...)` helper with a clear "not authorized" message when the running user lacks that assignment, so a `GTM_Content_Manager`-only user who somehow reaches the Apex action (e.g. a future LWC bug, or a manual `Aura`/`fetch` call) is still blocked at the server, not just hidden in the UI.
  3. Do **not** use `FeatureManagement` or a new Custom Permission — neither pattern exists anywhere else in this codebase (confirmed via `grep` across `force-app/main/default/classes`); the `PermissionSetAssignment`-query pattern is the established convention and should be reused rather than inventing a new one.

  This sub-issue's scope is deliberately narrow. It does **not** include:
  - Building the `gtmRecycleBin` LWC itself (separate sub-issue `184-recyclebin-lwc`, confirmed still unmerged — no matching worktree/branch/PR was found in this repo checkout at scoping time, so the Developer implementing this slice cannot assume the LWC's call sites exist yet and must not couple this permission work to any LWC-side assumption beyond the controller's existing `@AuraEnabled` signatures).
  - Building any purge/hard-delete batch job (a separate sub-issue implied by the "recycle-bin" umbrella but not part of this slice).
  - Any change to `GtmOfferingArchiveCascadeHandler`, the cascade trigger, or the field-level FLS grants already landed in PR #187 (those are done; this slice is Apex-class/method access only).
  - Any change to `GTM_Page_Section__c`/`GTM_Page_Content__c` object-level CRUD grants beyond what PR #187 already set — only the class access and the in-code admin check are new.

- **System Component Impacted:** Apex (permission gating inside `GTM_RecycleBinController.cls`) + Permission Set metadata (`GTM_Content_Manager.permissionset-meta.xml`, `GTM_Content_Admin.permissionset-meta.xml`).

## 2. Code Dependency Checklist

- [ ] Modifying GUS Tool Surface? **No** — `GTM_RecycleBinController` is internal Content Manager/admin tooling (per its own class header), not a GUS `@InvocableMethod`/tool-surface class; the zero-DML tool-surface rule in AGENTS.md §1 does not apply here. This class already performs DML directly (restore/delete), consistent with its non-tool-surface status.
- [ ] Altering Custom Metadata? **No** — this slice touches only Permission Set XML and an Apex class's in-code logic; no `GTM_Assessment_*` custom metadata or `migration-accelerator/` YAML is in scope.
- [ ] Introducing database fields? **No** new fields are introduced by this slice (the `Archived__c`/`Archived_Date__c` fields already exist and were already mapped to permission sets in PR #187). This slice only adds/edits `classAccesses` entries on the two Content permission sets and an in-code `PermissionSetAssignment` check — no new field-to-permission-set mapping is required, but the Developer must double-check no other permission set (e.g. `GTM_Offering_Admin`, `GTM_Offering_User`, `GTM_Guest`) is accidentally granted `classAccesses` to `GTM_RecycleBinController`, since that would silently reopen the restore/delete surface to roles this slice intentionally excludes.

## 3. Plan Acceptance Criteria

- **Success Metric:** (1) A user assigned only `GTM_Content_Manager` can successfully call `restoreRecord`/`restoreRecords` (and the existing `getArchivedItems`/`getOfferingTileStatus` reads) but receives a server-side `AuraHandledException` with a clear "not authorized" message when calling `deleteRecord`/`deleteRecords`. (2) A user assigned `GTM_Content_Admin` can successfully call both restore and delete methods. (3) A user with neither Content permission set (e.g. only `GTM_Offering_User`/`GTM_Offering_Admin`) cannot invoke any method on `GTM_RecycleBinController` at all (class-level access denied) — confirming `GTM_Offering_*` permission sets were correctly left untouched. (4) No permission set grants org-wide `Modify All Data`/`View All Data` to satisfy this requirement.
- **Target Test Target:** A new or extended Apex test class (e.g. `GTM_RecycleBinControllerTest.cls`, following this codebase's existing `System.runAs()` + `PermissionSetAssignment` insert pattern used elsewhere for admin-gated classes) covering: Content_Manager-only user blocked from delete but allowed to restore; Content_Admin user allowed both; a user with no relevant permission set blocked entirely at the class-access layer (`System.assert` on caught `NoAccessException`/`AuraHandledException` as appropriate). Run via `sf apex run test --class-names GTM_RecycleBinControllerTest` (or the project's existing Apex test invocation convention) as part of QA.
