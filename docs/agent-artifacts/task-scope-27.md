# TASK SCOPE — ISSUE #27

## 1. Requirements Breakdown

- **Target Objective:** Stop `GtmPageContentController.setOfferingStatus(offeringKey, 'Published')` from succeeding when the offering's required pages (Story, Configurator, Offerings Listing — `OFFERING_TEMPLATES` in `force-app/main/default/lwc/gtmPageLayouts/gtmPageLayouts.js:413`, mirrored server-side as the private `templatesFor()` list in `force-app/main/default/classes/GtmPageContentController.cls:27-34`) have not actually been built. Enforce this server-side (mandatory, `AuraHandledException` naming the unbuilt page(s)) and client-side (disable "Set to Published" in `gtmContentHome`'s Manage modal with the same explanation) — server is the real gate, client is a UX courtesy that must never be the only gate. Draft transitions and Archive toggles are never blocked by this rule — only a Draft → Published transition is.

  **Root cause, confirmed by reading the code (not assumed):** `setOfferingStatus` (`GtmPageContentController.cls:931-951`) does nothing but validate `offeringKey`/`status` shape and the framework exclusion, then upserts `Offering_Status__c` on the offering's tile section with **zero check of any page's actual content**. Live testing (issue body) reproduced this: Migration Accelerator's Story, Configurator and Offerings Listing pages were all `EMPTY — no sections yet`, and "Set to Published" still succeeded.

  **The scaffold subtlety, confirmed by reading the code:** `setOfferingStatus`/`setOfferingArchived` both call a private helper, `tileSectionFor()` (`GtmPageContentController.cls:987-1008`), which — if the offering has never built or renamed its Offerings Listing tile — inserts a bare `GTM_Page_Section__c` row (`Section_Key__c='tile'`, `Template_Type__c='offerings-listing'`) with **no accompanying `GTM_Page_Content__c` field rows at all**. This is a documented, deliberate side effect ("toggling status/archived is never blocked on the offering having built its listing page first" — comment at line 984). Contrast this with `createOffering()` (`GtmPageContentController.cls:632-691`), which inserts the same tile section **plus 3 content rows** (name/mark/description), and with the normal "New page" flow, `GtmPageSectionController.createPage` (`GtmPageSectionController.cls:771-831`), which always inserts a section's field rows in the same transaction as the section itself. `tileSectionFor()` is the *only* code path in the app that creates a `GTM_Page_Section__c` row with zero matching content rows. This is exactly the "1 sections · 0 fields" scaffold the issue found live on Migration Accelerator's Offerings Listing page — most likely created by the very "Set to Published" click that the coordinator then reverted (the section row insert is not reverted by setting status back to Draft).

  **Consequence for the guard's design:** a naive `sectionCount > 0` check (the definition `nextStepHintFor()`'s "Still to build" list already uses client-side, `gtmContentHome.js:151-163`, and the one `GtmSetupChecklistController.detectOfferingPages` uses for Story/Configurator, `GtmSetupChecklistController.cls:722-748`) is provably insufficient for Offerings Listing specifically, because `tileSectionFor()` can leave a `sectionCount=1` row with no content behind it. **Recommendation: "built" = `sectionCount > 0 AND fieldCount > 0`** for all three required templates, reusing the exact two aggregate queries `getHomeSummary()` already runs (`GtmPageContentController.cls:472-512`) scoped to the one offering being published, rather than inventing a third, field-specific check (e.g. "does `description` have a non-blank value"). This is a deliberate, evidence-backed design call, not a guess — it directly closes the scaffold hole without introducing new query shapes, and it does not attempt to validate that authored text is non-blank (a section+field row created by `createPage`/`createOffering` can still have blank `Text_Value__c`/`Rich_Value__c` and would pass this check, same as the existing "Still to build" hint already accepts). **This exact boundary — AND vs. a stricter per-field non-blank check — is a real design decision inside an otherwise-unambiguous fix; flagging it explicitly rather than treating it as silently settled, per the "genuinely ambiguous" instruction.** If the Architect/owner wants the stricter bar (require `description` specifically non-blank, matching `GtmPageContentReader.getOfferingTiles()`'s own `isLive` definition at `GtmPageContentReader.cls:334-393`), that is a bigger, separate lift (a third query keyed on `Field_Key__c` and `Section_Key__c`, plus divergence between "built" as used by the Home page hint vs. as used by the publish guard) and should be called out as such rather than folded in silently.

  **Framework's "Offerings Page" — confirmed out of scope, not by omission but by design:** `setOfferingStatus` already hard-refuses the framework key (`GtmPageContentController.cls:936-938`, "The framework is not an offering and has no dashboard status"), and `gtmContentHome`'s Manage control is not even rendered for the framework card (`showManage: !o.isFramework`, `gtmContentHome.js:222`). There is no Published/Draft toggle on the Framework's Offerings Page today, so there is nothing for this guard to extend there — the issue's open question #3 is answered: not applicable, no code change needed for the framework.

  **Dashboard-surfacing nuance, confirmed by reading the reader:** the tile actually shown to reps comes from `GtmPageContentReader.getOfferingTiles()` (`GtmPageContentReader.cls:334-393`), consumed by `offeringChooser` (`force-app/main/default/lwc/offeringChooser/offeringChooser.js:219`, `:165-204`). That method already filters out anything not `Offering_Status__c == 'Published' && !Archived__c` (`GtmPageContentReader.cls:383-392`) — so a genuinely-Draft offering never appears there regardless of this bug. But it does **not** filter on content: `isLive` (`GtmPageContentReader.cls:368`, driven by whether the `description` field resolved) only changes how the tile renders (`offeringChooser.js:176-198` — a non-live tile still renders as a "Next offering" placeholder card with no link, it is not hidden). So the issue's "content-less offering landed on the Dashboard" claim is accurate but with one nuance worth recording precisely: a content-less Published offering shows up as an inert "Next offering" placeholder tile (no href, generic copy), not as a broken live link. Still wrong per the owner's rule — an unbuilt offering should not be able to reach `Published` at all — but this detail matters for anyone judging blast radius.

- **System Component Impacted:** Apex (`force-app/main/default/classes/GtmPageContentController.cls`, method `setOfferingStatus`) + LWC (`force-app/main/default/lwc/gtmContentHome/gtmContentHome.js` and `.html`, the Manage-offering modal). No Custom Metadata, no Experience Cloud route, no YAML instrument touched.

## 2. Code Dependency Checklist

- [ ] Modifying GUS Tool Surface? **No.** Nothing here touches `GtmAgentToolSurface`, `GtmAppTool`, or any tool-surface class; this is a plain `@AuraEnabled` controller method and its LWC caller. Zero-DML-in-a-tool rule (AGENTS.md §1/§2) does not apply — this method has always performed ordinary DML (the tile-section upsert) and continues to.
- [ ] Altering Custom Metadata? **No.** `GTM_Page_Section__c` and `GTM_Page_Content__c` are real custom objects (sObjects with real DML), not Custom Metadata Types — confirmed no `.validationRule-meta.xml` exists on either object (`find force-app/main/default/objects/GTM_Page_Section__c -iname "*.validationRule-meta.xml"` and the same for `GTM_Page_Content__c` both returned nothing) and nothing in this fix reads or writes `force-app/main/default/customMetadata/GTM_Assessment_*` or `instrument/<offering-key>/` YAML. **Salesforce-first check run and negative:** a native Validation Rule cannot express this guard — the check is a cross-object aggregate (count of `GTM_Page_Section__c`/`GTM_Page_Content__c` rows per `Offering_Key__c` + `Template_Type__c`, three templates deep) matched only by a plain text field (`Offering_Key__c`, not a real Lookup/Master-Detail relationship), which Validation Rules and Roll-Up Summary fields cannot evaluate (no cross-object SOQL, no roll-ups without a Master-Detail parent). This has to be Apex, same as `getHomeSummary()`'s own aggregate queries already are.
- [ ] Introducing database fields? **No.** The guard reads existing fields only (`GTM_Page_Section__c.Active__c`/`Template_Type__c`/`Offering_Key__c`, `GTM_Page_Content__c.Active__c`/`Template_Type__c`/`Offering_Key__c`) via the same aggregate query shape `getHomeSummary()` already runs under this same `without sharing` class (`GtmPageContentController.cls:12`, `:472-512`). No new field, no new permission-set grant required.

## 3. Plan Acceptance Criteria

- **Success Metric:**
  1. `setOfferingStatus(offeringKey, 'Published')` throws an `AuraHandledException` that names every required template (using `TEMPLATE_LABELS`-style names, e.g. "Story", "Configurator", "Offerings Listing") that is not built — "built" defined as `sectionCount > 0 AND fieldCount > 0` for that `Offering_Key__c` + `Template_Type__c`, evaluated for all three of `OFFERING_TEMPLATES` (`story`, `configurator`, `offerings-listing`) before any DML (including the `tileSectionFor()` scaffold insert) executes — so a rejected attempt never leaves the empty-scaffold side effect behind.
  2. `setOfferingStatus(offeringKey, 'Draft')` and `setOfferingArchived` are never blocked by this rule (archiving/un-publishing/returning-to-draft must remain unconditional, matching current behavior).
  3. A fully-built offering (`sectionCount > 0 AND fieldCount > 0` on all three required templates) still publishes successfully — no regression for real offerings.
  4. The pre-existing "1 sections · 0 fields" scaffold state on Offerings Listing (a tile section with no field rows) is correctly treated as **not built** — the guard would have blocked the exact Migration Accelerator case found live.
  5. `gtmContentHome`'s Manage modal disables "Set to Published" (not just during `manageBusy`) whenever the same unbuilt-page condition holds for the offering being managed, and shows which page(s) are missing — reusing the same `templatesFor()` + `sectionCount`/`fieldCount` data the card/`nextStepHintFor()` already receives from `getHomeSummary()`, so the modal's hint text can never disagree with the card's own "Still to build" list.
  6. `GtmPageContentControllerTest.setOfferingStatus_updatesAnExistingTileSectionInPlace` (`GtmPageContentControllerTest.cls:456-473`) currently publishes an offering created via `createOffering()`, which only seeds the Offerings Listing tile (not Story/Configurator) — this test will start failing once the guard ships and must be updated (either to build Story/Configurator fixtures first, or split into a "blocked when unbuilt" test plus an "allowed once built" test). Call this out explicitly to the Developer so it isn't mistaken for guard breakage.
- **Target Test Target:** `GtmPageContentControllerTest` (Apex — new/updated methods around `setOfferingStatus`, e.g. `setOfferingStatus_blocksPublishWhenRequiredPagesAreEmpty`, `setOfferingStatus_blocksPublishWhenOfferingsListingIsScaffoldOnly`, plus the existing `setOfferingStatus_updatesAnExistingTileSectionInPlace` fixed to seed real pages first), run via `sf apex run test --class-names GtmPageContentControllerTest --target-org gtm-staging`; and `gtmContentHome.test.js` (Jest, `force-app/main/default/lwc/gtmContentHome/__tests__/gtmContentHome.test.js`, extending the existing `describe('c-gtm-content-home: offering Manage control (Status / Archive)')` block) for the disabled-button/hint-text assertions, run via `npm test -- gtmContentHome`.
