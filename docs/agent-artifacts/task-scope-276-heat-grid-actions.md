# TASK SCOPE — ISSUE #276-heat-grid-actions

## 1. Requirements Breakdown

- **Target Objective:** Fix three UX/correctness defects in the "Who's hot right now" heat grid widget (`c-gtm-heat-grid`), now confirmed live on the `gtmOverview` app page:
  1. The disabled Nudge (and Book-the-call) buttons carry a `title`/tooltip string (`NUDGE_TOOLTIP` / `SCHEDULE_TOOLTIP` in `gtmHeatGridModel.js`) that never visibly surfaces to the user. Root cause is almost certainly a known SLDS/browser limitation: native `title` tooltips and Lightning's own tooltip machinery generally do not fire hover/focus events on an element carrying the HTML `disabled` attribute, because disabled elements are excluded from the event/accessibility tree in most browsers. `lightning-button` with `disabled=true` renders a real `disabled` attribute on the underlying `<button>`, so `title={row.actionTitle}` on it is inert. The fix needs a wrapper approach that keeps hover/focus (and touch) events alive around the disabled control — e.g. wrapping the `lightning-button` in a `<span>`/`<div>` (or `lightning-helptext`/`lightning-icon` affordance) that itself carries the `title` or an SLDS popover trigger, since the wrapper is not disabled and will receive pointer/focus events even though the inner button stays non-interactive. This must preserve keyboard-accessibility (the existing code comment at `gtmHeatGrid.js:103-111` already flags this as an a11y concern for keyboard users tabbing to a disabled control).
  2. "Call now" (`handleCallNow` in `gtmHeatGrid.js:78-90`) issues `NavigationMixin.Navigate({ type: 'standard__quickAction', attributes: { apiName: 'Task.LogACall' }, state: { defaultFieldValues } })`. Per user report this opens a modal that spins forever instead of the Log a Call quick-action form. This is a real regression, not a stub — investigate, do not just re-verify the existing code as "correct." Concrete things to check before touching the component:
     - Whether `Task.LogACall` is the correct `apiName` format for a **global** quick action reached from an **App Page** context (`gtmOverview` is a Lightning App Page tab, not a record page) — Salesforce's `standard__quickAction` PageReference type has documented constraints where it needs the invoking context to be a record page, or the action needs to be present on the relevant object's Global Publisher Layout / the object's page layout's Quick Actions section, or it silently spins.
     - Whether `Task.LogACall` needs to be object-scoped instead (e.g. a Quick Action added to the Account or Opportunity Global Actions list, referenced accordingly), since there is no existing precedent for `standard__quickAction` navigation anywhere else in this codebase (`gtmHeatGrid.js` is currently the only usage) — this is genuinely new/unverified navigation code in this app, not a copy of a working pattern.
     - Whether `defaultFieldValues`'s encoded WhoId/WhatId pairing is malformed for the current row shape (e.g. `contactId`/`opportunityId` both undefined on a given row producing an empty string that the quick-action panel then can't resolve) — reproduce with a real row from `GtmLinkStageService.getHeatGridAura`.
     - Capture the browser console/network error during the stuck-loading repro; this is exploratory investigation, not a guessed fix — if the root cause turns out to be an org configuration gap (e.g. the LogACall action isn't on the right layout) rather than component code, say so plainly in the Developer's findings rather than papering over it with a client-side workaround.
  3. Replace any non-standard/custom-built loading indicators across the app's widgets with `lightning-spinner`. An audit of `force-app/main/default/lwc/*/*.html` for "Loading" text shows most widgets (`gtmTasksDueTodayWidget`, `gtmReadoutView`, `gtmAnalytics`, the `conduit*` family, etc.) already use `lightning-spinner`. The concrete non-standard offenders found:
     - `force-app/main/default/lwc/gtmHeatGrid/gtmHeatGrid.html:11-13` — plain `<div class="heat-grid__status">Loading who's hot right now…</div>` text, no spinner at all. In scope for this ticket (it's the widget under repair).
     - `force-app/main/default/lwc/gtmOverview/gtmOverview.html:230-231` — plain `<p class="ov-empty ar-loading">Loading assessments…</p>` text for the assessments panel's loading state. Flag as an in-scope quick win since it's the same page and same "no visible spinner" defect class, but confirm with the Architect whether it's folded into this ticket or split out — it's a different sub-widget (`assessmentsLoading`) than the heat grid.
     - `force-app/main/default/lwc/gtmConfigurator/gtmConfigurator.html:605` (`showGateLoading`) — inspect before deciding; not yet confirmed as text-only vs. already using a spinner-like element. Out of scope to guarantee a fix here; note it in the PR description as a candidate for a follow-up ticket if it turns out to be non-standard, since `gtmConfigurator` is a large, separately-risky surface (content authoring) that shouldn't be touched opportunistically inside a heat-grid bugfix PR.
     - Everything else grep'd already renders `<lightning-spinner>` — no broader systemic problem, this is not a large refactor.
- **System Component Impacted:** LWC (`force-app/main/default/lwc/gtmHeatGrid/`, secondarily `force-app/main/default/lwc/gtmOverview/gtmOverview.html`). No Apex signature changes expected for items 1 and 3. Item 2 may surface an Apex or org-metadata (Quick Action layout) root cause — if so, do NOT hand-edit generated metadata; escalate the specific finding back through this scope doc's assumptions rather than silently reconfiguring org Quick Action layouts, since that crosses into deployable org config outside a pure LWC fix.

## 2. Wiring-state discrepancy — RESOLVED

The header comment in `gtmHeatGrid.js` (lines 10-18) and the component's own `.js-meta.xml` description both say the widget is "self-contained" and "NOT wired into gtmOverview.html yet," pending the `agent/issue-overview-bd-heat-redesign-1-layout-toggle` branch. That comment is **stale**. Current `main` (verified by direct read, not by trusting the comment) shows:
- `force-app/main/default/lwc/gtmOverview/gtmOverview.html:92` — `<c-gtm-heat-grid></c-gtm-heat-grid>` is present and live.
- `force-app/main/default/lwc/gtmOverview/gtmOverview.css:119-124` — has heat-grid-specific spacing rules, i.e. someone already styled it in place on the real page.
- `git branch -a` shows `remotes/origin/agent/issue-overview-heat-grid-spacing-fix` — a separate, already-existing merged/pushed branch specifically for heat-grid spacing on the live page, which only makes sense if the widget is genuinely mounted.
- `force-app/main/default/lwc/gtmOverview/__tests__/gtmOverview.dailyWidgets.test.js` explicitly tests `c-gtm-heat-grid` as one of "the three already-built, self-loading components" wired into `gtmOverview`.

**Conclusion:** the widget IS wired into the live `gtmOverview` page today. The user's report of a live "Call now" modal is consistent with this, not evidence of some other reachability path. The Developer should update/remove the stale "NOT wired into gtmOverview.html yet" comment block in `gtmHeatGrid.js` (lines 10-18) and the matching sentence in the `.js-meta.xml` `<description>` as part of this fix, since leaving it will mislead the next person who reads the file the same way this ticket's own bug report did.
