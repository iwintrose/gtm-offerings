# TASK SCOPE — ISSUE #9

## 1. Requirements Breakdown

- **Target Objective:** GitHub issue #9, "Audit and standardize tile/card design system-wide (overflow, clearing, visual consistency)." This is explicitly a **BA scoping/inventory pass**, not implementation — the owner asked for an audit of every card/tile-rendering LWC across the app for (a) text/content overflow handling, (b) clearing/flex/grid layout bugs where card content spills outside its container or cards resize inconsistently against siblings, and (c) visual look-and-feel consistency (border-radius, shadow, spacing, hover states). This is the card/tile equivalent of the existing "Table column alignment never shifts" rule already enforced for tables in this repo (custom tables must keep identical column alignment across rows, truncating overflow text rather than letting it wrap/shift a row).

  **Inventory sweep performed** (`grep -rl -E "\.card|\.tile|box-shadow|border-radius" force-app/main/default/lwc/*/*.css`) surfaced 46 LWC CSS files with card/tile-ish styling. Of these, the `conduit*` components (11 files, e.g. `conduitAuditHistory`, `conduitAssetExplorer`) belong to the separate `ma-migrator` capability-manifest domain per ADR-0009 (reference material, non-deployable) — excluded from this audit's scope. The remaining ~35 are candidates; a representative sample was read in full to characterize the actual patterns in use (evidence below), not every file line-by-line.

  **Finding 1 — at least three unrelated card/tile systems coexist, each self-consistent internally but not with each other:**
  1. **`.tile` system** (`offeringChooser.css`, `chooseIndustry.css`) — hand-rolled front-door tiles. Each file independently defines its own full CSS custom-property palette (`--bg`, `--paper`, `--ink`, `--shadow`, `--shadow-soft`, etc.) and its own `.tile { border-radius: 14px; padding: 1.5rem 1.4rem; box-shadow: var(--shadow-soft); }` block, near-identical but copy-pasted (confirmed: `offeringChooser.css` uses `padding: 1.5rem 1.4rem` / `border-radius: 14px` / `.tile-desc` at `font-size: 0.88rem`; `chooseIndustry.css` uses `padding: 1.3rem 1.3rem` / same `border-radius: 14px` / `.tile-desc` at `0.85rem` — same shape, different hand-tuned numbers, no shared source). Text overflow: **`.tile-desc`/`.tile-name` have no `overflow`/`text-overflow`/`white-space` rules at all** — long descriptions or industry names will wrap freely with no truncation or line-clamp, unlike the table rule's discipline.
  2. **`.ov-card` system** (`gtmOverview.css`, and copy-pasted verbatim into `gtmHeatGrid.css`, `gtmTasksDueTodayWidget.css`, `gtmReadoutsAwaitingWidget.css`) — a shared card chrome convention (`.ov-card` / `.ov-card-h` / `.ov-card-b` / `.ov-ic` / `.ov-h`: `border: 1px solid #e5e5e5; border-radius: .25rem; box-shadow: 0 1px 1px rgba(0,0,0,.05);` with a colored `border-top: 3px solid <accent>` per-widget) that the developers *already tried* to share and explicitly documented that they could not: `gtmHeatGrid.css` and `gtmTasksDueTodayWidget.css` both carry a code comment stating an `@import 'c/gtmLinkCell'` attempt broke Jest ("Class constructor GtmLinkCell cannot be invoked without 'new'") and that "there is no working shared-stylesheet mechanism for a real LWC component in this SDK version," so the same `.ov-card` ruleset is hand-duplicated across 4 files with an explicit maintenance instruction: "Keep in sync with gtmOverview.css's .ov-card/... block if that ever changes." This is a real, self-acknowledged drift risk — a change to one file's `.ov-card` rule silently stops matching its siblings unless a human remembers to propagate it by hand. Text overflow inside this family: `gtmHeatGrid.css` explicitly documents fixing this once already (issue #274 comment: "Stage/Latest-signal/Next-best-action had no truncation at all... only Account/Contact did"), and its current `.gtm-link-cell` rule (`overflow: hidden; text-overflow: ellipsis; white-space: nowrap; max-width: 100%;`) is itself a second hand-duplicated copy of `gtmLinkCell.css`'s rule, with the same "KEEP THESE THREE RULES IDENTICAL" comment discipline as the `.ov-card` block. So the ellipsis-truncation rule from the table-column memory *is* being followed here, but only by convention/comment, not by a shared component or build-time check.
  3. **`.sl-*` system** (`gtmSavedLinksBar.css`) — a third, independent link-row/panel styling (not a "card" in the grid-tile sense, but a bordered panel with its own `border-radius: 14px` popover and per-row items). Notably this file explicitly documents *not* inheriting the parent page's accent variable on purpose ("Fixed, page-independent accent... embedded in three different pages, each with its own --accent... Using the parent's variable made this bar's own accent color silently change"), and its `.sl-link-name` does apply `overflow: hidden; text-overflow: ellipsis; white-space: nowrap;` correctly.

  **Finding 2 — layout mechanisms are inconsistent but mostly modern:** `offeringChooser`/`chooseIndustry` use CSS Grid with `@container` queries (not `@media`) for the tile grid, correctly scoped to the component's own rendered width rather than the browser viewport — a deliberate, documented fix ("a 414px preview drew three columns... because @media rules answered the browser, not the box"). `gtmHeatGrid` uses CSS Grid for its table-row-as-card layout, wrapped in a `.heat-grid-scroll { overflow-x: auto }` container added specifically because the grid previously had no independent scroll boundary and "behaved differently from the rest of the page at the same card width" (issue #274 comment, confirmed by reading the file). No component in the sample uses legacy float-based clearing; layout bugs found are container-sizing/overflow-boundary bugs (as above), not float-clearing bugs — the issue title's "clearing" framing may not map to a literal `float`/`clear` bug in this codebase; it more precisely applies to container/scroll-boundary mismatches like the one `gtmHeatGrid` already had once.

  **Finding 3 — visual tokens are hardcoded per-component, not shared:** none of the sampled files pull border-radius/shadow/spacing from a shared design-token module or SLDS custom property; each file defines its own literal values (`border-radius: 14px` in `.tile`, `border-radius: .25rem` in `.ov-card`, `border-radius: 14px` in `.sl-panel`) or its own `--shadow`/`--shadow-soft` CSS custom properties scoped to that file's own `:host`. There is no `c-gtm-card` (or equivalent) shared LWC today, exactly analogous to the pre-extraction state issue #8 documents for `c-gtm-page-header`.

- **System Component Impacted:** LWC (`force-app/main/default/lwc/*/*.css` — CSS/markup only, no Apex, no Custom Metadata, no YAML instrument content). Read-only investigation for this ticket; no code changed.

### Recommendation: separate `c-gtm-card` effort, not folded into issue #8

Issue #8's `c-gtm-page-header` targets a narrow, already-converged pattern (2 full matches + partial matches, all inside the GTM Offerings/Content Manager admin apps). This issue's card/tile problem is broader and touches a materially different audience split: `offeringChooser`/`chooseIndustry` are the **public-facing, password-protected front door** (Experience Cloud-adjacent, client-branded, own token palette per ADR/comment evidence above), while `.ov-card` family widgets are **internal rep/admin overview widgets**. Issue #8 explicitly scopes out Experience Cloud/prospect-facing chrome as "intentionally different, client-branded" (see `docs/agent-artifacts/header-bar-consistency-assessment.md`'s "Explicitly out of scope" section) — the same boundary almost certainly applies here: a single `c-gtm-card` cannot and should not try to reskin the public offering/industry tiles and the internal `.ov-card` overview widgets identically, since one is prospect-facing brand chrome and the other is internal admin tooling. Recommend **two** shared components, not one:
1. `c-gtm-card` (internal) — extracted from the already-converged `.ov-card`/`.ov-card-h`/`.ov-card-b`/`.ov-ic`/`.ov-h` family (4 files today, exact duplication already documented and comment-enforced), closing the same "no enforcing component, comment-only sync" gap issue #8 found for headers.
2. Leave `offeringChooser`/`chooseIndustry`'s `.tile` system as its own decision: either converge those two files onto one shared `.tile` component (lower risk, same audience, only 2 files) or leave as-is pending a broader public-front-door design pass — recommend the former as a small, separate, low-risk sub-ticket given the two files are already near-identical besides hand-tuned spacing numbers.
`gtmSavedLinksBar`'s `.sl-*` panel is a different UI shape (dropdown panel, not a grid tile) and its page-independent-accent design is deliberate; recommend leaving it out of the `c-gtm-card` scope entirely rather than forcing convergence.

### Recommendation: split into a numbered series (this ticket = part 1)

Given the breadth (3+ independent systems, ~35 candidate files, two different end-user audiences), following this repo's precedent of splitting broad redesigns into numbered sub-issues (see `docs/agent-artifacts/task-scope-overview-bd-heat-redesign-1-layout-toggle.md` through `-5-visual-parity.md`), propose:

- **Part 1 (this ticket, #9):** inventory + recommendation (delivered above). No code change.
- **Part 2 — `c-gtm-card` extraction + migration of the `.ov-card` family:** extract the shared component from `gtmOverview`/`gtmHeatGrid`/`gtmTasksDueTodayWidget`/`gtmReadoutsAwaitingWidget` (refactor-only, zero visual change), closing the comment-enforced-sync gap. Add/confirm the ellipsis-truncation rule (`overflow: hidden; text-overflow: ellipsis; white-space: nowrap;`) is enforced by the shared component for every card body text field, not just the ones that already happen to have it.
- **Part 3 — `offeringChooser`/`chooseIndustry` `.tile` convergence:** smaller, separate track (public front-door only), decide whether to share a component or just reconcile the two files' hardcoded values; add missing overflow/truncation rules to `.tile-name`/`.tile-desc` (currently absent).
- **Part 4 (optional, only if new bugs surface during 2/3):** any newly-discovered overflow/clearing bugs in components outside the two families above (the 35-file candidate list was not exhaustively read line-by-line; a fuller per-file audit could be its own ticket if the owner wants full coverage rather than the two converged families identified here).

**Ambiguity flagged for the Architect:** the issue title mentions "clearing/float" bugs specifically; no float-based layout was found in the sampled files (all use flex/grid). If the owner has a specific reproduction of a clearing bug in mind, that needs to be identified by URL/screenshot before Part 2/3 work starts, since this audit did not find one — only the already-fixed `gtmHeatGrid` scroll-boundary issue (#274, already resolved) came close to that description.
