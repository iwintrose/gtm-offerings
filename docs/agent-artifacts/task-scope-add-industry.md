# TASK SCOPE — ISSUE #add-industry

Verified against `origin/main` (16222d3), not against the Architect draft or the backlog text alone. Nothing here is implemented.

## 1. Requirements Breakdown

- **Target Objective:** An admin or content editor can add an industry in the app, from Framework > Industry Chooser in the Content Manager, with nothing seeded. The industry list is "something the user enters" and the Industry Chooser page is the one place that owns it. Backlog D12 records that the only route used to be the generic "Add section" modal, which was closed on purpose (`TEMPLATE_LAYOUTS['industry-chooser'] = []`). A purpose-built flow was promised and never built. The guided-setup row `industry_added` (gap G0 in `docs/architecture/guided-setup.md` on `agent/issue-guided-setup`) cannot be completed in-app without it.
- **System Component Impacted:** Apex (`GtmPageContentController` new `createIndustry` and its test, plus a small `GtmPageContentReader.getIndustryProfiles` change, see 1.2). LWC: `gtmContentManager` (rail foot control and modal), `gtmPageLayouts` (only if a shared constant or comment is touched). Experience Cloud route `/gtm/s/choose-industry` changes only through the reader fix, not through its own files (`chooseIndustry.*` belongs to the industry-empty-state task and must not be edited). No YAML instrument, no custom metadata, no schema.

### 1.1 What exists on origin/main (verified)

- `createIndustry` does NOT exist anywhere in `force-app`. The Architect's contract is design-only.
- Server building blocks already there: `GtmPageSectionController.createSection(offeringKey, templateType, sectionKey, label, layoutType, width, fields)` normalises the key with `GtmContentAddress.normaliseKey`, refuses a duplicate `offering/template/section` key ("This page already has a section called ..."), inserts the section as `Draft`, `Active__c = true`, next `Sort_Order__c`, and inserts the layout's field rows (json defaults to `[]`, icontext to an empty shell) in one savepoint transaction. The field list comes FROM THE CLIENT (`fieldsFor(layout)` in `gtmPageLayouts.js`) on purpose, so the layout vocabulary is defined once. `createOffering` in `GtmPageContentController` is the slugify precedent (`[^a-z0-9]+` to `-`, trim dashes, 80 chars).
- The client slugify in `gtmContentManager.js` (`slugify`, 80 chars) and `GtmContentAddress.normaliseKey` are the same rule.
- Industry-tile sections that already exist are fully managed by the generic rail: listed by `getEditorSections`, icon `utility:office` (`LAYOUT_ICONS['industry-tile']`), renamed by editing the `industryLabel` field, reordered (`saveSectionOrder`), hidden (`setSectionActive`, drafted), deleted (`deleteSection`: immediate if the section is still Draft, otherwise marked and removed at Publish). Only creation is missing. The rail foot (`gcm-rail-foot`, `gtmContentManager.html` ~line 240) holds the single "Add section" button and the modal (~lines 300-330); `noLayoutsReason` (js ~line 742) is the text shown when `hasLayoutOptions` is false on `industry-chooser`.
- The `industry-chooser` starter (`STARTER_PAGES`) creates Header, Intro, `industries` (card-grid), Footer. The `industries` key does not match `industry-%`, so it is not read as an industry. Leave it alone.

### 1.2 Draft versus Published: the public page does NOT honour it today (decision needed)

Findings:
- `neverLive` at `GtmPageSectionController.cls` ~line 503 lives in `deleteField` only. It decides whether removing a FIELD row is immediate (never published and never given a value) or marked as pending-delete. It has nothing to do with visibility.
- The generic public reader `GtmPageContentReader.getPageLayout` (line ~74) only returns sections with `Active__c = true AND Status__c = 'Published'`, with a comment that a section created in the editor "does not appear at all" until Publish.
- `getIndustryProfiles` does NOT do that. It selects `GTM_Page_Content__c` rows by offering, template, `Active__c = true` and `Section_Key__c LIKE 'industry-%'`. It never reads the section's `Status__c`, `Active__c` or `Draft_State__c`. It also creates an `IndustryProfile` for a section as soon as one row exists, before it skips blank values, so a section whose rows are all blank still yields a profile. `chooseIndustry.industries` renders every profile, using `industryLabel || key` as the label.
- Consequence for any new Draft industry (created by `createSection` or a `createIndustry` that mirrors it): its rows are `Active__c = true`, so the public chooser would show a tile labelled with the KEY (for example "steel-and-metals") with no blurb, the moment it is created, before Publish, even though the editor calls it Draft. If `createIndustry` writes `industryLabel` into `Text_Value__c` (rather than `Draft_Value__c`) the real label shows too. The same gap means hiding an industry (section Active off) or a pending delete does not remove it from the public page. That last part is a pre-existing bug, not new.

Recommendation (needs the user's yes/no): make "Draft until published" true for industries by adding a section join to `getIndustryProfiles` (only sections with `Status__c = 'Published'` and `Active__c = true`), mirroring `getPageLayout`. Then: add an industry, it is Draft and invisible publicly; an editor edits it and clicks Publish on the Industry Chooser page; then it appears. This also fixes hide and delete. Cost: one more Apex file in the change, a behaviour change on live data, so a pre-check that every existing industry section on the target org is Published and Active (a read-only query on gtm-staging first; on gtm-dev a read-only query only, no deploy). An industry section that is Draft or hidden today would disappear from the public page after the change. Note the Content Manager preview (`_preview` path in `chooseIndustry`) builds tiles from Draft content by design and is unaffected.

Alternative if the user does not want to touch the reader: create the industry Published and live immediately (like `createOffering` does for its tile). Simpler, no reader change, but it contradicts the "Draft" behaviour every other section has, and a half-empty industry is public instantly. Not recommended. Do NOT ship the third option (Draft in the editor, live on the site with a key label), which is what happens by default if nothing is decided.

### 1.3 Design of the feature

**Control and location.** Content Manager > Framework > Industry Chooser page (`selectedOffering = 'gtm'`, `selectedTemplate = 'industry-chooser'`). In the rail foot, when `selectedTemplate === 'industry-chooser'`, the "Add section" button is replaced by "Add industry" (icon `utility:office`, same `gcm-add` styling). Because `TEMPLATE_LAYOUTS['industry-chooser']` stays `[]`, the generic modal stays closed and its `noLayoutsReason` text is no longer reachable there; update that string only if it becomes dead. Do NOT re-open the generic modal.

**Modal.** Title "Add an industry". One input: "Industry name" (required, max 80). Below it a read-only preview of the generated key and address (`industry-<key>` and `gtm::industry-chooser::industry-<key>`), shown, not typed, same pattern as `addKeyPreview`. Buttons: Cancel and "Add industry" (brand, disabled while the name is blank, slugifies to nothing, or a save is in flight). Client pre-check for duplicates against the loaded `sections` list (case and punctuation-insensitive by key, and also by label) with an inline message, but the server check is authoritative.

**Messages (plain).**
- Blank: "Give the industry a name."
- No usable key: "That name has no letters or numbers to build a key from."
- Too long: trim to 80, no error (matches `createOffering`).
- Duplicate: "An industry called "<name>" already exists. Edit it instead."
- Page missing: "Create the Industry Chooser page first." (matches the guided-setup `framework_pages` prerequisite).
- Any DML failure: "The industry could not be created: <detail>" (savepoint rollback, nothing half-created).

**After adding.** The modal closes, "Industry added" shows, the page reloads and lands on the new section (same `activeKey` plus `scrollRailTo` handling as `handleCreateSection`). The editor sees one new rail item, an industry-tile section labelled with the name, marked as new/unpublished, with `industryLabel` filled and every other field empty. Publish is the existing page-level Publish. Delete of a Draft industry is immediate.

**Server.** `createIndustry` goes in `GtmPageContentController` (see permission sets, 1.5). Behaviour per the Architect draft, verified as consistent with the code, with two flagged refinements:
- Label trimmed, required, at most 80 chars; key via `GtmContentAddress.normaliseKey` (do not fork the regex again); refuse a blank key; refuse a duplicate section `gtm/industry-chooser/industry-<key>`; require an existing `industry-chooser` page (any section under `gtm/industry-chooser`); insert `industry-<key>` via `GtmContentAddress.forSection`, `Layout_Type__c = 'industry-tile'`, `Width__c = 'standard'`, `Active__c = true`, `Status__c = 'Draft'`, sort order after existing; one savepoint, roll back on any DML failure; return the key.
- Refinement 1, the field list (see 1.4): do not hand-copy the 12 field keys into Apex, that recreates the drift `createSection`'s own comment warns about. Recommended signature `createIndustry(String label, List<GtmPageSectionController.FieldSeed> fields)`, the client passing `fieldsFor('industry-tile')`, the server validating that `industryLabel` is among them and that every fieldKey is one of the industry-tile keys. The guided-setup contract fixes `createIndustry(String label)`, but guided-setup only deep links to the page and never calls it, so the signature is free to change; the Architect must update section 3A/G0 of that doc accordingly. Lower-ceremony alternative for the Architect to weigh: no new Apex, the LWC calls the existing `createSection` and then `saveDrafts` for the label. It avoids an Apex deploy and full test run but is two non-atomic calls (a section with no label if the second fails) and has no "require page exists" and no `industry-` prefix guard. Recommend the atomic `createIndustry`.
- Refinement 2, where the label lives: write it as the working copy (`Draft_Value__c`, row `Status__c = 'Draft'`) so Publish copies it to the live column exactly like every other edit; leave `Text_Value__c` blank until Publish. Confirm by test that Publish then makes `getIndustryProfiles` return the label. (If the user picks "live immediately" in 1.2, then write `Text_Value__c` and set Published.)

### 1.4 Seeded field set

`gtmPageLayouts.js` `LAYOUT_FIELDS['industry-tile']` declares exactly 12 fields: text `industryLabel`, `whyHead`, `demoRoot`; rich `pickerBlurb`, `coverSub`, `problem`, `useCase`, `solution`, `proofLine`, `whyLine`; json `uniquePoints`, `demoDeps`. These match, one to one, the 12 field keys `getIndustryProfiles` reads. `createIndustry` should create all 12, empty (json rows `[]`, as `createSection` does), with `industryLabel` the only one carrying the label. Otherwise `gtmFieldEditor` shows "N fields this layout supports have no record yet" (gtmFieldEditor.js ~line 610) with a create-missing affordance, and the new industry would open in an editor that looks half-built. Note this is a superset of what the guided-setup contract says ("industryLabel and pickerBlurb"); the Architect should widen it to all 12. Field `Label__c`, `Sort_Order__c` (10, 20, ...) and types come from the same `fieldsFor` output.

### 1.5 Salesforce first, Apex, permissions and deploy

- Native check: a list view, report, or the standard record page cannot create a rows-plus-section pair addressed by `Section_Address__c`/`Content_Address__c`, cannot slugify or duplicate-check against the address, and would bypass the Draft/Publish model. The custom piece is the smallest thing that composes existing rules (`createSection` semantics, `GtmContentAddress`). The modal itself reuses base components (`lightning-input`, `lightning-button`) and the existing modal CSS; no new component.
- This DOES add Apex (`createIndustry`, possibly the reader join). An Apex deploy to a production-type org forces a full local test run (75% and every test). `gtm-dev` is Production and is not a deploy target for this work. Validate on `gtm-staging` (`--dry-run` with the test level the runbook requires) and browser-test there.
- Tests must be hermetic: create their own `industry-chooser` page and sections in the test, no Migration Accelerator data, no reliance on org content, no `SeeAllData`. Add to `GtmPageContentControllerTest`: happy path (12 fields, `industryLabel` draft-set, section Draft and Active, sort after existing), slug/duplicate refused (case and punctuation variants, second insert leaves counts unchanged), blank label, label with no letters or numbers, over 80 characters, missing `industry-chooser` page, rollback on failure, an industry key colliding across offerings does not matter (always `gtm`). If the reader join ships, add to `GtmPageContentReaderTest`: a Draft industry is not returned, a hidden industry is not returned, a Published and Active one is returned with its label, after publish via `GtmPageContentController.publishPage`. Do not weaken existing reader tests.
- Permission sets. Verified: `GtmPageContentController` and `GtmPageContentReader` are both already granted in `GTM_Content_Manager` and `GTM_Content_Admin`. `GtmPageSectionController` is granted only there (not in `GTM_Offering_Admin` or `GTM_Offering_User`). `GTM_Offering_Admin` and `GTM_Offering_User` also hold `GtmPageContentController`, and `GTM_Guest` holds only the Reader. Because `createIndustry` goes in `GtmPageContentController` and is not a new class, NO permission set change is needed, and `GTM_Offering_Admin` can call it, which the guided-setup admin needs anyway. No new object or field, so no FLS work; the checklist below stays unchecked. Watch: `GtmPageContentController` is `without sharing` and is also granted to `GTM_Offering_User`, so any rep can call `@AuraEnabled createIndustry`, exactly as `createOffering` can be called today. The Architect should decide whether to add an `Schema.sObjectType.GTM_Page_Section__c.isCreateable()` guard (recommended for the new method; do not retrofit existing methods here). If `createIndustry` were placed in `GtmPageSectionController`, `GTM_Offering_Admin` would need a new `<apexClass>` grant, another reason to keep it in `GtmPageContentController`.

## 3. Plan Acceptance Criteria

- **Success Metric:** In a browser on gtm-staging, on a blank install where only the Industry Chooser page has been created (no industries, none seeded), as a user with `GTM_Content_Manager` (repeat once with `GTM_Content_Admin`):
  1. Framework > Industry Chooser shows an "Add industry" control in the rail and no "Add section" generic modal path for that page; other pages (an offering page, FAQ) still show "Add section" unchanged.
  2. "Add industry", type "Financial Services": the modal previews `industry-financial-services` and its address, the button is disabled while the field is blank or has no letters or numbers, and an inline message explains why.
  3. Submit: the modal closes, the rail lands on a new industry-tile section, "Financial Services", marked unpublished, with `industryLabel` filled and the other 11 fields empty, and no "fields have no record yet" notice.
  4. Before Publish (if the user approves the 1.2 reader fix): the public `/gtm/s/choose-industry` page still shows the neutral "No industries have been set up yet" notice (the separate industry-empty-state PR) and no ghost tile. After Publish: the tile "Financial Services" appears with its label and, once a blurb is written and published, the blurb; clicking it goes to the configurator with `?industry=financial-services`. If the user instead picks "live immediately", the tile appears without Publish.
  5. Adding "financial services", "Financial-Services" or "Financial Services!" is refused with the duplicate message and creates nothing (section and row counts unchanged). Adding "!!!" is refused. A name over 80 characters is trimmed.
  6. Deleting an unpublished industry is immediate and clean (no orphan rows); deleting a published industry marks it and Publish removes it and its rows, after which the public page returns to the empty notice. Rename (edit `industryLabel`), reorder and hide/show all still work on it; hiding then Publishing removes it from the public page (this passes only with the reader fix).
  7. No industry, offering, page copy or example content exists after deploy or setup until the user adds it. Every test creates its own data.
  8. QA checks every dependent surface, not just the modal: Content Manager on an offering page, guided-setup `industry_added` row if that branch is present (it should read DONE via `getIndustryProfiles` with a non-blank label once published), the configurator `?industry=` route for the new key, and the preview pane on the Industry Chooser page.
  9. Full local test run (`sf apex run test --test-level RunLocalTests`) and `npm test` pass; `--dry-run` deploy validation on gtm-staging passes. Nothing deployed to gtm-dev.
- **Target Test Target:** Apex: `GtmPageContentControllerTest` (new `createIndustry` cases) and, if the reader join ships, `GtmPageContentReaderTest`; then the full local run. LWC Jest: `force-app/main/default/lwc/gtmContentManager/__tests__/gtmContentManager.test.js` (Add industry control appears only on `industry-chooser`; modal key preview; disabled states; duplicate and server-error messages; success lands on the new section; generic "Add section" unchanged elsewhere) and, only if touched, the `gtmPageLayouts` spec.

**Risks.**
- The reader change alters live behaviour on production-type data; any existing industry section that is Draft or hidden vanishes publicly. Mitigate by a read-only pre-check query on staging (and, read-only, on gtm-dev) before deciding.
- A non-atomic implementation (createSection then saveDrafts) can leave a label-less section.
- Field-list drift if the 12 keys are hand-copied into Apex; use the client vocabulary with server validation.
- `without sharing` plus class grant to `GTM_Offering_User`: add an isCreateable guard.
- Full local test run on an Apex deploy is slow and any unrelated failing test blocks it; repair root causes, do not skip.
- Guided-setup doc G0 says `industryLabel` and empty-safe `pickerBlurb` only and a one-arg signature; update it in the same Architect pass to avoid contract drift (a blocked defect under CLAUDE.md §4).

**Open questions for the user.**
1. Draft versus Published (needs a decision): should a newly added industry stay invisible on the public chooser until published (recommended, requires the `getIndustryProfiles` section join and its behaviour change), or appear immediately? Today's code would show a key-labelled ghost tile the moment it is created, which we should not ship.
2. Do you accept fixing the pre-existing gap that hiding or pending-deleting an industry section does not currently hide it publicly, as part of the same reader change?
3. Atomic `createIndustry(label, fields)` (recommended; changes the guided-setup contract signature) versus the no-new-Apex option with two calls?
4. Should the modal ask for anything beyond the name (for example the picker blurb) or stay name-only? Recommended name-only, per "the key is generated, not typed", with the blurb edited afterwards in the normal field editor.
5. Should industries be case-insensitive unique by label as well as by key (recommended: key only on the server, label warned on the client), and is there any maximum on the number of industries?
6. Should the `industries` card-grid section the starter creates stay as is (it is not read by the public chooser)? Recommended: yes, untouched in this task.
