# TASK SCOPE — ISSUE #app-landing-page

## 1. Requirements Breakdown

- **Target Objective:** When a rep opens the GTM Offerings app on gtm-staging they see a "Home" tab showing Salesforce's stock Home page (generic Tasks / Today's Events / Assistant). The user asks: rather than creating or maintaining a custom overview page, can we EXTEND the standard Home (a Lightning App Builder Home page assigned to the GTM Offerings app, adding our components and hiding or replacing generic ones), or should the app simply land on the existing Offerings Overview tab? Deliver a "Salesforce first" comparison and a recommendation. This scope is a decision document; nothing is implemented here.
  - **Scope addition (user, stated later):** the same rule applies to the GTM Content Manager app, which has its own custom "Home" tab (`GTM_Content_Home`). **The user's stated preference for BOTH apps is the extended standard Home page** (a Lightning App Builder Home FlexiPage assigned to each app), and NOT a custom home tab. ### Options compared (Salesforce-first)

**Option A: extend the standard Home with a custom Lightning Home page (FlexiPage type `HomePage`).**
- Mechanics: create a `HomePage` FlexiPage (Lightning App Builder) with our components; make `gtmOverview` (or split pieces of it) available on it by adding `<target>lightning__HomePage</target>` to `gtmOverview.js-meta.xml`. Note: `lightning__HomePage` is the target for the org Home tab, `lightning__AppPage` for App pages; a component exposed to only AppPage cannot be dropped on a HomePage. Assign the page to the app via `profileActionOverrides` (page type `Home`, actionName `View`, `type` `Flexipage`, content = flexipage name, profile) inside the CustomApplication. Lightning App Builder offers three activation levels for a Home page: Org Default, App Default, and App-and-Profile. **App Default is the right level here**: it applies to every profile that opens that app and leaves other apps' Home alone. In metadata this is an `actionOverrides` entry on the CustomApplication (`actionName` View, `pageOrSobjectType` `standard-home`, `type` Flexipage, `content` = FlexiPage API name); the per-profile variant is `profileActionOverrides`. The Architect must VERIFY on staging (retrieve after activating in App Builder) that the app-level `actionOverrides` form round-trips for `standard-home`; this agent could not confirm it against an org. Org Default is not acceptable (changes Home for every app in the org).
- Files touched: new `flexipages/GTM_Offerings_Home.flexipage-meta.xml`; `lwc/gtmOverview/gtmOverview.js-meta.xml`; `applications/GTM_Offerings.app-meta.xml` (add `standard-home` tab and `profileActionOverrides` per profile); possibly the profiles listed by those overrides.
- Deployable as metadata: yes (FlexiPage, CustomApplication with profileActionOverrides). Hiding/removing the generic Tasks/Events/Assistant panels: a HomePage FlexiPage built from a template contains only the components we list, so "hiding" is by omission; no override of the standard components is needed.
- Packageable: FlexiPage and CustomApplication are unlocked-package-supported. If the app-level `actionOverrides` form is used (App Default), there is no profile-name dependency and this is packageable and blank-install safe. If only the per-profile `profileActionOverrides` form works, it references profiles by name, which cannot be enumerated for a customer's custom profiles, and that would be the weak point for the package (fallback: Option B for that app). This is the one item that could flip the recommendation and must be proven on gtm-staging first.
- Costs and drawbacks: Home is a "shared" page. Our LWC's known layout constraints apply: `gtmConfigWizard._measureChromeOffset` (documented in `gtmOverview.html`) assumes the wizard is the first child of the top of the page; on a Home page with region components or a different template the offset can be wrong and the wizard would render off screen. `gtmOverview` is a full-page component (page header, tiles) designed as the tab body, so hosting it in a Home page region is dubious unless it is the only component. A HomePage FlexiPage without the header/template chrome also duplicates the "Overview" page (two places to maintain) unless Overview is removed. Effort: medium (FlexiPage, meta target change, app overrides per profile, Jest unchanged, manual layout verification on staging, wizard offset re-verification).
- Does it satisfy "extend rather than maintain a custom page"? Partly: the LWC bodies are unchanged and Home is the native surface, but two thin HomePage FlexiPages are new metadata to maintain, and this is only a real win if the custom tabs are then retired (otherwise there are two landing pages).

**Option B: make Overview the landing tab and take Home out of the nav.**
- Mechanics: in a Lightning Standard-nav app the landing item is the first item in the app's tab list. Source already has `GTM_Offerings_Overview` first and no `standard-home`. So in source B is already the state of the world. What remains is to make staging match: redeploy the app metadata so Home is absent (deploy REPLACES the tab list for the app). If Home reappears through user personalization, it can be prevented by `isNavPersonalizationDisabled=true` (trade-off: users lose ALL personalization of the nav, including pinning their own tabs) or the rep can be told to remove it. If the source of Home is the org's default app fallback for a user with no visible app, that is a profile app-visibility matter, not a Home matter.
- Home cannot be "hidden" in Lightning app config in any way other than omitting `standard-home` from the tabs. There is no hide flag.
- Files touched: `applications/GTM_Offerings.app-meta.xml` only (and only if drift shows `standard-home` re-added or personalization must be disabled). Possibly the `default` flag on app visibility in a profile/permission-set if the app should open by default (out of scope unless asked).
- Deployable: yes, fully. Packageable: yes, no per-profile references, nothing new. Effort: minimal (possibly zero source change; a staging redeploy plus a check). Risk: low; rep data scoping already lives in the Apex.
- Drawback: the Overview page is still custom, but it already exists, is tested, and is maintained anyway.

**Option C: leave as is.**
- No change. Reps continue to see whatever staging currently has (a generic Home tab, possibly alongside Overview). Zero effort, but does not resolve the user's complaint that reps see non-app content. Note that leaving as-is on staging while source differs leaves environments inconsistent (blank-install would deliver Overview-first, staging delivers Home), which is itself a defect to be traced.

### Cross-cutting risks and constraints

- **gtm-dev is Production and is not a deploy target for this work**; gtm-staging is the test org. No deploy or org run against gtm-dev in any option.
- **Permission sets:** Overview tab is granted in `GTM_Offering_User` and `GTM_Offering_Admin`. Option B needs no new grants. Option A: a FlexiPage is not permission-set-gated (visibility comes from the profile override and app visibility), but any component newly exposed to Home must keep its Apex classAccess grants in the User and Admin sets. If a new tab or component is added anywhere, all five sets (`GTM_Offering_User`, `GTM_Offering_Admin`, `GTM_Content_Manager`, `GTM_Content_Admin`, `GTM_Guest`) must be reviewed, with the guest and Content sets expected to have no grant. The standard `standard-home` tab needs no grant.
- **Audiences:** internal reps (`GTM_Offering_User`) and admins (`GTM_Offering_Admin`) land here; Content Managers use the separate GTM Content Manager app (has its own `GTM_Content_Home` tab) and are unaffected. Rep data ownership: `GtmHomeSnapshotController` is `with sharing` plus explicit `OwnerId = UserInfo.getUserId()` scoping, so a rep sees only their own links and related records regardless of where the LWC is placed. Admins see the org-wide variant per the controller's own logic. Mounting on a Home page changes nothing here.
- **Experience Cloud / guest sites:** unaffected in all options. The `lightning__HomePage`/`lightning__AppPage` targets do not touch `lightningCommunity__*` targets; `gtmConfigWizard` also renders on two Experience sites, which must not be touched.
- **Blank install and future unlocked package (ADR-0001):** Option B is trivially safe. Option A adds a profile-name-keyed override that cannot be packaged generically, and `deploy-fresh-org.sh` `--with-profiles` behavior would need review. Do not adopt A without a packaging answer.
- **Contract First:** none of the options changes an Apex signature, LWC data contract or schema. If Option A goes ahead, the LWC exposure target change and the page-assignment mechanism must be recorded in a new `docs/architecture/` note BEFORE implementation. Option B needs at most a one-line note in the app's nav section of the docs, if one exists.
- **Mobile:** `formFactors` is Large only; Home for phone is irrelevant.
- **Do not touch** the worktree or branch `agent/issue-site-shell-metadata` (in flight in a separate PR); this scope must not modify metadata that PR changes (verify whether it touches `applications/`, before the Developer starts).

### Recommendation (BA view, for human/Architect ratification)

The user prefers the extended standard Home for both apps, and the Salesforce-first rule agrees: Home is a native, admin-editable surface and the App Default assignment is native. Recommended path, per app, in order:

1. **Gate (blocking):** on gtm-staging, prove that an App Default Home FlexiPage assignment (app-level `actionOverrides` on `standard-home`) exists as retrievable/deployable metadata and does not require per-profile entries. Also retrieve the current staging `GTM_Offerings` app and find out why Home appears there at all (source has none; see Q1). If app-level assignment does not round-trip, stop and take the decision back to the user (fallback: Option B for the affected app).
2. **Expose the components on Home:** add `<target>lightning__HomePage</target>` to `gtmOverview.js-meta.xml` and `gtmContentHome.js-meta.xml` (keep `lightning__Tab` and `lightning__AppPage` during transition). Both are full-page tab bodies (own header, own modals), so the simplest Home page is a ONE-region Home FlexiPage holding just that component, which also keeps the wizard mount at the top (see `gtmOverview.html` comment on `_measureChromeOffset`; the Architect must re-verify the wizard renders on-screen at scroll 0 and 500px on a Home page, since Home adds its own region chrome). Do not put both apps' components on one Home page.
3. **Create two FlexiPages of type `HomePage`:** one for GTM Offerings, one for GTM Content Manager, each assigned as App Default of its own app only. Add `standard-home` as the first tab in each app so the Home item exists and is the landing item. (Building a Home page that MIXES our component with standard components -- reports, list views, Tasks -- is possible and is the reason Home is worth using; only add those if the user asks, Q2.)
4. **Retire the custom home tabs in two steps, not one:** (i) first deploy, remove `GTM_Offerings_Overview` and `GTM_Content_Home` from the two apps' tab lists but leave the tab files and permission-set `<tab>` grants in place, so a rollback is a one-line app change; (ii) after staging QA passes, delete both `tabs/*.tab-meta.xml`, remove the `<tab>` entries from `GTM_Offering_User`, `GTM_Offering_Admin` (Overview) and `GTM_Content_Manager`, `GTM_Content_Admin` (Content Home), and delete the `lightning__Tab` target if nothing else uses it. Deleting a tab from an org needs a destructive-changes deployment (a normal source deploy does not remove it); do it on gtm-staging only. Keep a custom tab only if something truly needs it: today the only hard dependents found are the GUS `ALLOWED_NAVIGATION` entry, the `GtmStageFilterAppToolTest` fixture and docs, all of which are code/doc updates, not reasons to keep the tab.
5. **Update the GUS navigation contract** (`docs/architecture/gus-utility-bar-host.md`) BEFORE code: the "Overview" navigation target becomes a `standard__namedPage` `home`, and the allow-list shape (currently apiName -> state keys for `standard__navItemPage`) needs a decision for a namedPage entry. This is the one non-trivial code touchpoint and it is out of the "metadata only" zone.

**Rep vs editor audiences:** GTM Offerings Home serves reps and admins; rep-scoping is already enforced by `GtmHomeSnapshotController` (`with sharing` + `OwnerId = running user`), so it holds unchanged on a Home page. GTM Content Manager Home serves content editors/BAs (`GTM_Content_Manager`, `GTM_Content_Admin`); no rep-ownership rule applies and they must not be given rep or GUS permissions as a side effect.

**Risks of removing the custom tabs:** (a) users with bookmarks or personalized nav pointing at `/lightning/n/GTM_Offerings_Overview` or `/lightning/n/GTM_Content_Home` get a broken link, so announce it and keep step 4(i) live for one cycle; (b) the GUS navigation allow-list (above); (c) the Content Manager Home is a heavy component (modals, feedback queue); confirm it behaves correctly inside the Home page shell (tab persistence/refresh, `CurrentPageReference` usage in `gtmContentHome`); (d) other apps' Home unchanged only if App Default (not Org Default) is used; (e) gtm-dev must not be touched, since it is Production.
