# TASK SCOPE — ISSUE #assessments-tab-filter

## 1. Requirements Breakdown

- **Target Objective:** Owner: "a similar sort of filter should be available on the All assessments tab too." Add a filter bar to the Assessments tab (GTM_Assessments, `gtmReadoutsOverview`, "All Assessments" mode) so a seller can decide whom to call. Dimensions: request status; readiness tier; readout status (waiting on approval / approved not sent / published); submitted date range (7/30/90 days); offering; plus a named shortcut "Ready to book" (Status New AND tier Fast-Track or Accelerator-Ready). Filter state lives in the URL (c__ params via `@wire(CurrentPageReference)` plus a `history.replaceState` write, the existing idiom), filters are clearable, active filters are visible with an accurate result count. Definitions live in ONE server-side Apex place (rows + counts), no DML, rep-scoping preserved (rep sees own, admin sees all). Pattern mirrors sibling `stage-filter-pages-tab` (`c__stage=<key>`), but this issue is independent of it (different tab, different objects) and can proceed in parallel.

- **System Component Impacted:** LWC `gtmReadoutsOverview` (html/js/css/tests) and Apex (new server-side filter definition + query, see forks). No Experience Cloud route, no YAML instrument.

### Current state (verified in code, not from specs)

- **The tab has no filters today.** The header is `c-gtm-page-header` ("Find an assessment") with a Refresh button; a two-button mode toggle ("All Assessments" / "By Account or Contact"); then a flat card grid. Nothing else.
- **CRITICAL FINDING: the "All Assessments" grid is a list of READOUTS, not assessment requests.** `loadReadouts()` calls imperative `GtmReadoutController.getReadoutsForReview()`, which queries `GTM_Readout__c WHERE Status__c IN ('Draft','Pending Approval','Approved') ORDER BY LastModifiedDate DESC LIMIT 200`. Consequences:
  - Published readouts are excluded (so "published" cannot be filtered on today).
  - An assessment request with NO readout (e.g. a brand-new submission) never appears in this grid. "Ready to book" (Status New) would therefore mostly return nothing from the current data source. The card shows readout status badge, requester/company, request name, last-modified. It does not show request status, tier, score or submitted date.
  - Empty-state copy: "No draft or approved readouts right now."
- Request-level lists exist elsewhere: `GtmHomeSnapshotController.getRecentNewAssessmentRequests()` (Status New only, LIMIT 5, admin via `PermissionSet.Name='GTM_Offering_Admin'` else `OwnerId = running user`) and the account-trail Apex in `GtmReadoutController` (`getContactsWith...`/`RequestSummary`, ownership via `hasViewAllRecords('GTM_Assessment_Request__c')` else `OwnerId = currentUserId`). "By Account or Contact" mode uses the latter and is unfiltered.
- Existing URL params read in `capturePageRef`: `c__assessmentRequestId`, `c__readoutId`, `c__offeringKey` (workspace open), `c__browseMode` (`account`; `all` omitted), `c__repDirectId` (modal). All written by `writeSelectionToUrl()` with `replaceState`, best-effort in try/catch. New params must be added to that same writer/reader and must not disturb these. Note `capturePageRef` returns early when `c__assessmentRequestId` is absent, so new param parsing must go BEFORE that early return.
- Fields (verified in `objects/`): `GTM_Assessment_Request__c.Status__c` = New / Contacted / Scheduled / Completed / No Show; `Assessment_Tier__c` = Discovery First / Prep Required / Accelerator-Ready / Fast-Track (picklist order in metadata is exactly that); `Assessment_Score__c`; `Submitted_At__c`; `Offering_Key__c`; `Saved_Configuration__c`; `Source__c` is free Text (255), NOT a picklist, so it is not a reliable "Rep_Direct origin" discriminator. Rep_Direct is a `GTM_Saved_Configuration__c` concept and per existing comments a Rep_Direct config has no request until the prospect submits. `GTM_Readout__c.Status__c` = Draft / Pending Approval / Approved / Published, with `Assessment_Request__c` lookup, `Published_Date__c`, `Approved_Date__c`, `Notification_Sent_Date__c`.
- Sharing: both objects `sharingModel` Private. Owners differ: readouts may be owned by the `GTM_Readout_Triage` queue (orphans; `getReadoutsForReview` uses "own OR my queues" and `hasViewAllRecords('GTM_Readout__c')`), whereas requests use plain `OwnerId = me` / `hasViewAllRecords`.

### Open forks for the Architect (do not treat as settled)

1. **(Resolved by product owner, see Amendment 2: row grain = one row per GTM_Assessment_Request__c; forks renumbered as listed, original numbering kept below for cross-reference.)**
2. **Tier ordering.** "Ready to book" = New + (Fast-Track OR Accelerator-Ready) assumes the two higher tiers are "ready". That is inferred from picklist labels only; no scoring doc was checked to define it. Architect to confirm with the instrument/scoring owner (see `instrument/` tier thresholds and `Assessment_Tier__c` writers) before it ships. Do not hardcode without a source.
3. **Readout-status keys mapping.** "Waiting on approval" = readout Pending Approval; "approved not sent" = Approved (and, if desired, `Notification_Sent_Date__c` null / not Published); "published" = Published. Confirm Approved-not-sent semantics (Approved vs Approved with no notification sent).
4. **Ownership predicate for the joined grain.** Readout grain must keep own-or-queue + view-all semantics; request grain must use request `OwnerId`/view-all. Pick ONE consistent rule and document it; do not introduce a permission-set-name check (`isAdmin()` in `GtmHomeSnapshotController` is the pattern being phased out per the rep-data-scoping-owd docs; prefer `hasViewAllRecords`). Since Overview tiles link here, Overview counts and tab counts must use the same predicate.
5. **Single-select vs multi-select** per dimension and whether dimensions AND together (assumed AND across dimensions, single value within). "Ready to book" named shortcut: a preset key (`c__apreset=ready-to-book`) that Apex expands, versus setting astatus+atier in the URL. Recommend preset key expanded server-side so the definition exists in one place.
6. **Result cap.** Today LIMIT 200. "Accurate result count" must be the true count, not the capped list length; decide count query vs cap disclosure ("showing first 200 of N").
7. **Date range boundary.** Which field defines "submitted" (`Submitted_At__c` vs `CreatedDate` fallback when null) and whether range is inclusive and computed server-side in the running user's timezone/UTC.
8. **Account-trail mode.** Filters apply to "All Assessments" mode only in this issue; confirm the trail is out of scope and filter params are ignored (but preserved in the URL) when `c__browseMode=account`.

### Proposed URL contract (Architect to finalise; all distinct from existing params)

`c__astatus` (New|Contacted|Scheduled|Completed|No Show, slugged), `c__atier` (discovery-first|prep-required|accelerator-ready|fast-track), `c__areadout` (waiting-approval|approved|published), `c__arange` (7|30|90), `c__aoffering` (Offering_Key__c; note existing `c__offeringKey` is the workspace selection and must NOT be reused), `c__apreset` (ready-to-book). Unknown/invalid values are ignored (treated as no filter), never throw. Absent params behave exactly as today.
