### Defect 1 — Instrument Editor header "Test Offering · vundefined"

- **Root cause (verified):** `gtmInstrumentAuthor.js` `get headerMeta()` (~line 186) returns `` `${offeringLabel} · v${this.pack.version}` `` whenever `this.pack` is truthy. For an offering with no instrument, `getPack` (GtmAssessmentRequestController -> GtmAssessmentInstrument.getPack / basePack) returns a non-null pack DTO whose `version` is only set when a `Version__c` row exists (GtmAssessmentInstrument.cls ~line 863), so `version` is undefined. The same defect exists in the template at `gtmInstrumentAuthor.html:45` (`pack: {pack.pairKey} · v{pack.version}`).
- **Decision:** LWC-only guard. Add a `hasVersion` getter (pack.version not null/undefined/blank). `headerMeta` appends ` · v<N>` only when it is true, otherwise `<offeringLabel> · No instrument yet`. In the template, show the `pack:` chip only when a version exists, so there is no "vundefined" there either. Empty-state wording ("No instrument yet") is a copy decision to confirm with the human, see Open Questions. Native Salesforce is not applicable (custom authoring screen).
- **Files touched:** `force-app/main/default/lwc/gtmInstrumentAuthor/gtmInstrumentAuthor.js`, `.html`, and its Jest spec under `__tests__/`. Jest: YES (add: pack with no version renders no "vundefined"; pack with version 3 renders "v3").
- **Do not** change the Apex to invent a version; `Version__c` semantics (bumped on publish) stay as is per `docs/architecture/gtm-instrument-editor.md`.

### Defect 2 — "MA Assessment Draft Purge" on the Scheduled Jobs card

- **Root cause (verified):** `GtmScheduledJobsController.getStatuses()` always returns both jobs with hardcoded labels, including `'MA Assessment Draft Purge'`. The job it backs, `GtmAssessmentDraftPurge`, deletes expired `GTM_Form_Draft__c` rows scoped to `Draft_Type__c = 'Assessment'` (questionnaire resume drafts). It has no dependency on a Migration Accelerator pack, and the card reads only CronTrigger by job name (no custom object or setting). So the job is legitimately framework-level: the framework's assessment questionnaire exists on every install. "MA" is legacy naming from the Migration Accelerator origin, not a real precondition.
- **Decision:** Do NOT hide it. Relabel the displayed text only, to "Assessment Draft Purge" (or "Expired assessment drafts purge", confirm copy). Do it in the LWC (`gtmScheduledJobsSettings.js`, map `jobKey` `assessmentDraftPurge` to the new label when rendering rows) so that NO Apex changes: the CronTrigger job name string `'MA Assessment Draft Purge'` in `GtmAssessmentDraftPurge.JOB_NAME`, in `GtmScheduledJobsController.JOB_NAME_ASSESSMENT_DRAFT_PURGE`, and in `docs/runbooks/questionnaire-resume.md` line 170 MUST stay unchanged, because renaming it would orphan already-scheduled jobs in live orgs (they would show "Not scheduled"). Renaming the job itself is out of scope and would need a separate migration plan.
- **Files touched:** `force-app/main/default/lwc/gtmScheduledJobsSettings/gtmScheduledJobsSettings.js` (and possibly `.html` intro copy), its Jest spec `__tests__/gtmScheduledJobsSettings.test.js` (existing spec references the old label; update it). Jest: YES. Apex: NONE. If the human insists the label come from Apex, that becomes an Apex change to `GtmScheduledJobsController.cls` and its test, which forces a full test run on deploy — call that out and get sign-off first.

### Defect 3 — Content Manager "No offerings set up yet" while the picker lists offerings

- **Root cause (verified):** It is rendered by `gtmContentManager.html` (~lines 133-139), in the `if:false={hasOffering}` and not-loading "Choose an offering to begin" block. The sentence "No offerings set up yet — ask an admin to add one." is static text inside that block. It is NOT driven by any offerings-count condition, so it shows whenever no offering is selected, even when the picker is populated. It is also effectively unreachable as a true statement: `GtmPageContentController.getOfferings()` always prepends the "Framework (all offerings)" entry, so the list is never empty.
- **Draft reconciliation:** No conflict. `getOfferings()` deliberately returns every `GTM_Offering__mdt` row plus page-only offerings and applies no Published filter, because the authoring tool must let editors open drafts to build them. The Published filter (GtmPageContentReader `Status__c = 'Published'`) applies to reader-facing surfaces (rep Overview, public chooser). So the draft offering appearing in the picker is correct; only the copy is wrong. gtmOverview.html ~line 308 has the same sentence, but there it is conditioned on an empty list and is out of scope.
- **Decision:** Drop the static sentence, or make it conditional on a `hasNoRealOfferings` getter (`offerings.filter(o => o.offeringKey !== framework key).length === 0`) with wording that is true ("No offerings yet besides the Framework — add one from Settings"). Smallest correct fix: keep "Choose an offering to begin." and show the extra sentence only in the genuinely-empty case. Do not filter drafts out of the picker.
- **Files touched:** `force-app/main/default/lwc/gtmContentManager/gtmContentManager.html`, `.js` (getter), Jest spec in `__tests__/` (Jest: YES, add cases: picker populated shows no "No offerings set up" text; Framework-only shows it). Apex: NONE.

### Defect 4 — Config wizard slide-out leaves a 32px undimmed strip (nav at y=128, panel at y=160)

- **Root cause (verified):** `gtmConfigWizard._measureChromeOffset()` (js ~line 355) computes `Math.round(host.getBoundingClientRect().top + window.scrollY)`. That is the HOST's page position, not the Salesforce chrome height. The "KEEP THIS FIRST" comments in `gtmOverview.html` and `gtmConfigurator.html` rely on the host being the first child so the value equals the chrome height, but this is only true if nothing above the host adds space. Any container padding/margin above the mount point (here ~32px, i.e. the `.ov` container / Home page shell region padding, in both the new Home page and the old tab) is added to the measured offset, so top = 160 while the real nav bottom is 128. (The CSS fallback is 106px in `gtmConfigWizard.css` `.mw-scrim--standalone` / `.mw-sheet--standalone` and the JS `_standaloneTopOffset = 106`; it is only the fallback and is not the source of the 32px.) `gtmModalShell._measureChromeOffset` has the identical formula, so it carries the same latent defect.
- **Decision (fix in the wizard, not per-host):** stop inferring chrome height from the host position. Measure the chrome bottom directly: at open time (not only one tick after connect), find the bottom edge of the Salesforce global header/nav (e.g. bottom of the app nav bar via `document.querySelector` on the LEX chrome, guarded by try/catch), and fall back to the current host-based value and then 106 if not found. Also re-measure when `is-open` turns true and on `resize`. Architect must verify feasibility under Lightning Web Security/Locker (document-level queries may be restricted) and, if the DOM query is not reliable, choose the alternative: a zero-height probe element with `position: fixed; top: 0` cannot find the chrome either, so the fallback option is to mount the wizard in a padding-free wrapper at the very top of the host page/region and keep the existing formula. Native option to evaluate first ("Salesforce first"): `lightning-modal`/native overlay or quick-action panel that Salesforce positions itself. Architect must document why it does or does not fit the slide-out UX before custom work.
- **Home page shell:** the new Home page wizard mount (gtmOverview under the GTM_Offerings_Home flexipage, added/changed in PR #239) must be verified in the browser after the fix, and its container padding must not re-introduce the gap.
- **Files touched:** `force-app/main/default/lwc/gtmConfigWizard/gtmConfigWizard.js` (+ `.css` if fallback values change), `gtmModalShell.js` if the same formula is shared/kept in step, and possibly the "KEEP THIS FIRST" comments in `gtmOverview.html` / `gtmConfigurator.html` (update wording). Jest: YES, `gtmConfigWizard/__tests__/gtmConfigWizard.test.js` (mock getBoundingClientRect/nav element; assert top equals measured chrome bottom and fallback path). Apex: NONE. Also a `docs/architecture/gtm-modal-shell.md` update if the measurement contract changes.
