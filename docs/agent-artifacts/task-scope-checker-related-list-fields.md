# TASK SCOPE — ISSUE #checker-related-list-fields

## 1. Requirements Breakdown

- **Target Objective:** Remove 17 false-positive deploy-blocking findings from `python3 scripts/check-references.py` section 9 (LAYOUTS AND LIST VIEWS). Verified today: the 17 `x` findings are all on `GTM_Assessment_Request__c-Assessment Request Layout` (5), `GTM_Readout__c-GTM Readout Layout` (3) and `GTM_Saved_Configuration__c-GTM Saved Configuration Layout` (9), all introduced by commit e3eedc8 (related lists). Cause (scripts/check-references.py ~lines 656-668): the loop `for el in list(r.iter(NS+"field")) + list(r.iter(NS+"fields"))` treats every `<fields>` element as a column of the layout's own object. Inside `<relatedLists>`, `<fields>` are columns of the CHILD object named in the sibling `<relatedList>` element, whose value is `ChildObject__c.LookupField__c` (e.g. `GTM_Link_Event__c.Saved_Configuration__c`). Staging deploys these layouts fine and the fields exist on the child objects in source.

  Desired behavior:
  1. Keep checking `<layoutItems><field>` (and any top-level `<fields>` outside `<relatedLists>`) against the layout's own object, unchanged.
  2. For each `<relatedLists>` block, parse `<relatedList>` as `Object.Lookup` (split on the first "."). Resolve each `<fields>` `__c` entry against that child object's field set (`objects[child]`), not the parent's. Message should name the child object (e.g. "related list 'GTM_Link_Event__c.Saved_Configuration__c' places 'GTM_Link_Event__c.Foo__c', which is not defined in source ...").
  3. `<relatedList>` values with no "." (RelatedNoteList, RelatedActivityList, RelatedHistoryList, RelatedCompetitorList, RelatedContactRoleList, RelatedLineItemList, RelatedOpportunityHistoryList, RelatedPartnerList; standard names) have no child object: skip field checks for that block. Standard-field tokens (NAME, CREATED_DATE, no `__c` suffix) continue to be ignored by the existing `endswith("__c")` filter.
  4. A field genuinely missing on the child must still be flagged as deploy-blocking (`P`). If the child object itself is not in source (`objects`) and is not standard, flag it (one finding) rather than silently passing; if standard, skip. Optional and low-priority: also verify the lookup part exists on the child (`objects[child]` contains it); Architect decides, but it must not create new findings on current main.
  5. The `customLink`/`customButtons` and standard-object-replacement checks in section 9 are untouched.

  No design fork or ambiguity; this touches no org and no `gtm-prod` data (static source check only).
- **System Component Impacted:** Python tooling only: `scripts/check-references.py` section 9. Also runs via `scripts/check-all.sh` and the `agent-ci-gate.yml` "findings new vs. main" comparison (no change needed there; a fix only removes findings, so it cannot fail that diff).
