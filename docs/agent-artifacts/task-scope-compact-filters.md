# TASK SCOPE — ISSUE #compact-filters

## 1. Requirements Breakdown

- **Target Objective:** Owner feedback: "the filters look great, but have you seen how Jira does their filtering? I think it should work like this so it doesn't take up so much real estate at the top." Replace the tall, multi-row filter bar with a compact Jira-style pattern: ONE short row (search + a few compact filter buttons, each opening a small popover with checkboxes; the chosen value/count shown inside the button; extra filters folded into "More"; one "Clear filters" link; optionally saved filters), giving the content below more room.
- **System Component Impacted:** LWC only (recommended path): `force-app/main/default/lwc/gtmFilterBar/` (html, js, css, `__tests__/gtmFilterBar.test.js`) plus contract doc `docs/architecture/gtm-filter-bar.md` (Architect updates first, Contract First). No Apex, no metadata, no permission sets, no Experience Cloud publish (internal Lightning app tabs).

### Options evaluated (Salesforce first: native before custom; custom justified)

**(a) Restyle `gtmFilterBar` in place into a compact single-row bar with popover filter pills. RECOMMENDED.**
- Composition of native pieces: a `lightning-input type="search"` for the search box (only if the consumer has something to search, see Q4); for each filter a trigger `<button class="slds-button slds-button_neutral" aria-haspopup="true" aria-expanded>` opening an SLDS **dropdown/popover** (blueprint markup) containing `lightning-checkbox-group` (multi; checkbox list) or a list of `role="menuitemradio"` items / `lightning-radio-group` (single), toggle via `lightning-input type="toggle"` or a simple pill button, date range via the existing preset `lightning-combobox` + `lightning-input type="date"` inside the popover. "More" = `lightning-button-menu`-style overflow (or the same popover pattern) holding the lower-priority filters. "Clear filters" = existing `lightning-button variant="base"`.
- **Why custom is justified:** no base component provides a multi-select filter popover. `lightning-button-menu` supports checkbox menu items (`lightning-menu-item` with `checked`) and closes on selection (usable for very short lists, weak for the unbounded offering list, no per-menu search, `lightning-menu-item` cannot hold inputs). `lightning-combobox` is single value only. `lightning-dual-listbox` is a heavy two-pane picker. So the popover shell is our SLDS-blueprint markup, but the CONTENTS stay base components.
- Files touched: `gtmFilterBar.html/js/css`, `__tests__/gtmFilterBar.test.js`, `docs/architecture/gtm-filter-bar.md` (new Addendum B). Consumers (`gtmRepLinkFinder`, `gtmReadoutsOverview`) unchanged if the public API stays; small consumer edits only if a "filter priority / More" hint is added to the config (an OPTIONAL, additive config field, e.g. `priority` or `pinned`, to be decided in Q3).
- Jest: rewrite/extend `gtmFilterBar.test.js` (popover open/close, Escape, outside click, aria attributes, in-button value/count text, one `filterchange` per user change, More overflow, Clear filters, pill row removal). `gtmFilterUrlState` tests unchanged. Consumer tests should pass untouched; that is itself a check on API stability. `npm test` (sfdx-lwc-jest).
- Apex: NONE. No `@AuraEnabled` change. (Any accidental Apex change would force a full test run on the production-type gtm-dev; call it out and stop.)
- Permission sets: none. No fields, objects or tabs.
- Accessibility (the main risk, since we hand-own popovers): trigger is a real `<button>` with `aria-haspopup`, `aria-expanded`, and an accessible name that includes the selection (e.g. "Status, 2 selected"); Enter/Space opens, focus moves into the popover, Tab stays inside or Escape closes and RETURNS FOCUS to the trigger, outside click closes, checkbox items are native/`lightning-checkbox-group` so Space toggles and screen readers announce checked state; the result count stays `aria-live="polite"`; selection is announced (count in button label changes). Avoid focus traps that block Tab out; no hover-only behaviour.
- URL state: contract UNCHANGED (config-driven, same events). Must still round-trip: state -> `values` -> in-button display -> user change -> `filterchange` -> `buildNavigateArgs` -> URL -> refresh restores. Only a new optional config field would need documenting first in `docs/architecture/gtm-filter-bar.md`.
- Responsive: fewer rows by construction. Narrow rule: search takes the full first row, pills wrap; popover must not overflow the viewport (max-width `calc(100vw - 1rem)`, right-align when near the right edge); at ~320px fold everything except the top-priority filter into "More". Prefer pure CSS wrap over a ResizeObserver; if a JS width switch is needed, copy the guarded pattern already in `gtmPagePreview` (create in `renderedCallback`, `typeof ResizeObserver === 'undefined'` early return, disconnect in `disconnectedCallback`). NOTE Addendum A.6 pointed at a `gtm-page-header-layout.md` Addendum A that is not on main; use `gtmPagePreview` as the reference.
- Overlap with #214 / wizard offset fix / other PRs: no shared files expected; both consumers are non-modal. If a popover renders inside a container with `overflow: hidden` (card body) it can clip; the Architect must check the host containers (`ov-filters` wrapper, Pages card header) and use absolutely-positioned SLDS dropdown with sufficient z-index. Popover-inside-modal is not a current case; #214's modal shell is not in play. Re-scan open PRs at branch time.

**(b) Native list-view filter panel / other native patterns. NOT RECOMMENDED.**
- The standard list-view filter panel (Filters flyout with "Add Filter", "Filter by Owner", Reset/Done) belongs to `lightning-list-view`/standard List View UI and works on a single sObject list view with its own saved List View metadata. `lightning-list-view` is not exposed as a base component for custom pages in the way needed here, cannot be fed our Apex-aggregated rows (both consumers are custom tabs over Apex aggregations, stage counts, derived readiness tier and readout state that are not fields on one object), and would not accept our URL param contract. Reports/report filters and `lightning-datatable` column filters likewise do not exist for arbitrary Apex row sets (base datatable has sort/resize/inline edit, no filter UI). This already agrees with the "standard list-view filters do not apply" line in section 1 of `gtm-filter-bar.md`. Files touched would be a full rebuild of both tabs' data path; unjustifiable.
- Adjacent native piece worth reusing: `lightning-button-menu` for "More" and `lightning-combobox` for single selects. Saved filters: the native equivalent (List View pins/saved views) needs an sObject-backed list view, so real saved filters would require a NEW persistence (custom object or user preference), see Q5. That would add fields and permission sets, and probably Apex, and is out of scope unless the owner says otherwise.

**(c) Leave as is. FALLBACK.**
- Zero risk and zero cost; but it ignores explicit owner feedback, and the Assessments bar (6 filters, unbounded offering chips, duplicated chips+pills) is the real space hog. A cheaper partial alternative within (c): collapse the pills row when chips already show state, or add a "Filters" disclosure toggle that hides the bar by default (still a change, but small). Mention to the owner as a minimum-viable variant.

### Recommendation

Do (a), scoped narrowly: one shared-component restyle (no Apex, no permission sets, no URL-contract change), with the Assessments bar as the priority (largest win) and the Pages single stage filter following automatically. Ship without saved filters (Q5) and without the search box unless a consumer supplies something to search (Q4). Foldable "More" driven by an additive optional config hint. Do the popover contents from base `lightning-*` components, hand-build only the SLDS popover shell and keyboard handling, and treat accessibility as an acceptance gate, not a follow-up.

### Risks

- Hand-built popover accessibility (focus, Escape, outside click, `aria-expanded`) is the biggest risk; base components do not give a ready multi-select popover.
- Popover clipping inside card/overflow containers and z-index versus datatable and page headers.
- Unbounded offering list needs an in-popover search or scroll (`max-height` + overflow); without it the popover is a new tall element.
- LWC synthetic vs native shadow: outside-click handling must use `composedPath`/focus checks that work in both.
- Losing the always-visible "everything at a glance" quality the owner said "looks great": in-button summaries hide options one click away. Mitigate with the active pill row only when needed, or drop it since state is in the button (Q6).
- Overlapping open PRs (#214 modal shell, #238/#239/#240): re-check for late edits to filter-bar files. Live QA on Pages and Assessments needs gtm-staging; if it is not provisioned, QA cannot sign off (gtm-dev not an allowed target).
- Contract creep: adding config hints must stay additive/optional so the GUS filter-key contract and consumers stay valid.
