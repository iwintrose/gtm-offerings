# TASK SCOPE — ISSUE #demo-seed-integrity-rebuild

## 1. Requirements Breakdown

- **Target Objective:** Rebuild `gtm-staging`'s demo/seed data (`[DEMO] ...` Accounts,
  Contacts, Opportunities, `GTM_Saved_Configuration__c` "engagement links",
  `GTM_Assessment_Request__c`, `GTM_Readout__c`, `GTM_Link_Event__c`, and any
  Task automation) so every record is produced by driving the SAME real Apex
  controller entry points the LWCs call, in the same sequence a human rep's
  clicks would invoke them, against Offerings/templates that are genuinely
  Published — not by inserting pre-formed rows directly, and not "tons of
  seeds" but a small, deliberately varied set. This is a straight
  restatement of the owner's 8 verbatim requirements; every clause below is
  backed by a live command run against `gtm-staging` tonight, not
  assumption.

  **Non-goal, added on revision — read before anything else below:** this
  issue does **not** author or publish any `migration-accelerator`
  Configurator-template `GTM_Page_Section__c`/`GTM_Page_Content__c` content.
  That work is already owned, designed (not yet built), and actively
  in-review under a separate, concurrently-scoped issue — see §7
  (Dependency) below. The first version of this scope doc (pre-revision)
  proposed building that content itself as "Phase A"; that has been
  **removed**, not deferred-and-forgotten, because building it here would
  duplicate/race a more considered redesign that isn't ready to build yet
  (a 9-chapter-to-6 restructure, PS-branded copy, and a reconciliation of
  Configurator's industry mechanism onto Story's, all still open questions
  pending owner review on that other issue). §1 item 7, §3, §5, and §6 below
  are revised accordingly; every other finding in this document is
  unchanged from the original audit.

  **Confirmed root cause (requirement 8 violation, live evidence).** The
  live `[DEMO] ...` data was loaded by
  `python3 scripts/seed-synthetic-data.py --load` from
  `data/seed/synthetic-demo.*.json` — `sf data import tree`-style raw
  record files, not Apex controller calls. Proof: every `synthetic-demo.*.json`
  record carries `"Description": "Synthetic demo account seeded by
  scripts/seed-synthetic-data.py (issue synthetic-seed-data). Safe to
  delete via --teardown."`, and that exact Description string is present on
  the live Accounts today (`sf data query`, confirmed on `[DEMO] Northwind
  Apparel Group` et al.). This explains every integrity violation found
  below — it is not a one-off mistake, it is what this specific loader
  mechanism inherently cannot produce correctly, because it never runs any
  Apex validation/derivation/side-effect logic.

  **1) Account/Contact must exist for every link/assessment.** Structurally
  true today — all 18 `GTM_Saved_Configuration__c` rows and all 12 demo
  `GTM_Assessment_Request__c` rows have non-null, resolvable `Account__c`/
  `Contact__c`. But **cross-object consistency is broken**: live query
  proof —
  `GTM_Assessment_Request__c` `AR-4362` (Name) has `Contact__c` = Chidi
  Okafor, but its own `Saved_Configuration__c` lookup (`SC-3831`) has
  `Contact__c` = Lucia Bianchi — a *different* contact at the same account.
  A real `submitRequest()` call can never produce this (the assessment's
  Contact is derived from the same link context it's submitted against).
  This is proof the assessment-request rows were inserted independently of
  their linked config, not generated by walking the real flow.

  **2) Seeded activity must be visible wherever a real one would be.**
  `GTM_Link_Event__c` (27 rows, "Page View"/"Form Opened"/"Form Submitted"/
  "Drop-off"/"Section Viewed") is the object the app actually calls
  "activity" — surfaced via `lwc/gtmLinkActivity`
  (`lightning/uiRelatedListApi.getRelatedListRecords` against
  `GTM_Saved_Configuration__c`'s related lists), and every row here does
  have a real `Saved_Configuration__c` lookup, so these ARE visible today
  where a real one would be. Standard Salesforce `Task`/`Event` activity is
  a *separate* concept (see #3) and there are currently **zero** Task or
  Event records anywhere in the org referencing any demo record (`sf data
  query ... FROM Task WHERE What.Name LIKE '%DEMO%' OR Who.Name LIKE
  '%DEMO%'` → 0 rows).

  **3) "If an activity is to trigger a task, that should all occur."**
  **Correction to this issue's own briefing:** a real, live, wired Task-firing
  mechanism already exists on `main` today — `GtmLifecycleNotificationService`
  (`fireTask`/`fireTasksBulk`/`closeOpenTasks`/`fireBell`), called from
  `GtmAssessmentRequestController.submitRequest` (fires `SUBJECT_NEW_REQUEST`
  on every new request), `GtmReadoutController` (approve/return-to-draft/
  publish edges) and `GtmReadoutApprovalHandler`. This is NOT the unmerged
  `agent/issue-31` mechanism (`GtmContextualTasksController`/
  `GtmEngagementStateClassifier`, still unpushed per `docs/backlog.md`'s
  "Open: issue #31" note) — it is separate, already on `main`, already
  tested. **But it is currently gated OFF for the assessment-request path**:
  `GtmNotificationSettingsController.getOrgDefaults()` returns
  `notifyOnNewAssessmentRequest = false` whenever no
  `GTM_Notification_Settings__c` custom-setting row exists — and none exists
  in `gtm-staging` today (`sf data query ... FROM
  GTM_Notification_Settings__c` → 0 rows). This is why zero Tasks exist for
  the 12 demo assessment requests even in principle — it is not solely
  because the seed bypassed Apex, it is ALSO because the org-wide switch this
  automation depends on has never been turned on. **Enabling
  `Notify_On_New_Assessment_Request__c = true` on the org-default
  `GTM_Notification_Settings__c` row is a genuine, legitimate admin
  configuration step and a precondition of this issue satisfying requirement
  3** — not a code change, not a special-case hack for seeding. Separately,
  the 8 demo `GTM_Readout__c` rows (`RDO-1865`..`RDO-1871`) already sit at
  `Approved`/`Published`/`Pending Approval` — states only reachable in real
  life via `GtmReadoutController.submitForApproval`/native approval/
  `publishReadout`, each of which also fires a Task/bell — with zero Tasks
  on record, proving these statuses were hand-set, not walked through.

  **4) Overview stage must match the Opportunity record everywhere.**
  Architecturally this is **already guaranteed correct by design** —
  `GtmHomeSnapshotController.getDeals()` selects
  `Opportunity__r.StageName` directly off the linked
  `GTM_Saved_Configuration__c.Opportunity__c` (no cached/duplicated stage
  value anywhere), and `gtmOverview.js`'s CRM-stage pill (`crmStage`/
  `crmStageClass`) reads that same live field — there is a *second*,
  unrelated "engagement funnel" pill (`dealStage()`, derived from
  `GTM_Link_Event__c` activity: "Request received"/"Opened the form"/etc.)
  that must not be confused with the Opportunity CRM stage. So there is no
  code-level drift risk for requirement 4; the only real risk is **the
  underlying data itself** — e.g. all 14 demo Opportunities currently have
  `Offering_Key__c = null` and `Engagement_Link__c = null` (never resolvable
  in the real flow, where `ensureOpportunity`/`resolveOpportunity` always
  stamp both), which is more evidence of the same root cause, not a
  requirement-4-specific defect.

  **5) No backend shortcuts — the real sequence must be followed.** This is
  the umbrella the above four items all fall under. Confirmed violated
  as detailed above.

  **6) Curated variation, not volume.** Current live counts: 8 Accounts, 15
  Contacts, 14 Opportunities, 18 `GTM_Saved_Configuration__c`, 12 demo +1
  non-demo `GTM_Assessment_Request__c`, 8 demo +1 non-demo `GTM_Readout__c`,
  27 `GTM_Link_Event__c`. Several accounts have 2-3 separate
  `GTM_Saved_Configuration__c` "snapshot" rows at different
  `Presentation_Stage__c` values pointing at the *same* Opportunity (e.g.
  `[DEMO] Brightfield Financial Partners`: `SC-3819` Sent, `SC-3826`
  In_Review, `SC-3829` Assessment, all on the same Opportunity) —
  this inflates the count without adding real variation (a real client has
  ONE link whose stage advances over time via `advanceStage`, not three
  static alternate-universe copies). The curated rebuild plan in §6 below
  proposes trimming this, now bounded further by the Configurator-content
  dependency (see item 7's revision).

  **7) Hard precondition — content must be genuinely Published first.**
  **Confirmed, and broader than the one gap flagged in this issue's
  briefing — audit finding unchanged by this revision, only the resolution
  below is revised.** Live query (`GTM_Page_Section__c` grouped by
  `Offering_Key__c`/`Template_Type__c`): `migration-accelerator` has 37
  `story` sections (36 Published + 1 Draft "test") and 1 `offerings-listing`
  row — **and zero rows of `Template_Type__c = 'configurator'`, for
  `migration-accelerator` or for ANY offering in the org.** The
  Configurator template's content is running 100% off the
  `gtmConfiguratorCopy.js` `CHAPTER_DEFAULTS` JS hardcode — confirmed in
  code, not just inference: `gtmConfigurator.js` line 504,
  `const base = CHAPTER_DEFAULTS[sectionKey] || {}`, is the only source ever
  reached because `getPageLayout` (the real Apex read) has nothing to
  return. Per requirement 7 this makes **any engagement link that renders
  the branded Configurator chapters invalid by definition** for now.

  **Revised resolution (this issue does not close this gap — see the
  non-goal above):** rather than seed nothing prospect-facing for
  `migration-accelerator` until the other issue ships, this revision found
  a real, already-supported, currently-reachable path that is **not**
  gated by the chapter-content gap at all —
  `GtmSavedConfigurationController.createRepDirectAssessment()`
  (`Presentation_Stage__c = 'Rep_Direct'`). Confirmed directly in its
  sibling method's doc comment
  (`generateRepDirectShareLink`, same class): "`gtmConfigurator`'s
  `Rep_Direct` branch... renders the questionnaire directly rather than any
  branded chapter content, since this record was never given one." A
  Rep_Direct record's URL is still `/configurator?cfgId=<id>`, but the page
  never renders `cover`/`partner`/`challenge`/etc. for it — it goes straight
  to the assessment questionnaire (a separate component,
  `gtmAssessmentQuestionnaire`, backed by the already-real, already-Published
  instrument metadata, not by `GTM_Page_Content__c`). This is confirmed to
  be the app's own currently-supported answer to "capture an assessment
  without a branded page" — its doc comment explicitly frames it as "the
  supported replacement for the accidental bare-URL 'direct booking' path...
  now closed," i.e. that legacy no-link path is deliberately no longer
  reachable, so `createRepDirectAssessment` → `submitRequest` is the one
  real, current path this issue can legitimately drive for
  `migration-accelerator` today. `GtmAssessmentRequestController
  .resolveConfigContext` (the method `submitRequest` uses to resolve
  Account/Contact/Offering/Opportunity from a link) reads no
  `Presentation_Stage__c` value at all, so it resolves a `Rep_Direct` config
  identically to any other stage — full Task-firing, Draft-readout
  generation, and Opportunity creation/linking all still fire for real.
  `GtmReadoutPublicController.getPublishedReadout` (the one method behind
  the published-readout overlay) also has zero dependency on
  `Template_Type__c='configurator'` content — confirmed by inspection, no
  `getPageLayout`/`CHAPTER_DEFAULTS` reference anywhere in that class or in
  `lwc/gtmReadoutView`. So Readout seeding (Draft/Pending Approval) is
  unaffected by this gap either.

  **What stays genuinely blocked, and is deferred rather than worked
  around:** `saveConfiguration()`-created links (`Presentation_Stage__c`
  `Draft`/`Sent`/`In_Review`/`Assessment`) and `advanceStage()` calls for
  `migration-accelerator` — visiting any of those links' `generatedUrl`
  does render the 9 branded chapters, currently 100% fallback copy. Seeding
  any of those stages for `migration-accelerator` right now would be
  exactly the "prospect/rep-facing seed record... valid for a given
  Offering" violation requirement 7 forbids. This narrows the demo's
  achievable `Presentation_Stage__c` variety to `Rep_Direct` only until the
  Configurator content ships — an honest trade-off, not hidden in §6 below.

  Separately and unaffected by the Configurator gap: the framework's
  Industry Chooser (`Offering_Key__c='gtm', Template_Type__c='industry-chooser'`)
  has only ONE industry genuinely Published — `industry-financial-services` —
  of the 8 industries the current demo Accounts span (Financial Services,
  Healthcare, Government, Biotechnology, Transportation, Retail, Media,
  Manufacturing). None of the 18 `GTM_Saved_Configuration__c` rows even
  populate `Industry__c` today (all null) despite `migration-accelerator`'s
  `story` template having real Published per-industry variant content for 9
  industry slugs (`financial-services`, `health`, `public-sector`,
  `transportation-mobility`, `retail`, `energy-commodities`,
  `consumer-products`, `telecommunications-media-technology`, plus the
  no-longer-relevant `test`). `Industry__c` on `GTM_Saved_Configuration__c`
  is a plain informational/reporting field with no Apex validation gating
  it (unlike the Configurator chapter content) — safe to stamp directly for
  realism even on a `Rep_Direct` record (`createRepDirectAssessment`'s
  `RepDirectInput` has no `industry` parameter at all, so this needs one
  small supplementary `update` after creation, the same class of
  housekeeping write already used for `Is_Synthetic__c`). See §6 for the
  revised curated plan.

  **8) Real Apex entry points, real sequence — already proven possible in
  this exact repo.** `scripts/data/reset-accelerator-demo.apex` (present
  since the initial import, untouched, never actually the source of the
  live `[DEMO]` data — see root cause above) already demonstrates the
  correct pattern: `GtmSavedConfigurationController.saveConfiguration()` and
  `GtmAssessmentRequestController.submitRequest()`, in sequence, for real,
  including `Database.DMLOptions.DuplicateRuleHeader.allowSave = true` on
  the one raw Account/Contact insert it does perform (before any link
  exists to resolve them through), and it deliberately leaves 1 of 4 demo
  clients with activity-but-no-submitted-assessment ("a real deal that has
  interaction events but no assessment request is a normal state the
  Overview needs to be able to show, not a bug to seed away" — its own
  comment, directly matching requirement 6's spirit). This script's naming
  convention (`(Demo)` suffix, `*.example` emails) is now out of step with
  the `[DEMO] ` prefix / `.invalid` email convention the newer
  `seed-synthetic-data.py` pipeline established and tags via
  `Is_Synthetic__c = true` (already present and `true` on all 18 live
  `GTM_Saved_Configuration__c` rows) — the rebuild should follow the newer
  naming/tagging convention. **Revised note:** this script calls
  `saveConfiguration()`, which (per item 7's revision above) this issue must
  NOT call for `migration-accelerator` right now — the rebuild reuses this
  script's *methodology* (real controller calls, in the real sequence,
  `dupOptions` for the one legitimate raw insert) but substitutes
  `createRepDirectAssessment()` wherever this script used
  `saveConfiguration()`, and does not call `GtmStageActionsController
  .advanceStage()` at all this round (that method stays fully in scope for
  a future issue once the Configurator content dependency clears).

  **Real operational side effects of using the real controllers (must be
  planned for, not treated as bugs):** `submitRequest()`'s own notify path
  (`GTM_Assessment_Config__mdt` `Default` record: `Send_Email__c = true`,
  `Notify_Email__c` null, so it falls back to the link's own
  `Notify_Email__c`, which defaults to the creating/running user) will send
  a real "new assessment request" email to whoever's user context runs the
  seed script — expected, not a defect, and lands in an internal inbox, not
  a fake prospect's. (The `GTM_Config_Send_To_Client` flow / proposal-email
  side effect from the original audit only fires on an `advanceStage(...,
  'Sent')` call, which this revision no longer makes for
  `migration-accelerator` — noted for completeness, not currently a live
  risk under this scope.)

- **System Component Impacted:** Apex (seed-authoring script(s) under
  `scripts/data/` calling existing controllers — no new/modified
  `@AuraEnabled` or `GtmAgentToolSurface` methods) and the existing
  `data/seed/` synthetic-demo tooling (`scripts/seed-synthetic-data.py`,
  its `data/seed/synthetic-demo.*.json` fixtures, and `Is_Synthetic__c`
  tagging/teardown). No LWC changes are anticipated. No schema/permission-set
  changes are anticipated (see §2). **No GTM Content Manager data
  (`GTM_Page_Section__c`/`GTM_Page_Content__c`) is authored by this issue at
  all** — see the non-goal above and §7 (Dependency).

## 3. Plan Acceptance Criteria

- **Success Metric — mechanically checkable, not "looks right":**
  1. **No orphaned FKs (requirement 1).** Zero
     `GTM_Saved_Configuration__c`/`GTM_Assessment_Request__c` rows tagged
     `Is_Synthetic__c = true` with a null `Account__c` or `Contact__c`. Zero
     rows where `GTM_Assessment_Request__c.Contact__c !=
     Saved_Configuration__c.Contact__c` for the linked config (the exact
     `AR-4362`/`SC-3831` class of bug found live tonight). Zero seeded
     Opportunities with `Offering_Key__c = null` when created through a
     `createRepDirectAssessment` config (`ensureOpportunity`/
     `resolveOpportunity` always stamp it).
  2. **Activity visible (requirement 2).** Every seeded
     `GTM_Link_Event__c` has a resolvable `Saved_Configuration__c` and is
     visible via the config record's related list
     (`lwc/gtmLinkActivity`) — spot-checked live in-browser by QA on at
     least 2 seeded links.
  3. **Real task automation fires (requirement 3).**
     `GTM_Notification_Settings__c` org-default row exists with
     `Notify_On_New_Assessment_Request__c = true` BEFORE any seeded
     `submitRequest()` call runs. After seeding, `SELECT COUNT() FROM Task
     WHERE Subject = 'New assessment request needs review' AND WhatId IN
     (<seeded Assessment Request Ids>)` equals the number of seeded
     assessment requests notification was enabled for. Any seeded
     `GTM_Readout__c` that reaches Approved/Published does so via
     `GtmReadoutController` calls (`submitForApproval` → native approve →
     `publishReadout`), each leaving the matching closed/fired Task behind
     per `GtmLifecycleNotificationService`'s Subject-key contract — spot
     checked by SOQL against `Task.Subject IN
     (GtmLifecycleNotificationService.SUBJECT_*)`.
  4. **Overview/Opportunity consistency (requirement 4).** For every seeded
     Opportunity, the `StageName` shown by `GtmHomeSnapshotController
     .getDeals()` (Overview "who's hot" widget) is queried live and diffed
     against `SELECT StageName FROM Opportunity WHERE Id = :id` — must be
     byte-identical (this is architecturally guaranteed by the single-source
     read already, so this is a regression check, not a fix).
  5. **Curated, not bulk (requirement 6), revised.** Total record counts
     land within the ranges in §6 below (one `GTM_Saved_Configuration__c`
     per seeded account, no redundant same-account/same-opportunity
     duplicates), spanning at least 4 distinct real Opportunity `StageName`
     values and at least 4 distinct industries drawn only from the 9
     industries with real Published Story variant content. **Every seeded
     `GTM_Saved_Configuration__c` for `migration-accelerator` has
     `Presentation_Stage__c = 'Rep_Direct'`** — this is the one honest
     limitation of this revision, not a gap to paper over; full
     Draft/Sent/In_Review/Assessment stage variety is explicitly deferred
     to the follow-up noted in §7.
  6. **No Configurator-content dependency introduced (new, this
     revision).** `SELECT COUNT() FROM GTM_Saved_Configuration__c WHERE
     Is_Synthetic__c = true AND Offering__c = 'migration-accelerator' AND
     Presentation_Stage__c != 'Rep_Direct'` returns 0 — mechanically proves
     this issue never created a link that would render the unpublished
     Configurator chapters to anyone. Code review confirms no call to
     `GtmSavedConfigurationController.saveConfiguration()` or
     `GtmStageActionsController.advanceStage()` for `migration-accelerator`
     anywhere in the rebuild script.
  7. **Provenance (requirement 8).** `git log`/code review confirms the
     rebuild script contains no direct `insert`/`Database.insert` of
     `Account`, `Contact` (except the one legitimate
     `Database.insert(acc/con, dupOptions)` pre-link-creation pattern
     `reset-accelerator-demo.apex` already establishes),
     `GTM_Saved_Configuration__c`, `GTM_Assessment_Request__c`, or
     `GTM_Readout__c` — every one of those objects' rows must trace to a
     call into `GtmSavedConfigurationController.createRepDirectAssessment`,
     `GtmAssessmentRequestController.submitRequest`, or
     `GtmReadoutController`'s lifecycle methods.
  8. **Old data provably wiped, not just added-to.** `python3
     scripts/seed-synthetic-data.py --teardown --dry-run -o gtm-staging`
     run before the rebuild shows the full 18/12/8/27-row-class set from
     tonight's audit (§1); after `--teardown` (real run) + rebuild, a
     repeat of every SOQL query in §1's evidence returns only the new,
     curated set — nothing from the old broken generation survives
     alongside it.

- **Target Test Target:** Apex —
  `GtmSavedConfigurationControllerTest.cls`,
  `GtmAssessmentRequestControllerTest.cls`,
  `GtmReadoutControllerTest.cls` (all pre-existing; must still pass —

`migration-accelerator` is `Rep_Direct`; variety comes from Account
industry, Opportunity `StageName`, and assessment outcome, not from
`Presentation_Stage__c` (deliberately narrowed, see §1 item 7 and §3 item
5):

  `financial-services`, `health`, `public-sector`,
  `transportation-mobility`, `retail` (5 concrete picks; `energy-commodities`/
  `consumer-products`/`telecommunications-media-technology` available as a
  6th/7th if more variety is wanted). Reuse the existing `[DEMO]` Account
  names/industries that map onto this set rather than inventing new ones
  (e.g. Brightfield Financial Partners→financial-services, Cascade Regional

  Logistics→transportation-mobility, Northwind Apparel Group→retail); drop
  Helix BioSciences/Solvent Materials Corp/Prime Stream Media unless
  `energy-commodities`/`consumer-products`/`telecom-media` variant content
  is confirmed Published too.

  least `Prospecting`, `Qualification`, `Needs Analysis`,

  range. (Advancing `StageName` after creation is a plain, native

  GTM Apex method for this because Opportunity stage management is
  standard Salesforce functionality, not app-specific business logic, so
  this is not a requirement-8 violation.)

  `createRepDirectAssessment` (`Presentation_Stage__c = 'Rep_Direct'` for
  all of them — see above), with `Industry__c` stamped to match the
