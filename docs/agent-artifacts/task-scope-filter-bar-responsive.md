# TASK SCOPE — ISSUE #filter-bar-responsive

## 1. Requirements Breakdown

- **Target Objective:** Owner report (live, no screenshot yet): "the filter buttons break when you resize the window small." Make the shared `gtmFilterBar` render with no horizontal overflow, clipped labels or squashed chips from 320px up, without changing its public API (`filters`, `values`, `resultCount`, `resultLabel`, `label`, `variant`; events `filterchange` `{key,value}` and `clear`) so the two consumers (Pages-tab stage filter in `gtmRepLinkFinder`, live on gtm-dev; Assessments-tab filter in `gtmReadoutsOverview`, merged #227, not yet deployed) need no change.
- **System Component Impacted:** LWC only: `force-app/main/default/lwc/gtmFilterBar/` (html, js, css, `__tests__/gtmFilterBar.test.js`) plus contract doc `docs/architecture/gtm-filter-bar.md` (Architect updates first, per Contract First). No Apex, metadata, permission sets or Experience Cloud publish (internal tabs).

### Findings from current code (verified by reading, not rendered)

1. `gtmFilterBar.html` renders every `type: 'chips'` filter as `lightning-checkbox-group type="button"` (multi) or `lightning-radio-group type="button"` (single). Both render an SLDS button group inside their shadow DOM. The wrapper (`.gtm-filter-bar__item`, root `slds-grid slds-wrap`) can wrap whole filters, but a single chip group is one unbreakable flex item whose inner group is `display:inline-flex`, nowrap. Inner `.slds-button-group` / `.slds-checkbox_button-group` / `.slds-radio_button-group` markup is inside synthetic/native shadow of the base component, so consumer CSS (`gtmFilterBar.css`) cannot reach it, and `lightning-*` base components expose no wrap attribute or styling hook. Option (a) (wrap via wrapper CSS) is therefore effectively UNREACHABLE. Cannot verify offline which shadow mode the org uses for the internal Lightning app, or the exact base-component markup version; the conclusion holds in both because the inner classes are not addressable from our stylesheet either way except via unsupported `::part`/pierce hacks.
2. Worst case is real: Pages stage filter = 7 radio chips with count-bearing labels via `_optionsWithCounts` (e.g. "Assessment submitted (12)", "Prospect engaged (4)", "Not opened yet (9)"), all in one nowrap group, roughly 900px+ wide. Assessments tab has status, tier (4), readout (5), offering (N, server-driven, unbounded) multi chip groups, each equally unbreakable.
3. Other pieces are probably fine but unproven: `lightning-combobox`, toggle, date inputs, preset combobox wrap as whole items; `.gtm-filter-bar__dates` is `slds-wrap` already; status row (`lightning-pill-container`, "Clear all", count) is `slds-wrap`, but `lightning-pill-container` with long pills (e.g. "Readout: Approved, not sent, Waiting on approval") may need its own wrap/`is-collapsible` check. Compact variant uses `label-hidden` and `slds-grid_align-spread`; a card-header host is narrow, so it is the likeliest to overflow.
4. `.gtm-filter-bar__count` colour `#747474` is the only hex in the CSS; keep it, add none (repo has no CSS custom properties; reuse the existing allowlist).
5. Reference point: `gtmPagePreview.js` (lines ~294-300) already uses a guarded `ResizeObserver` (`typeof ResizeObserver === 'undefined'` early return). The page-header Addendum A referenced in the task is NOT present in `docs/architecture/gtm-page-header-layout.md` on `main` (no "Addendum" heading; that work is not merged here), and `gtmPageHeader` has no ResizeObserver on main. Architect should copy the `gtmPagePreview` pattern (create in `renderedCallback`, disconnect in `disconnectedCallback`, stub-safe), not depend on unmerged work.
6. Not verified: the actual broken visual. An offline reading strongly predicts the chip-group overflow above, but a screenshot at the reported width would confirm which element breaks (chips vs pills vs date row vs compact). **Request to coordinator: please supply a screenshot of the broken state (Pages tab, and window width) if available; otherwise the harness below stands in.**

### Options evaluated

- (a) Wrap the base group via wrapper CSS: unreachable (see finding 1). Rejected.
- (b) Render chips as individual `lightning-button` (variant `brand` when selected else `neutral`, `aria-pressed`) inside our own `slds-grid slds-wrap` container with `role="radiogroup"`/`role="group"` and label. Fully native controls, wraps naturally, counts stay in the label, cheap. Cost: we own arrow-key/roving-tabindex behaviour for radio semantics (base radio-group gives it free). Mitigation: single-select modeled as `role="group"` + `aria-pressed` toggle buttons (each Tab-reachable, Space/Enter toggles) rather than a fake radiogroup; this is a valid, simpler pattern and avoids hand-built arrow-key logic.
- (c) Below a container width switch chip groups to `lightning-combobox` (single) or a multi-select equivalent. Problem: `lightning-combobox` is single-value only; multi chips (status/tier/readout/offering) have no native multi-select combobox in base components (`lightning-dual-listbox` is too heavy; a custom multi-select is out of standing-rule scope). Counts and current selection are less visible in a collapsed dropdown.

### Recommendation (Architect to confirm)

**(b) at all widths, no width-switch needed for multi chips; (c) only for the single-select chip group, and only if (b) still fails the 320px check.** Rationale: (b) removes the root cause everywhere, keeps counts/selection visible, no new dependency, and makes ResizeObserver unnecessary for the common case. Wrapped chips at 320px for 7 stage options is ~5-7 rows, tall but not broken; a single-select `lightning-combobox` (with counts in labels) below ~600px bar width for `isChipsSingle` filters is a clean, native compression if the owner finds 7 stacked rows too tall. That switch is the only place the ResizeObserver is needed. The Assessments multi chip groups stay as wrapped buttons at all widths (no native multi combobox).

### Open forks for the Architect (need a decision, not guessed here)

1. Single-select chips: keep `role="radiogroup"` semantics (needs roving tabindex + arrow keys, hand-built) vs `role="group"` + `aria-pressed` (recommended). Also: does a click on the already-selected single chip clear it? Today `lightning-radio-group` cannot deselect; deselecting is via pill/"Clear all". Preserve parity: clicking the selected chip is a no-op (or emits same value), do not add deselect.
2. Whether to include the ~600px single-chip to combobox collapse now, or ship (b) first and add it only if the live check shows 7 rows is too tall. Recommend ship (b) first as the fast fix; add (c-single) in the same PR only if the harness at 320px looks unacceptable.
3. Selected style: `lightning-button` `variant="brand"` vs `neutral` with `slds-is-selected` styling. Base `lightning-button` does not expose `aria-pressed` as an attribute on all API versions; verify in the Salesforce docs/Component Library (cannot confirm offline). If not exposed, fall back to native `<button class="slds-button slds-button_neutral">` with `aria-pressed` (SLDS blueprint markup, still Salesforce-native) using only existing SLDS classes.
4. Compact variant (card header): confirm hiding group labels visually (`label-hidden`) still gives each button group an accessible name via `aria-label` on the wrapper.
5. Pills: confirm `lightning-pill-container` wraps at 320px; if not, fall back to per-pill `lightning-pill` in an `slds-wrap` container (same `itemremove` mapping).
