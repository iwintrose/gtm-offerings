# TASK SCOPE — ISSUE #gus-provider-settings-field-type-fix

**PRIORITY: HIGH — this blocks ALL pending/future deploys to `gtm-dev`.** `main` currently cannot be cleanly deployed at all: a real `sf project deploy start --dry-run --target-org gtm-dev` run against the current `main` (as merged via PR #215) returns 20 "Invalid data type" component failures. Any other agent's work (Developer, QA) that requires a deploy to `gtm-dev` is blocked until this lands.

## 1. Requirements Breakdown

- **Target Objective:** Fix a live, confirmed deployability regression introduced by the already-merged `gus-provider-settings` PR (#215). That PR added two new fields to `GTM_Agent_Settings__c` — `Chat_Provider__c` (declared `Picklist`) and `OpenAI_API_Key__c` (declared `EncryptedText`). `GTM_Agent_Settings__c` is a **Hierarchy Custom Setting** (confirmed via `force-app/main/default/objects/GTM_Agent_Settings__c/GTM_Agent_Settings__c.object-meta.xml`: `<customSettingsType>Hierarchy</customSettingsType>`). Salesforce Custom Settings do not support `Picklist` or `EncryptedText` as field types on their fields — this was verified live via `sf project deploy start --dry-run` against `gtm-dev`, which returned the 20 "Invalid data type" failures. Both fields must be converted to plain `Text`, matching the existing precedent already established on the same object by `Claude_API_Key__c` (`Text`, length 255) and `Claude_Model__c` (`Text`). The picklist-style value constraint on `Chat_Provider__c` (only `"Anthropic"` or `"OpenAI"` allowed) must be re-implemented as an explicit Apex-level allow-list check, since the database will no longer enforce it once the field is plain Text.
- **System Component Impacted:** Apex (`force-app/main/default/classes/GtmAgentSettingsController.cls`, `force-app/main/default/classes/GtmAgentProxyController.cls`, and their test classes `GtmAgentSettingsControllerTest.cls` / `GtmAgentProxyControllerTest.cls`) and Salesforce metadata (`force-app/main/default/objects/GTM_Agent_Settings__c/fields/Chat_Provider__c.field-meta.xml` and `force-app/main/default/objects/GTM_Agent_Settings__c/fields/OpenAI_API_Key__c.field-meta.xml`). No LWC, Experience Cloud, or `instrument/` YAML changes are in scope.

### Confirmed current state (read directly from repo, not assumed from the original PR spec)

- `Chat_Provider__c.field-meta.xml`: currently `<type>Picklist</type>` with a `<restricted>true</restricted>` `<valueSet>` containing `Anthropic` (default) and `OpenAI`.
- `OpenAI_API_Key__c.field-meta.xml`: currently `<type>EncryptedText</type>`, `<length>175</length>`, `<maskChar>asterisk</maskChar>`, `<maskType>all</maskType>`.
- `Claude_API_Key__c.field-meta.xml` (the established working precedent on this same object, pre-dating this bug): plain `<type>Text</type>`, `<length>255</length>`. No masking attributes — masking is handled entirely at the Apex layer (see below), not at the field-type layer.
- `GtmAgentSettingsController.cls` (`with sharing`, admin-only access):
  - `getAgentSettings()` (cacheable, `@AuraEnabled`) returns an `AgentSettingsDto` with `hasApiKey`, `model`, `chatProvider`, `hasOpenAiApiKey`, `openAiModel` — it never returns `Claude_API_Key__c` or `OpenAI_API_Key__c` raw values, only booleans (`hasApiKey` / `hasOpenAiApiKey`) derived via `String.isNotBlank(...)`. This write-only/never-prefill pattern is explicitly documented in the class-level ApexDoc comment (lines 15–24) as intentional and, per that same comment, already understood to be independent of `EncryptedText` vs `Text`: "EncryptedText's masking is a UI-layer restriction (list views, layouts, reports) -- Apex can read the raw value via SOQL/field access same as any Text field, so the write-only/never-prefill boundary here is still the only thing protecting it, exactly as it always has been for Claude_API_Key__c." **This confirms requirement #3 below is already true in the existing code and comment — changing `OpenAI_API_Key__c` to Text does not weaken this protection, and the class-level comment should be lightly updated (the "despite it being EncryptedText" framing) once the field is Text, so it doesn't read as stale/contradictory.**
  - `setAgentSettings(String apiKey, String model, String chatProvider, String openAiApiKey, String openAiModel)` (`@AuraEnabled`, not cacheable) currently does **no validation at all** on `chatProvider` beyond blank-defaulting to `'Anthropic'` (line 73: `settings.Chat_Provider__c = String.isBlank(chatProvider) ? 'Anthropic' : chatProvider;`). Any non-blank string is written as-is today; the Picklist field type was the only thing preventing garbage values from persisting. This is the exact method that needs the new allow-list check added.
- `GtmAgentProxyController.cls` reads `Chat_Provider__c` as a plain string at line 620 (`String p = s?.Chat_Provider__c;`) and `OpenAI_API_Key__c` as a plain string at line 627 (`return s?.OpenAI_API_Key__c;`) — both are simple string reads/compares with no dependency on Picklist or EncryptedText-specific platform behavior, so no code changes are expected here; this file only needs to be re-confirmed working (via the existing Apex test suite and a live dry-run) after the field-type change, not edited.
- Test coverage check: neither `GtmAgentSettingsControllerTest.cls` nor `GtmAgentProxyControllerTest.cls` currently contains any assertion that depends on the platform silently rejecting an invalid `Chat_Provider__c` value (no test passes a value other than `'Anthropic'`, `'OpenAI'`, blank, or `null`). This means there is **no existing test to "move"** — the new Apex-level allow-list validation needs a **new** test case added (not a modified one), asserting that `setAgentSettings(...)` throws (e.g. `AuraHandledException`) when given an invalid `chatProvider` value such as `'Gemini'` or `'anthropic'` (case variants — decide and document expected case-sensitivity behavior explicitly in the implementation).

### No ambiguity / design fork flagged

This is a mechanical, well-scoped bug fix with a clear precedent already established in the same object (`Claude_API_Key__c`, `Text`). There is no conflicting requirement and no human design decision left open, other than the Developer needing to pick exact wording/case-sensitivity for the new Apex allow-list error message, which is an implementation detail, not a scope ambiguity. This issue does **not** touch `gtm-dev` production *data* — it only touches deployable metadata/Apex, though the acceptance criteria below does require a live `--dry-run` validation call against `gtm-dev` (non-destructive; dry-run only, not an actual deploy) to confirm the fix.

**Explicit decision reversal to document (not a regression):** The original `gus-provider-settings` Architect step chose `EncryptedText` for `OpenAI_API_Key__c` as "free hardening" over plain `Text`. That decision is being reversed here **not** because it was a bad idea in isolation, but because it was made without knowing `GTM_Agent_Settings__c` is a Hierarchy Custom Setting, and Custom Settings do not support `EncryptedText` at all — the platform itself makes the field type illegal, independent of any security tradeoff. The actual protection for both API key fields has always been, and remains, the Apex-level write-only/never-prefill boundary in `GtmAgentSettingsController`, not the field type. Any code comment referencing the old `EncryptedText` rationale (see class-level ApexDoc above) should be updated to reflect this, so a future reader does not mistake the `Text` field type for an accidental regression.
