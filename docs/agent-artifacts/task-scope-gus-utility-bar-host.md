# TASK SCOPE — ISSUE #gus-utility-bar-host

## 1. Requirements Breakdown

- **Target Objective:** Owner requirement (stated twice): GUS, the app's AI chat, must be reachable from the bottom of EVERY page of the app, as the overlying chat interface for the whole platform. Standing rule is Salesforce-native first, so the host is the Lightning App **Utility Bar**: a utility item hosting an LWC (target `lightning__UtilityBar`) configured on a UtilityBar flexipage attached to the app. Utility panels persist while the rep navigates between tabs. This issue delivers ONLY the host plus a general "app" chat surface with zero tools. Tools (stage filter, etc.) come later in follow-up issues that depend on this one. Internal reps only; Experience Cloud (prospect-facing) is OUT of scope.
- **System Component Impacted:** LWC (new host `gtmGusUtility`, refactor of `gtmAgentChat`/`gtmAgentBubble`), Apex (`GtmAgentProxyController` new `chatOnApp` entry plus a new `AppSurface` implementing `GtmAgentToolSurface`), Metadata (new UtilityBar flexipage, Application updates, permission-set checks). No YAML instrument impact.

### Current state (verified in code, not from specs)

- `c-gtm-agent-bubble` is mounted only in `force-app/main/default/lwc/gtmConfigurator/gtmConfigurator.html` (about lines 488-495 docked preview for the editor, 510-519 live floating mount for reps). Its `js-meta.xml` has `isExposed=false`. Neither `gtmAgentBubble` nor `gtmAgentChat` meta exposes any target.
- `gtmAgentBubble` couples three things: the FAB/panel chrome (`ab-fab`, `ab-panel`, mascot), a `lightning/empApi` subscription to `/event/GTM_Config_Update__e` filtered by `sessionToken` (skipped when `docked`), and props `sessionToken/configId` passed to the chat. It re-emits `agentdelta` upward.
- `gtmAgentChat` has `mode` ('config' default | 'readout') and `_send()` picks `chat({sessionToken, configId, userMessage, historyJson})` or `chatOnReadout({readoutId, workingDraft, userMessage, historyJson})`. Error handling already catches rejections and renders `err.body.message` as an assistant bubble, so an AuraHandledException is shown inline and does not throw to the page. State (`messages`, `historyJson`) lives in the component instance. The delta event contract (`agentdelta` with `detail.changes`) is unchanged and must stay so.
- Tests: `lwc/gtmAgentChat/__tests__/gtmAgentChat.test.js` exists (config send, delta, readout mode, error fallbacks, greeting, readOnly). **There is NO Jest spec for `gtmAgentBubble`** (no `__tests__` dir). Apex: `GtmAgentProxyControllerTest`, `GtmAgentProxyControllerReadoutTest`.
- Apex: `GtmAgentProxyController` is `without sharing`, has `@AuraEnabled chat(...)` (uses private inner `ConfigSurface`) and `chatOnReadout(...)` (asserts readability, then uses `GtmReadoutAgentSurface`, `with sharing`). One shared `runLoop(surface, userMessage, historyJson)`; provider dispatch (Anthropic/OpenAI/Gemini; 'Agentforce' resolves statelessly to a keyed provider) happens inside the loop, so any new surface is automatically provider-agnostic. `GtmAgentToolSurface` contract: `systemPrompt(toneClause)`, `toolDefinitions()`, `maxTokens()`, `executeTool(...)` (never throw, no DML, no callout).
- Apps: `applications/GTM_Offerings.app-meta.xml` (`navType` Standard, `uiType` Lightning, `formFactors` Large, no `utilityBar` element) and `applications/GTM_Content_Manager.app-meta.xml` (same, no utility bar). `flexipages/` currently holds only three record/page flexipages (`GTM_Assessment_Request_Record_Page`, `GTM_Readouts_Overview`, `GTM_Saved_Configuration_Record_Page`). No UtilityBar flexipage exists.
- Permissions: `GtmAgentProxyController` classAccess is granted in `GTM_Offering_User` and `GTM_Offering_Admin` ONLY. `GTM_Content_Manager` has no agent classAccess. `GtmAgentSettingsController` and the `GTM_Agent_Settings__c` API-key fields are Admin-only. `GTM_Agent_Settings__c` is a hierarchy/org-default custom setting read server-side via `getOrgDefaults()`; the LWC never sees keys.

### Requirements and design decisions

**R1. Host LWC and reuse strategy.**
- Create `gtmGusUtility` (`isExposed=true`, `<target>lightning__UtilityBar</target>`, `masterLabel` "GUS", `description`). It is a THIN host: a full-height panel containing `c-gtm-agent-chat mode="app"`, header with mascot/name/role. No FAB (the utility bar item IS the launcher).
- Recommended: do NOT fork the chat. Extend `gtmAgentChat` with a third mode `'app'` whose `_send()` calls a new `chatOnApp`. Extract only the panel chrome (header with mascot, status line) if the Architect wants the bubble and host to share it; otherwise the host renders its own small header and reuses `gtmAgentChat` for the body. The bubble and the FAB stay as is. Nothing in `gtmConfigurator` changes; its mounts, the `GTM_Config_Update__e` subscription, `chat()` and `chatOnReadout()` are untouched. The empApi subscription stays in the bubble and is NOT added to the host (app mode has no config session or deltas at zero tools).
- The chat's existing `agentdelta` event stays the single mechanism for surface-to-page effects. The host must listen for `agentdelta` and, initially, ignore it (no consumer). Follow-up issues define the consumer (see recommendations).
- Open fork F1 (Architect): mode-in-one-component (recommended, minimal code) versus a new sibling component. Recommendation is mode-in-one-component. The host passes `mode="app"` and `page-context` (below).

**R2. Page context and the `chatOnApp` surface.**
- Host learns where the user is via `@wire(CurrentPageReference)` from `lightning/navigation` (gives `type`, `attributes.apiName` for tabs, `attributes.recordId`/`objectApiName` for record pages, and `state`). The host serialises a small, allow-listed context object: `{ appName?, pageType, tabApiName?, objectApiName?, recordId? }`. Do NOT send raw `state` (may hold free-text filters). Utility-bar-specific APIs (`lightning/platformUtilityBarApi`: `getInfo`/`onUtilityClick`) are optional and only needed to detect open/closed; verify availability in the sfdx-lwc-jest stubs before depending on them (Open fork F2). Also verify that `CurrentPageReference` emits inside a utility item in the target org's API version (62.0); if it does not, fall back to `lightning/platformWorkspaceApi` (`getFocusedTabInfo`) which is supported in console apps only, so this may not work in standard nav apps. QA must confirm live in the browser on navigation between tabs. Context is re-read on every send (not cached at connect) because the panel stays mounted across navigation.
- New `@AuraEnabled public static String chatOnApp(String pageContextJson, String userMessage, String historyJson)` on `GtmAgentProxyController`. It: (a) parses the context defensively (blank/invalid JSON becomes empty context, never throws); (b) builds a new private inner `AppSurface implements GtmAgentToolSurface`; (c) returns `runLoop(new AppSurface(ctx), userMessage, historyJson)`. It does no record access assertion at zero tools because it reads no record. When later tools read records they must be `with sharing`-style surfaces (per the interface doc and the `GtmReadoutAgentSurface` precedent), which suggests moving `AppSurface` to its own `with sharing` top-level class `GtmAppAgentSurface` from the start so follow-up tools inherit sharing. Recommended: do it as top-level `GtmAppAgentSurface` (fork F3).
- `AppSurface` minimum: `toolDefinitions()` returns an empty list (verify the three provider adapters, `callClaude`/`callOpenAi`/`callGemini` and the `openAiToolsFromToolDefinitions`/`geminiToolsFromToolDefinitions` helpers, omit the `tools` key when the list is empty, since an empty tools array is rejected by some providers. This is a REQUIRED check and probable code fix in the loop or adapters); `executeTool` returns `{"error":"no tools available"}` and never throws; `maxTokens()` returns 1024 or similar. `systemPrompt(toneClause)` minimum: you are GUS, the Go-To-Market Utility Sidekick for the Publicis Sapient GTM Offerings Salesforce app, used by internal reps; you answer questions about how to use the app and the user's current page (given as context); you currently have no tools and must not claim to have taken, or be able to take, any action or read any data; if asked to do something you cannot, say so plainly and suggest the manual path; be concise; then append `toneClause`. Provider-agnostic because it goes through the unchanged interface and `runLoop`.
- Zero DML, zero callout in the surface (AGENTS.md §1 zero-DML rule stays in force).

**R3. Metadata.**
- New flexipage `force-app/main/default/flexipages/GTM_Offerings_UtilityBar.flexipage-meta.xml` (`type` UtilityBar, `template` `one:utilityBarTemplateDesktop`, `flexiPageRegions` name `utilityItems`) containing one `componentInstance` for `c:gtmGusUtility` with properties `icon` (recommend `einstein` or `chat`; owner-fixed label is "GUS"), `label` "GUS", `panelBodyHeight` ~560, `panelWidth` ~420, `startAutomatically` false (default closed), `textColor`/none. Optionally also add a standard Utility `History`/`RecentItems` item: NO, keep only GUS.
- Register in `applications/GTM_Offerings.app-meta.xml` with `<utilityBar>GTM_Offerings_UtilityBar</utilityBar>` (element order matters for the metadata XSD; Architect to place correctly and validate with a check-only deploy).
- **GTM Content Manager app: recommend NOT adding it in this issue.** `GTM_Content_Manager` permission set grants no `GtmAgentProxyController` access, and content editors were not named as GUS users (GTM_Offering_User/Admin only; CLAUDE.md §1 personas put GUS with BD/Sales reps). Adding it would show a utility that errors for editors. Open fork F4 for the owner: if "every page of the app" is meant to include the Content Manager app, add the same flexipage (or a second one) to that app AND grant `GtmAgentProxyController` in `GTM_Content_Manager`/`GTM_Content_Admin` (and consider that the chat then exposes the same org-wide API key to editors). This is a human decision, not to be guessed. Default in this scope: GTM Offerings app only.
- Permission sets: LWC bundles and flexipage access have no permission-set grant. `GtmAgentProxyController` is already granted in `GTM_Offering_User` and `GTM_Offering_Admin`, so `chatOnApp` needs no new grant. If `GtmAppAgentSurface` is a separate class it is only called from within the controller (no `@AuraEnabled`) and needs no classAccess, matching how `GtmReadoutAgentSurface` is handled (Developer to confirm `GtmReadoutAgentSurface` is absent from the permsets and mirror that). No new fields or objects.
- The ChatterNetworkPicasso Experience Cloud site is untouched. `gtmGusUtility` must expose ONLY `lightning__UtilityBar` (no `lightningCommunity__*`, no `lightning__AppPage`).

**R4. Audience, secrets, no-provider behaviour.**
- Audience: users with `GTM_Offering_User` / `GTM_Offering_Admin` (they can invoke the Apex). Users lacking class access who see the utility (e.g. someone with app access but without the permset) get the Apex "insufficient access" error, rendered as an inline assistant bubble by the existing catch; the host should also show a friendly message rather than a stack.
- Secrets: provider, model and API keys remain in `GTM_Agent_Settings__c` (Admin-only fields, Settings tab per `docs/architecture/gus-chat-provider-settings.md`). The host and chat send no key and receive none; `chatOnApp` returns only `{text, historyJson, changes}`. Do not add any key/provider LWC prop.
- No provider/key configured: `runLoop` throws `AuraHandledException` with "Claude/OpenAI/Gemini API key not configured. Go to Setup → Custom Settings → GTM Agent Settings → Manage..." The chat renders it as an inline message, so nothing throws to the page. Issue: that text is written for admins and points to Setup > Custom Settings, which is stale now that a Settings tab exists (`gtmOfferingsSettings`). Recommended: keep the existing config/readout behaviour unchanged (existing tests assert on it) but make the utility path friendlier: the host shows a note for non-admins "GUS is not set up yet. Ask an admin to add an API key in GTM Offerings Settings." Simplest low-risk implementation: `chatOnApp` catches the key-not-configured condition (pre-check via the same `getApiKey`) and returns a normal JSON reply with that text instead of throwing, without touching `runLoop`. Open fork F5: whether to instead reword the shared runLoop message for all surfaces (touches existing tests).

**R5. Deployment (source vs manual).**
- Deploys via source: `gtmGusUtility` bundle, the UtilityBar flexipage, the two modified Apex classes and tests, the changed `GTM_Offerings.app-meta.xml` (with `utilityBar` reference), and the `gtmAgentChat` changes. `scripts/deploy.sh` pass 1 handles all of these (flexipage and app are core metadata; no custom metadata records are involved).
- Manual/org-side: (1) app utility bar changes deploy with the app metadata but reps may need a hard refresh/re-open of the app; (2) confirm in the live org that the `GTM Offerings` app shows the "GUS" utility item at the bottom bar (Setup > App Manager > GTM Offerings > Utility Items shows it); (3) if a user has a personalised/other version of the app, nothing further; (4) admins must have saved an API key in the Settings tab (an existing manual prerequisite, not new). No Experience Cloud publish step is needed (Experience Cloud untouched, so the CLAUDE.md §5 `sf community publish` note does not apply). If the app-meta `utilityBar` deploy does not take effect when the app already exists in the org with a customised utility bar, the fallback is assigning the flexipage in App Manager by hand: the Architect must validate this with a check-only deploy and record whichever occurs.
- Constraints for Developer/QA: NO real deploy and NO Apex execution against `gtm-dev` (treated as production) except a validate-only `sf project deploy start --dry-run` WITH `--test-level RunSpecifiedTests` and the specified tests (it runs tests, then rolls back). Do not use `-c` (means `--ignore-conflicts`). Avoid Apex reserved words as identifiers (e.g. do not name variables `system`, `date`, `limit`, `object`, `transaction`, `final`, `new`, `class`). Never commit the Org ID.

**R6. Utility panel lifecycle and state.**
- A utility item's component stays mounted (kept alive) while the panel is collapsed and during tab navigation, so `messages`/`historyJson` persist across navigation and collapse, which is desired. Consequences: (a) `connectedCallback` runs once, so page context must be read reactively/at send time, not once; (b) the history grows without bound in a long session (already capped by `MAX_TOOL_ROUNDS` per turn but not history length): recommend a client-side history-length cap or "New chat" reset button in the host header (small, in scope; default cap suggestion: last 20 turns; Architect to confirm); (c) a full browser refresh clears state (acceptable, no persistence in this issue); (d) the host must not subscribe to `GTM_Config_Update__e`; (e) `scrollToBottom` uses `lwc:ref` on a possibly hidden panel, verify no error when collapsed.

## 5. Recommendations for follow-up issues (build on this host)

- Sequence: `gus-utility-bar-host` (this) first; then `gus-stage-filter-tool`; then the owner's larger list (create assessment / create link, analytics queries, per-offering/account/contact/link/assessment stage queries).
- Extension pattern: every new capability is (1) a tool definition plus `executeTool` branch in `GtmAppAgentSurface` (reads via `with sharing`, never DML in the loop, per the `GtmAgentToolSurface` contract) and (2) where the tool must change what the rep sees or writes, a returned delta in `changes` (e.g. `{ stageFilter: 'X' }`), never a server write.
- Page effects (stage filter, "go to page"): the host, which already receives `agentdelta`, translates a delta into either a NavigationMixin navigation (with state) or a Lightning Message Service message published on a new message channel that page LWCs (e.g. the shared filter bar from #224, `gtm-filter-bar.md`) subscribe to. Recommend LMS (Salesforce-native, works across a utility item and tabbed page LWCs), defined in the stage-filter issue, not here. LMS channel is a metadata addition, needs to be added to the contract docs before build (CLAUDE.md §4 Contract First).
- Writes (create assessment/link): follow the readout precedent: the model proposes, the rep confirms in the UI, and the LWC calls the existing controller method that does the DML with its own state checks, keeping DML out of the callout transaction.
- Read queries (analytics/stage by entity): read-only tools with strict parameter allow-lists, sharing-aware, row-capped, returning summaries to keep tokens low; page context from this issue tells the tool which record is in scope without giving the model an Id parameter (same blast-radius argument as `chatOnReadout`).
- Per-tool permission checks, and raising `MAX_TOKENS`/rounds, belong to those issues.
