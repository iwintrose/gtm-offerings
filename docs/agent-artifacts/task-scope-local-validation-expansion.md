# TASK SCOPE — ISSUE #local-validation-expansion

## 1. Requirements Breakdown

- **Target Objective:** Reduce real Salesforce deploy attempts against `gtm-dev` (which is production, and shares a hard daily API request quota with all other org traffic) by catching more deploy-blocking metadata mistakes locally, with zero org connection, before a deploy is ever attempted. This session hit the quota partly because of deploy failures that a static check on `force-app/main/default/` XML could have caught in advance (missing permission-set FLS grants per CLAUDE.md §6, and a picklist-literal mismatch a QA agent used as a deliberate negative control). Expand the existing local, org-free static-check tooling (`scripts/check-references.py`, which already runs a "deployability audit" over the whole tree with no `sf` CLI and no org involved, per its own module docstring) to add four specific new checks, confirmed against real files in this repo as genuinely static/deterministic and implementable without executing or compiling anything:
  1. Permission-set FLS completeness for new/changed custom fields.
  2. Required-field / MasterDetail `fieldPermissions` exclusion (the exact "You cannot deploy to a required field" failure CLAUDE.md §6 documents).
  3. Picklist-literal validity in Apex test files and seed-data JSON against each field's `<valueSet>`.
  4. A gap-check on `check-references.py`'s existing dangling-reference coverage, specifically for LWC `@wire`/imperative Apex call parameter shapes vs. the called Apex method's actual signature — to be scoped further by the Architect only if a genuine gap is confirmed (see §1 note below).
- **System Component Impacted:** Local tooling only (`scripts/check-references.py` and/or a new sibling script under `scripts/`), plus any doc updates to `AGENTS.md` §2 / `CLAUDE.md` §5 recording the check as part of the standard pre-deploy sequence. **No Salesforce metadata, Apex, LWC, or YAML instrument content is touched by this issue** — it is a developer-tooling/process change, not a GTM feature.
- **Note on item 4 (ambiguity flag):** I confirmed `check-references.py` already resolves dangling references across Apex, LWC, FlexiPages, Custom Tabs, permission sets, Experience Cloud views, and seed data (its docstring and `main()`/`refs_to()` logic cover "every grant, record, page, route, layout and seed row in this tree"). Whether it *already* validates LWC `@wire`/imperative Apex parameter shapes against the target Apex method's actual signature, or only that the *method exists*, is not fully resolved by my read-only pass — this is a genuine judgment call for the Architect to confirm by tracing the Apex-reference logic (`apex_blank`, `fields_of`, and the JS-reference block starting near `js_blank`) against 2-3 real `@wire`/`import { x } from '@salesforce/apex/...'` call sites before deciding whether item 4 is in-scope work or a no-op. Do not assume a gap exists without that trace — a check added against a false gap risks false positives on legitimate calls, which per the requirements is worse than doing nothing.

## 2. Code Dependency Checklist

- [ ] Modifying GUS Tool Surface? **NO** — this issue touches only local dev-tooling scripts (`scripts/`), never Apex/LWC that ships to the org.
- [ ] Altering Custom Metadata? **NO** — no `migration-accelerator/` YAML or `force-app/main/default/customMetadata/GTM_Assessment_*` XML is created, read-generated, or modified by this issue. `build-instrument.py` is referenced only as prior art to understand its `--check` flag pattern, not modified.
- [ ] Introducing database fields? **NO** — no new object/field/permission-set grants are introduced by this issue itself. (The new *checks* validate other issues' field/permission-set changes; this issue does not add any of its own.)

## 3. Plan Acceptance Criteria

- **Success Metric:** All of the following, run with no `sf` CLI and no org authentication, must pass on a clean checkout of `main` and correctly flag injected negative-control cases without producing any false positive against the current, currently-passing repo state:
  1. A new/changed custom field on a GTM-owned object lacking the FLS grant CLAUDE.md §6 requires in the relevant permission set(s) is flagged as a failure (exit code 1), with the offending field and expected permission set(s) named in the output.
  2. A `fieldPermissions` entry in any permission set that references a field whose `field-meta.xml` has `<required>true</required>` or is a MasterDetail relationship type is flagged as a failure, matching the real "You cannot deploy to a required field" `sf` deploy error.
  3. An Apex test (`.cls`) or seed-data JSON (`data/seed/`) referencing a picklist value literal not present in that field's `<valueSet>` in its `field-meta.xml` is flagged as a failure; a currently-valid literal (e.g. any value already used in a passing Apex test today) must NOT be flagged.
  4. If the Architect confirms a genuine gap in `@wire`/imperative Apex parameter-shape coverage, a mismatched call is flagged; if no gap is confirmed, this item is documented as a no-op with the trace recorded, not silently dropped.
  5. Re-running the full existing check suite (`python3 scripts/check-references.py`, `python3 scripts/build-instrument.py --check`) against the current `main` branch continues to exit 0 — i.e., the new checks introduce zero false positives against the current repo state, and each new check has been explicitly validated (per issue requirements) against at least one real, currently-passing example of that pattern in the repo before being considered done.
  6. Whatever invocation point is chosen (extending `check-references.py` directly, or a new sibling script) is wired into the same command Developer/QA agents already run before a deploy, and — if a sibling script is used instead of extending `check-references.py` in place — both scripts are documented together as the standard pre-deploy check sequence in `AGENTS.md` §2 and/or `CLAUDE.md` §5, so neither is a command an agent has to remember unprompted.
- **Target Test Target:** No existing Apex class or LWC Jest spec applies — this is a Python tooling change. The test target is the script(s) themselves: `python3 scripts/check-references.py` (and, if item 4 requires it, its extended reference-resolution logic) run against (a) the current clean `main` tree (expect exit 0, no new findings) and (b) deliberately injected negative-control fixtures for each of the four new checks (expect exit 1 with a clear, actionable message per finding). Negative-control fixtures should be constructed the same way QA already did this session (e.g. a deliberately invalid picklist literal in seed data) and removed/reverted after validating the check fires, or kept as a documented self-test fixture if the Architect prefers a permanent regression fixture — Architect's call.
