# TASK SCOPE — ISSUE #overview-redesign-funnel-drilldown

## 1. Requirements Breakdown

- **Target Objective:** On `gtmOverview` (the GTM Offerings Overview/landing page), make the "How far pages get" funnel interactive: clicking a funnel stage filters the adjacent "New assessment requests" panel to that stage; by default (nothing clicked) the panel shows the "Assessment" (i.e. "Asked for the assessment" / `requested`) stage's requests; and the panel should surface a bit more information per row when filtered.

- **System Component Impacted:** LWC (`force-app/main/default/lwc/gtmOverview/gtmOverview.js/.html/.css`) and, conditionally, Apex (`force-app/main/default/classes/GtmHomeSnapshotController.cls`) — see the data-model fork flagged below, which the Architect must resolve before implementation starts.

- **Pre-work verification (post-merge state, confirmed against `origin/main` @ `c7048a3`, PR #213):** The local `main` this BA scope was drafted against was stale by several merged PRs (#211–#213) at the start of investigation; `git pull origin main --ff-only` was run to bring it current before reading any file below. Confirmed current (not stale) structure:
  - `gtmOverview.js` has a `funnelShape` getter (line ~269) that maps `this.funnel` (the existing four-stage array) into chip/shape/style props: `chipClass` (`fn-chip fn-chip--<tone>`), `shapeClass` (`fn-shape fn-shape--<tone>`), `shapeStyle` (CSS custom properties `--fn-top`/`--fn-bottom`), tone palette `['quiet','info','warn','good']` by stage index.
  - `gtmOverview.html` renders `<ol class="fn-labels">` (one `<li class="fn-step" key={st.key}>` per stage, with the chip, label, count, drop-off badge) and a sibling `<div class="fn-funnel">` (one `<div class={st.shapeClass} style={st.shapeStyle}>` per stage) — two parallel `for:each` loops over the **same** `funnelShape` array, so `st.key` is the same 4 stable string keys in both places: `sent`, `opened`, `started`, `requested` (defined in the `funnel` getter, ~line 228–255, unchanged by #213 as designed).
  - `gtmOverview.css` already defines the tone tokens to reuse for a selected/active state: `.fn-chip--quiet/info/warn/good` and `.fn-shape--quiet/info/warn/good` (and the identically-toned `.pill--good/warn/info/quiet` used elsewhere on the page). No new colors are needed for point 6 below.
  - The "New assessment requests" panel (`gtmOverview.html` ~line 126–144) is untouched by #213: `hasRequests` / `requests` / `showEmptyRequests` getters, `rows`/`row` markup, backed by `loadRequests()` → `getRecentNewAssessmentRequests()` in `gtmOverview.js`.

- **⚠️ Design fork the Architect must resolve before assigning a Developer — this is NOT a settled detail, do not let a Developer guess it:**
  The four funnel stages are **not** the same population as the "requests" panel's data source, and reconciling that is the core of this issue, not an implementation detail:
  - `funnel`'s `sent`/`opened`/`started`/`requested` counts are derived entirely from `getDeals()` → `GTM_Saved_Configuration__c` + `GTM_Link_Event__c` rows (a deal reaches a stage the moment its link was sent / opened / form-started / converted).
  - The "New assessment requests" panel's `requests` array comes from a **separate** Apex method, `GtmHomeSnapshotController.getRecentNewAssessmentRequests()`, which queries `GTM_Assessment_Request__c WHERE Status__c = 'New'` (top 5, `OwnerId`-scoped unless the running user is a `GTM_Offering_Admin` — see OWD note below). A `GTM_Assessment_Request__c` record **only exists once someone has actually submitted a request** — i.e. it is inherently scoped to the `requested` stage. There is no `GTM_Assessment_Request__c` (or any other) record representing "this specific deal reached `opened` but never submitted," so there is no natural row-level dataset to show in the panel for the `sent`, `opened`, or `started` stages.
  - Two ways to resolve this, and the Architect must pick one and say so in the design plan rather than leaving it for the Developer to invent:
    1. **Narrow scope (recommended default if no other signal emerges):** only the `requested` stage is meaningfully "clickable" against the current requests panel; clicking `sent`/`opened`/`started` either (a) is a no-op / stages are rendered non-interactive for those three, or (b) toggles the panel to an explicit "No submitted requests reached this stage yet — N deals are here" empty state that does NOT attempt to list individual deals. This keeps the panel's Apex surface unchanged for those three stages.
    2. **Full drilldown (matches the user's literal framing more closely):** clicking `sent`/`opened`/`started` swaps the middle panel's data source to the relevant slice of the existing `getDeals()` result (already loaded client-side as `this.deals`, no new Apex call needed) rather than to `requests`, i.e. the panel becomes "requests, or matching deals" depending on which stage is selected. This is more work in `gtmOverview.js` (a second row-shaping function reusing `deals`) and in `gtmOverview.html` (either two `for:each` branches or a single computed `panelRows` getter) but needs zero new Apex.
  - This scope document intentionally does **not** pick between the two — it is a UX/product decision (does "click sent → see the list of individual deals that only got a link sent" make sense to a rep the same way "click requested → see request rows" does?), not a technical one, and the mockup/Artifact referenced in the ticket was not re-checked panel-by-panel against these two options by this BA pass. Flag to Architect: confirm against the Artifact before choosing.

- **Toggle-to-deselect (point 4 of the ticket) — flagged as an assumption, not settled:** clicking the already-selected stage again resetting to the default (`requested`) view is a reasonable UX default and is what this scope assumes, but it was not explicit in the user's framing (which only said "by default show the assessment submissions"). The Architect should confirm this rather than have the Developer silently decide it. An equally defensible alternative is that there is no "deselect" — the funnel always has exactly one active stage, defaulting to `requested` on load, and a click always sets (never toggles) `selectedFunnelStage`.

## 3. Plan Acceptance Criteria

- **Success Metric:**
  1. Clicking a funnel stage element (in `.fn-labels` and/or `.fn-funnel`, whichever the Architect designates as the click target — likely both, since they render the same stages side by side) sets a new `@track selectedFunnelStage` property to that stage's `key` (`sent`/`opened`/`started`/`requested`).
  2. On initial load, with nothing clicked, `selectedFunnelStage` defaults to `'requested'` and the "New assessment requests" panel shows exactly what `getRecentNewAssessmentRequests()` returns today (no regression to the panel's current default behavior).
  3. Selecting the `requested` stage (whether by default or by click) continues to show the same request-row data; selecting `sent`/`opened`/`started` follows whichever resolution path (1 or 2 above) the Architect has chosen and documented in the design plan — QA must be able to point at that design plan to know which behavior is correct, rather than inferring it from the code.
  4. The selected stage has visible active styling in both `.fn-labels` and `.fn-funnel`, built from the existing `fn-chip--<tone>` / `fn-shape--<tone>` / `pill--<tone>` color tokens already in `gtmOverview.css` — no new hex values introduced.
  5. When the panel is showing `requested`-stage rows (default or explicit), each row shows at least one additional field beyond today's `name`/`meta` (company · platform)/`date` — minimum bar: `Assessment_Tier__c` and/or `Assessment_Score__c` and/or `Offering_Key__c`, all already present on `GTM_Assessment_Request__c` and addable to the existing `SELECT`/`RequestSummary` DTO without a new query or join.   6. `Database.query`/SOQL scoping in `getRecentNewAssessmentRequests()` (the `OwnerId = :runningUserId` filter unless `isAdmin()`) is preserved exactly as-is if that method's `SELECT` is touched — this is the rep-data-scoping-OWD work from this session (`GTM_Assessment_Request__c` flipped to Private OWD); do not widen or narrow the WHERE clause as a side effect of adding columns.
  7. No files under the `overview-redesign-table-nav` deal-table's ownership are touched (that work is separate, unmerged, and blocked on org quota).

## 4. Architect Addendum — Design Fork Resolution (Architect, 2026-09-18)

**Compliance review:** Scope doc contains no unresolved placeholders. Code Dependency Checklist verified against source: all three items correctly "No" — `getDeals()` and `getRecentNewAssessmentRequests()` are both read-only SOQL (no DML/callouts, so `GtmAgentToolSurface`'s zero-DML/zero-callout contract is not implicated regardless — this page is not a GUS tool surface); no `GTM_Assessment_*` custom-metadata XML is touched; no new fields/objects, so no permission-set grants are required under `CLAUDE.md` §6.1. Approved as-is.

**Artifact access:** Unable to load `https://claude.ai/artifact/LMGAZmo9W8ZhiT3PS9y8qa` from this environment (no browser/fetch tool available in this session). Decision below is therefore made on the documented user framing rather than a re-inspection of the mockup, per the fallback guidance given for this review.

**Decision: Option 2 — Full drilldown.** All four funnel stages (`sent`/`opened`/`started`/`requested`) are clickable. Selecting `requested` (or the default, unclicked state) shows `GtmHomeSnapshotController.getRecentNewAssessmentRequests()` rows exactly as today. Selecting `sent`/`opened`/`started` swaps the panel's data source to a client-side filtered slice of `this.deals` (already loaded via the existing `getDeals()` call — zero new Apex, zero new SOQL) keyed on each deal's furthest-reached stage matching the selected `key`.

**Reasoning:**
- The user's own words — "the section that shows the new assessment requests should be updated based on the portion of the funnel the user clicks" — describe a single generalized behavior applying to "the portion... the user clicks" (i.e., any stage), not a special case carved out for one of four. Nothing in that framing singles out `requested` as the only interactive stage; Option 1 would silently contradict the literal instruction for 3 of 4 click targets.
- Option 2 has no Apex/SOQL cost (`this.deals` is already resident client-side), so there's no technical pressure toward the narrower option — the BA's flagged concern ("is this more work") is not a blocker.
- This does require the `panelRows`-shaping work the BA scoped as optional (a second row-shaping function/getter in `gtmOverview.js` and either a computed getter or two `for:each` branches in `gtmOverview.html`), and the Developer must clearly distinguish the two row shapes (assessment-request DTO vs. deal row) in markup — e.g. deal rows won't have `Assessment_Tier__c`/`Assessment_Score__c` (those only exist post-submission per §3 point 5, which still applies only to the `requested`-stage panel view). Non-`requested` stages should show whatever fields `this.deals` rows already carry (company/platform/date equivalents), not fabricate assessment-specific fields that don't exist pre-submission.
- Acceptance criterion §3.3 is updated in effect: for `sent`/`opened`/`started`, "correct behavior" is now the deals-slice view (Option 2), not a no-op/tooltip. QA should validate all four stages return distinct, correctly-filtered row sets, not just `requested`.

**Toggle-to-deselect: confirmed as scoped.** Clicking the already-selected stage again resets `selectedFunnelStage` to `'requested'` (the default), not to an unset/no-selection state — there is always exactly one active stage, and `requested` is both the initial default and the deselect target. This keeps the panel always populated (matches today's no-empty-panel default) and gives the funnel a single always-highlighted stage for the active-styling requirement in §3 point 4. Developer should implement toggle as: `selectedFunnelStage = (clicked === selectedFunnelStage) ? 'requested' : clicked`.
