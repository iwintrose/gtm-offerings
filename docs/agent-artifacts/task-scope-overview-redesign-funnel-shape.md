# TASK SCOPE — ISSUE #overview-redesign-funnel-shape

## 1. Requirements Breakdown

- **Target Objective:** Replace the current "How far pages get" visualization in `gtmOverview` — today a stacked list of separate horizontal progress bars, one per stage, with visible gaps between them — with a true tapering trapezoid funnel matching the standard Salesforce CRM Analytics / Tableau funnel-chart convention: widest at the top, each stage's bottom edge flows directly into the next stage's top edge (no gap, no separate boxes), continuously narrowing toward the bottom stage. This is a **visual/rendering change only**. Do not touch `get funnel()`'s data or math in `gtmOverview.js` — re-verified below, it is already correct and already computes the right stage populations; this issue only changes how those numbers are drawn.
- **System Component Impacted:** LWC (`force-app/main/default/lwc/gtmOverview/gtmOverview.html`, `.css`). No Apex changes. `gtmOverview.js` should only change if the trapezoid rendering needs additional derived geometry values (e.g. a per-stage width percentage or clip-path polygon string) computed alongside the existing `get funnel()` getter — see below.

### Current-state findings (verified against real code)

- `gtmOverview.js`'s `get funnel()` (lines 228–255) computes four stages — `sent` (Page sent), `opened` (Opened it), `started` (Started the form), `requested` (Asked for the assessment, labeled "Requested" in the approved mockup copy) — each as a strict fallout-subset of the one before (`deals.filter(d => d.opened)`, `d.started`, `d.converted`), with `pct` (percentage of the top stage), `barStyle` (a `width: N%` inline style for the current flat bar), `showDrop`/`dropLabel`/`dropClass` (the "N did not" annotation, with the single worst single-stage drop highlighted), and `barClass`. This math is confirmed correct and unchanged by this issue — it already satisfies "one unit (deals), one window (all-time), each stage a strict subset of the one before," per that getter's own doc comment, and matches the four approved stage labels/order from the mockup (`Page sent → Opened it → Started the form → Requested` — note the mockup's exact copy is "Requested," not this getter's current longer `'Asked for the assessment'` label; **relabeling stage 4's `label` string to "Requested" is in scope for this issue** since it's part of the approved visual, but the underlying `n`/`pct`/fallout math is not touched).
- Current rendering (`gtmOverview.html` lines 90–105, `.fn`/`.fn-step`/`.fn-track`/`.fn-bar` in `gtmOverview.css` lines 299–319): each stage is a `<li>` with a label/count row above a `.fn-track` div containing one `.fn-bar` sized to `barStyle`'s width — a horizontal bar chart, stacked vertically, each bar independently rounded (`border-radius: 999px`) and visually separate from its neighbors. This is the shape requirement 3 replaces.
- **Recommended implementation approach** (for the Architect/Developer step to confirm, not prescribed as final here): a true tapering funnel where each stage's own top/bottom edges are literal straight-line continuations of its neighbors' edges is most reliably built with four stacked `<div>`s, each stage using CSS `clip-path: polygon(...)` with the stage's own top-width and bottom-width computed from `pct` (stage N's top width = stage N-1's bottom width, guaranteeing no gap/step at the seam) rather than `border-radius`-pill bars. This requires `gtmOverview.js` to emit one additional derived value per stage beyond what `get funnel()` already returns today — e.g. `topPct`/`bottomPct` (or an inline `clip-path` string) computed from consecutive stages' `pct` values — most cleanly as a **new getter that wraps `get funnel()`** (e.g. `get funnelShape()`) rather than modifying `get funnel()` itself, keeping the "funnel math" and "funnel geometry" concerns separated and leaving `get funnel()`'s own existing return contract (and anything else that might read it) unchanged. Confirm no other component or test currently consumes `get funnel()`'s return shape directly before deciding whether to extend it in place vs. wrap it (a quick check of `gtmOverview.test.js` for `.funnel` assertions is enough).
- **Styling requirement (validated in mockup):** reuse `.ov-card`/`.ov-card-h`/`.ov-h` verbatim for the card chrome (unchanged — this issue only touches the `.fn`/`.fn-step`/`.fn-track`/`.fn-bar` family inside the card body). The existing `.fn-drop`/`.fn-drop--worst` "N did not" annotations and the `.asides` block below the funnel are unchanged and must keep rendering exactly as today, underneath the new trapezoid shape.
- This issue does **not** include the interactive click-to-filter behavior (clicking a stage to filter "New assessment requests") — that is `overview-redesign-funnel-drilldown`, scoped separately, which depends on this issue's markup existing first (the drilldown issue adds click handlers onto whatever DOM elements this issue produces per stage — coordinate the per-stage element/key naming so the two issues don't collide, e.g. keep `st.key` as the stable per-stage identifier both issues key off of).
