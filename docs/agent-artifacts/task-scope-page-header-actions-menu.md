### Current state (verified in code)
`gtmPageHeader.html` has only `<slot name="actions">` inside `.slds-page-header__col-actions`; JS has four `@api` string props (iconName, eyebrow, title, meta). Its CSS: row `flex-wrap:wrap; align-items:flex-start`, title `flex:1 1 16rem`, actions `flex:0 1 auto; flex-wrap:wrap; justify-content:flex-end; align-items:center; margin-left:auto`. Slotted buttons live in the consumer's template so they cannot be re-parented into a menu; the header has no knowledge of its actions.

### Decision 1 — Declarative `actions` prop (recommended)
Add `@api actions = []`, each `{ name, label, iconName, variant ('brand'|'neutral'|'destructive'), disabled? }`. Native-first check: the SLDS page-header pattern is a primary button plus `lightning-button-menu` overflow, and `lightning-button-menu` / `lightning-menu-item` are the base components; nothing standard replaces a custom header on an App Page. So we compose base components, we do not hand-roll a menu.
- Wide: `lightning-button` per action (data-name). Narrow: ONE `lightning-button-menu` (icon `utility:rows` per mockup hamburger; `alternative-text`/aria label e.g. "Page actions"), items are `lightning-menu-item` with value=name, label, prefix-icon-name; first item = the primary action.
- Emit ONE bubbling-not-required `CustomEvent('headeraction', { detail: { name } })` from both variants (button click and menu `onselect`); consumers use a single `onheaderaction` dispatcher keyed on `name`.
- Keep `slot="actions"` for non-collapsing custom content (gtmAnalytics 12rem combobox). Slot content renders in the actions block at every width; it is not folded into the hamburger.
- I added `'destructive'` to the variant list because gtmRecycleBin's "Delete Selected Permanently" uses `variant="destructive"` today; owner's list only named brand/neutral. `lightning-button` supports it; `lightning-menu-item` has NO variant, so in the menu it can only be distinguished by order/label/icon (see fork F3).

### Decision 2 — how the 900px breakpoint is detected (recommendation, Architect to spike)
Owner said "below 900" without saying viewport vs container. In the Salesforce app shell (nav bar, utility bar, Lightning App Builder side panels, split view) the page's container is narrower than the viewport, so a viewport `@media (max-width:900px)` would fire too late (a 1000px window can hold an ~750px header). Recommendation: measure the HEADER'S OWN width (container semantics).
- Preferred: CSS container query, `:host { container-type: inline-size; }` and `@container (max-width: 899.98px)` to switch. No JS, no observer lifecycle, works with Jest static-CSS assertions. Risk to verify in a spike: LWC synthetic-shadow/CSS scoping and the org's browser floor for `@container` (Chrome 105+, Safari 16+, Firefox 110+), and that `container-type` on `:host` does not break the block-level width the header has today (inline-size containment means the host cannot size from its content; it is `display:block` so this should be fine).
- Fallback if container queries are unsafe: `ResizeObserver` on `this.template.host` (or the `.hdr` div) in `renderedCallback`/`connectedCallback`, setting a tracked `isCompact` boolean, disconnected in `disconnectedCallback`. Note jsdom has no ResizeObserver, so Jest must stub it (`global.ResizeObserver`) and call the callback manually.
- Rejected: plain viewport `@media` (wrong measure in the app shell). If the owner literally meant viewport width, that is a one-line change; flag it (F1).

### Decision 3 — both variants in the DOM vs `lwc:if`
- If container queries are used: both variants are in the DOM, CSS `display:none` switches them, single `actions` source, no JS state. Cost: hidden nodes still exist, so Jest queries like `querySelectorAll('lightning-button')` see both sets, and tab order/AT ignore `display:none` correctly. Tests must scope by data attribute/class (`.hdr-actions-wide lightning-button`).
- If ResizeObserver is used: use `lwc:if={isCompact}` (only one variant rendered, cleaner DOM, easier tests via toggling the stub). Choose per Decision 2 outcome; do not mix.

### Layout rules to add to the contract
- `.slds-page-header__col-actions` gains `align-self:flex-end` (bottom-right when the row is one line and the title stack is taller, and when wrapped under the title). Existing `margin-left:auto`, `justify-content:flex-end`, `flex-wrap` stay; the `align-items:center` inside the actions column stays allowed (aligns buttons among themselves only). The row/title column keep `align-items:flex-start`.
- Hamburger touch target >= 44x44px (`lightning-button-menu` icon button renders ~32px by default; enforce with min-width/min-height 44px on the host via CSS custom-property/wrapper, verify it does not clip).
- Update `docs/architecture/gtm-page-header-layout.md` (or a new `gtm-page-header-actions.md`) BEFORE code (Contract First): prop schema, event payload, breakpoint mechanism, CSS rule table, consumer migration table.

### Owner addenda (2026-09-19, after mockup review) — supersede anything above that conflicts
- **A1 Menu opens DOWNWARD, never clipped.** Use `lightning-button-menu` with `menu-alignment="right"` (dropdown anchored to the right edge, default opens down; do not use `bottom-*` alignments, and do not set `auto`, which can flip upward). Clipping audit done by the BA: `.hdr` in `gtmPageHeader.css` has no overflow rule (keep it that way; add none to `.hdr`, the row or the actions column). The three migrating consumers' `overflow:hidden` rules found in gtmOverview.css (lines 19, 121), gtmContentHome.css (line 83) and gtmPageBrowser.css (line 21) sit on card/panel/body elements, not on ancestors of the header, but the Architect must confirm each is not an ancestor of `c-gtm-page-header` (and check the lightning-app-page region wrapper). `gtmPageBrowser` `.pb-head` is `position:sticky; top:0; z-index:2` with no overflow, so the dropdown is not clipped, but its z-index of 2 may let later siblings (e.g. `c-gtm-story`, rep-link-finder) paint OVER the open menu; the Architect must verify and raise/adjust stacking only if needed (the menu has its own high z-index inside the sticky stacking context, so the sticky header's z-index is what matters). Acceptance: open menu at 600px and 360px is fully visible, drops down over page content, does not create page scrollbars or horizontal overflow (also at the right edge; right-aligned menu must not extend past the viewport at 360px).
- **A2 Icons are kept everywhere.** `iconName` is REQUIRED per action in the `actions` schema (already in it); wide buttons use `icon-name`, and each menu item shows the same icon via `lightning-menu-item` **`prefix-icon-name`** (the correct attribute; `lightning-menu-item` has no `icon-name`). Overview keeps utility:new (New engagement link), utility:identity (New assessment (no page)), utility:search (Find a link you sent), utility:preview (See Assessments); Content Home and Recycle Bin keep their current icons (utility:refresh, utility:recycle_bin_empty, utility:new, utility:undo, utility:delete). Jest asserts every item's `prefixIconName` equals its action's `iconName`.
- **A3 Position of the hamburger is TOP-RIGHT below 900px** (aligned to the top of the header row, beside the title block), NOT bottom-right. At >= 900px buttons stay bottom-right (`align-self:flex-end`). So the CSS rule is breakpoint-dependent: wide `.slds-page-header__col-actions` `align-self:flex-end`; compact `align-self:flex-start` (row already `align-items:flex-start`; keep `margin-left:auto` so it hugs the right and never wraps under the title: below 900 the hamburger is a single 44px control, and the 16rem title floor still fits beside it at 360px, 16rem = 256px + 44px + 1rem gap + 2rem padding ~ 348px, so verify at 360 and let it wrap only if the title floor would be violated). Slot content (Analytics combobox/refresh) follows the same compact rule. Static CSS tests assert both alignments. Where the earlier text says "at every width bottom-right", this addendum overrides it for the compact variant.
