# TASK SCOPE — ISSUE #pages-preview-fixes

## 1. Requirements Breakdown

- **Target Objective:** Fix three related, stakeholder-reported live bugs in the Pages tab's preview flow (`gtmRepLinkFinder` → `gtmConfigurator` / `gtmReadoutWorkspace`):
  1. The `c-gtm-config-wizard` overlay renders off-position/full-page-width instead of respecting the preview-pane boundary, when `gtmConfigurator` is embedded inside `gtmRepLinkFinder`'s preview pane.
  2. The "Engagement Link" box (`gtmRepLinkFinder.html`) and the "Assessment Link" box (`gtmReadoutWorkspace.html`) both render the same `Generated_URL__c` value (same URL, same password, same Apex) a few inches apart on screen once a rep clicks into the workspace.
  3. Preview/workspace UI state (`showPreview` / `showWorkspace` / password-reveal) is lost when a rep follows a real `<a href>` navigation out of `gtmAssessmentDetail` (e.g. to the Account/Opportunity/Contact) and back, because that link is a full page unload/reload that unmounts the whole LWC tree, and unlike the Account→Contact→Link drill state, this view-state is not currently mirrored anywhere that survives remount.
- **System Component Impacted:** LWC (`gtmConfigurator`, `gtmConfigWizard`, `gtmOverview` — reference only, `gtmRepLinkFinder`, `gtmReadoutWorkspace`, `gtmAssessmentDetail`). No Apex, no Custom Metadata/YAML, no schema changes.

Findings below were independently re-verified against the current code (not re-derived from a spec) before this scope was written; all three bugs and their proposed fixes are confirmed accurate as of this scoping pass. No ambiguity requiring human design-fork resolution was found — each bug has a single reasonable fix direction, documented below. Nothing here touches `gtm-dev` production data (these are LWC template/client-state changes only, no DML, no seed/migration scripts).

### Bug 1 — wizard overlay ignores preview-pane boundaries

**Confirmed:** `gtmOverview.html` lines 1–30 mount `<c-gtm-config-wizard>` as the literal first child of its `.ov` container, with an explicit doc comment (lines 3–24) stating "KEEP THIS FIRST" and explaining why: `gtmConfigWizard._measureChromeOffset` (`gtmConfigWizard.js` lines 327–336) computes `host.getBoundingClientRect().top + window.scrollY` and only resolves to the constant Salesforce-chrome height (~106px) when the host sits at document position 0 — i.e., is the first thing painted in its ancestor chain. `gtmConfigurator.html` mounts its own `<c-gtm-config-wizard>` at line 467 (of 669 total lines), well after the entire main page body/footer template (closing at line 465) — not first-child of its root `.rootClass` div (line 2). This is exactly the failure mode the `gtmOverview.html` comment warns about, and it's live now because `gtmConfigurator` is rendered nested inside `gtmRepLinkFinder`'s preview pane (Pages tab → "Find a link you sent" → Preview), where the host's document offset is no longer near 0.

**Recommended fix:** Move `gtmConfigurator.html`'s `<c-gtm-config-wizard>` block (lines 467–482) to be the first child rendered inside the component's root div, mirroring `gtmOverview.html`'s pattern exactly (including porting forward the "KEEP THIS FIRST" doc comment, adapted to `gtmConfigurator`'s own prop names). Do **not** change `_measureChromeOffset`'s strategy — it is a shared component consumed by `gtmOverview` (already correct) and two other Lightning tabs plus two Experience Cloud sites per the existing comment; altering its measurement approach is a much larger blast-radius change for a problem that already has a proven, working, minimal fix (mount order) at the call-site level.
  - **Risk check performed:** Read the surrounding ~230 lines (240–470) of `gtmConfigurator.html`. The wizard's current position (line 467) sits between a closing `</template>` for the main page body (line 465) and the "assistant bubble" block (line 484 onward) — it is not nested inside any conditional wrapper that depends on sibling DOM order, and its own `is-open={customizeOpen}` prop already gates its actual visibility, so moving its *position* in the template (not its *condition*) should not change when it renders, only where in the DOM it sits. No CSS in the surrounding template targets the wizard via sibling/adjacency selectors as far as this read confirmed (SLDS/`position:fixed` overlay pattern, consistent with `gtmConfigWizard`'s own `sheetStyle`/`scrimStyle` getters using inline `top` styling rather than flow layout). Developer should still grep `gtmConfigurator.css`/any shared CSS for adjacency selectors (`+`, `~`) referencing the wizard tag before merging, as a final guard — flagged here as residual risk, not fully eliminated by this read-only pass.

### Bug 2 — duplicate Engagement Link / Assessment Link sections

**Confirmed:** `gtmRepLinkFinder.html` lines 254–316 render the "Engagement Link" + "Password" box unconditionally inside the `isViewVisible` block — i.e., it is **always visible** as soon as a rep is on the "view" step for a selected link, before any further action. `gtmReadoutWorkspace.html` (rendered inline via `showWorkspace`, itself only reachable by clicking "View readout"/"Generate Readout" from further down the same view — i.e., **only shown after an explicit rep action**, layered on top of the always-visible Engagement Link box above it) duplicates the identical URL/password box at lines 11–40+, sourced via a different relationship path (`Saved_Configuration__r.Generated_URL__c` vs `gtmRepLinkFinder`'s direct field) but backed by the same Apex and same underlying data. `gtmReadoutWorkspace.html`'s own doc comment (line 1, "mirroring gtmRepLinkFinder's own view-step block exactly, same fields, same actions, same Apex") confirms this was a deliberate copy, not independent logic.

**Recommended fix (direction confirmed, not reversed):** Remove the "Assessment Link" box (`gtmReadoutWorkspace.html` lines ~11–40+, the `grw-link-section` block gated by `hasCfg`) from `gtmReadoutWorkspace.html`, keeping its distinct "Preview the assessment" button (which opens `GtmAssessmentPreviewModal` — genuinely different from `gtmRepLinkFinder`'s own "Preview" button, which toggles the live `c-gtm-configurator` page inline). Do **not** remove the box from `gtmRepLinkFinder.html` — it is the always-visible parent view the rep sees first; removing it would leave no link/password box at all until a rep clicks into the workspace, which is not the fix. Confirm no other logic reads `gtmReadoutWorkspace.js`'s local `selectedLinkUrl`/`passwordDisplay`/`passwordRevealed` state independent of the box being deleted (i.e., check whether those JS properties/handlers become fully dead code and should be removed too, or whether they're still needed elsewhere in `gtmReadoutWorkspace.js`).

### Bug 3 — preview/workspace state lost on navigating to the assessment

**Confirmed:** `gtmAssessmentDetail.html` lines 25, 47, 62, 77 use plain `<a href={...}>` tags (`cfgRecordUrl`, `accountUrl`, `oppUrl`, `contactUrl`) — real browser navigation that fully unloads the page and unmounts the LWC tree, rather than `NavigationMixin`. `gtmRepLinkFinder.js` already has a working, well-commented precedent for surviving exactly this class of problem for its Account→Contact→Link drill selection: `writeDrillStateToUrl()` (lines ~509–534) mirrors state onto `window.location` via `window.history.replaceState`, and `captureLinkFinderState()` (wired to `CurrentPageReference`, lines ~433–471) restores it on load — both best-effort/try-catch wrapped. `showPreview`/`showWorkspace`/password-reveal state is not currently part of either function.

**Recommended fix: extend the existing URL-param mechanism** (`writeDrillStateToUrl()` / `captureLinkFinderState()`) with new namespaced params — e.g. `c__rlfShowPreview`, `c__rlfShowWorkspace`, `c__rlfPwRevealed` — following the same "only write the non-default value" convention already used for `c__rlfMode`. This is preferred over introducing a second, parallel sessionStorage-keyed-by-record-id mechanism (the pattern `gtmConfigurator.js` uses for its `ma-auth-<savedRecordId>` auth-token cache, lines ~1435–1680) for three reasons:
  1. `gtmRepLinkFinder`'s own component already owns a proven, working URL-state mechanism for this exact user journey (its immediate parent state — link selection); showPreview/showWorkspace are child-state of that same selection and belong on the same channel rather than split across two competing state systems for one component.
  2. Because the navigation is a real full-page unload/reload (not an SPA hop), the browser's native back-navigation returns to the exact prior URL — URL params survive that transparently, with no extra plumbing.
  3. Splitting state between URL params (drill) and sessionStorage (view) for the same component instance would create two independent restore code paths that could race or disagree (e.g., URL says link X selected, sessionStorage says workspace open for link Y) — a correctness risk the single-channel approach avoids.

  **Do not touch** `_restoredAccountId` / `_restoredLinkId` / `_targetApplied`'s existing branching logic in `captureLinkFinderState()` — that machinery already has non-trivial edge-case handling (the "only act once per distinct restore target" re-entrancy guard, and the explicit "do NOT restore when targetRecordId is present" deep-link precedence rule). Add the new `showPreview`/`showWorkspace`/password-reveal restoration as an **additive, independent read** inside the same wired method (gated on `_restoredLinkId` already being set, since preview/workspace state is only meaningful once a link is selected) rather than interleaving it into the existing account/contact/link restore branches.

## 3. Plan Acceptance Criteria

- **Success Metric:**

  - Bug 2: The "Assessment Link" box no longer appears in `gtmReadoutWorkspace`; the "Engagement Link" box in `gtmRepLinkFinder`'s view step remains the single source of the URL/password UI; "Preview the link" (gtmRepLinkFinder) and "Preview the assessment" (gtmReadoutWorkspace, via `GtmAssessmentPreviewModal`) both still work and remain visibly distinct.

Existing drill-state refresh-survival behavior (Account→Contact→Link) and the deep-link `targetRecordId` precedence rule must both continue to pass unregressed.
- **Target Test Target:** No existing Jest specs currently found for `gtmConfigurator`, `gtmRepLinkFinder`, `gtmConfigWizard`, or `gtmReadoutWorkspace` at scoping time — Developer must add/extend Jest specs under `force-app/main/default/lwc/gtmRepLinkFinder/__tests__/` (URL-param write/restore round-trip for the new params, mirroring any existing drill-state test coverage) and `force-app/main/default/lwc/gtmConfigurator/__tests__/` (wizard mount-order/first-child assertion) as part of this change; run via `npm test`. Manual/browser QA (per this repo's standing QA convention) must cover the live Pages tab preview flow end-to-end for all three fixes, not just the changed component in isolation.

## PR Sequencing Note

Recommend landing all three fixes in a **single PR**: they are all small, isolated to the same three-component preview/workspace flow, were reported together by the same stakeholder session, and a single combined QA pass over the Pages tab preview flow is more efficient and more likely to catch cross-bug interaction issues (e.g., Bug 3's restored state interacting with Bug 2's removed box) than three separate review/deploy cycles. If the Developer or QA step finds Bug 1's mount-order change carries meaningfully higher regression risk than Bugs 2/3 (per the residual CSS-adjacency-selector risk flagged above), it is reasonable to split Bug 1 into its own PR at that point — but default to one PR unless that risk materializes.
