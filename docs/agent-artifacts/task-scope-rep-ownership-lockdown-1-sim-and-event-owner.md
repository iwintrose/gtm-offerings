### 1B. Design (for the Architect to confirm and place in `docs/architecture/`)

- **C1 shared helper.** ONE class, `GtmLinkOwnerStamp` (final, `public without sharing`, no `@AuraEnabled`, no DML). API sketch (Architect owns the final contract):
  - `public static Id ownerForLink(Id savedConfigurationId)` : one dynamic SOQL `SELECT OwnerId FROM GTM_Saved_Configuration__c WHERE Id = :savedConfigurationId LIMIT 1` (dynamic to keep the Lookup-repoint rule), then validates the owner with one `SELECT Id FROM User WHERE Id = :ownerId AND IsActive = true AND UserType != 'Guest'` (mirror `firstUsable`), returns the Id or null. Whole thing in try/catch returning null; never throws.
  - `public static void stamp(List<SObject> rows, Id ownerId)` : `put('OwnerId', ownerId)` on each row only when `ownerId != null`.
  Query budget: `ownerForLink` = 2 queries (config + user) unless the Architect merges them into one query (`SELECT OwnerId FROM GTM_Saved_Configuration__c` cannot filter `Owner.IsActive`/`Owner.UserType` via dynamic SOQL with `Owner.IsActive = true AND Owner.UserType != 'Guest'`? It can: `WHERE Id = :id AND Owner.IsActive = true AND Owner.UserType != 'Guest'` is valid polymorphic-safe for User-owned objects, and yields the ONE-query-per-call requested). PREFERRED: the single-query form; owner of a Saved Configuration is always a User (not a queue; confirm the object has no queue-ownership, it is a Private custom object with no queues), so the relationship filter is safe. Architect confirms.
  - Guest note: a guest running `without sharing` code can read `User` via relationship; verify in the check-only run.
- **Event stamping.** In `logEvent` and `logEvents`, after `GtmLegacyConfigId.resolve`, call `GtmLinkOwnerStamp.ownerForLink` ONCE per call (not per row), stamp before the `insert`. `logEvents` looks up once for the whole batch. If the lookup returns null, OwnerId is left unset (guest-owned) and insert proceeds as today. No new throw path; keep the existing try/catch around insert. Insert with an explicit OwnerId of a non-guest user requires "Transfer" semantics only for owner changes on existing rows; a new row can name any active user as owner when the running (guest) user is `without sharing`? Architect/QA must verify in the check-only deploy that the guest-context insert with a non-guest OwnerId succeeds (custom objects: setting OwnerId on create is allowed with Create permission). The test (run as a non-guest stand-in) cannot prove the guest case; note as residual risk to verify manually post-deploy by the coordinator via a real prospect page view and a SOQL read (read-only).
- **Other stamped records.** Same helper, same single lookup per entry point: `GtmFormDraftController` saveDraft/clearDraft (`resolvedConfigId`), `GtmAssessmentDraftController` mint/re-save/resume-email budget rows (`configId` / `current.configId`; null configId means no owner, leave unset), `GtmAssessmentRequestController` closing row (add `Saved_Configuration__c` to the ~1199 SELECT, copy to the row, stamp), and `GtmLinkAuthController.logAccess` (`Task.OwnerId`; `recordId` is the link id). Every stamp is inside the existing try/catch; none may add a throw path.
- **C3 readers.** `GtmHomeSnapshotController.recentViews`: keep the `OwnerId = :runningUserId` rep branch (it is right once events are owned); no change is REQUIRED for correctness, so the deliverable is (i) a regression test proving rep A's `recentViews` equals A's own Page View count and never B's after stamping (fails today), and (ii) leave the admin branch unchanged. All other readers unchanged (see 1A.5); the sim test is the proof and any gap it reveals is fixed in a follow-up, not guessed here.
- **F1 (recorded).** Events (and drafts/Tasks) whose link is missing, deleted or owned by an inactive/guest user stay unowned by a rep (guest/site-owned). NO `GTM_Readout_Triage` queue fallback: events are analytics, not work items. Consequence: invisible to both reps after piece 4; visible to admins. Decision recorded, not open.
- **F2 (recorded).** Contact-level engagement (`GtmContactEngagementController`) shows each rep only their own links (and their events) for a shared contact. Follows the owner rule literally. Decision recorded, not open.
- **Open for the Architect:** (a) single-query vs two-query owner lookup (above); (b) helper name/visibility; (c) whether `GtmHomeSnapshotController` DealSummary/sitemap should get an explicit `OwnerId` belt-and-braces filter (parent C3 says only if the sim shows a gap); (d) whether to make `Task` stamping conditional on `recordId` being a `GTM_Saved_Configuration__c` id (it is the only caller today, but `logAccess` takes any Id: guard with `getSObjectType()`).

### 3B. Simulation test spec (write FIRST; sub-issue 1 owns it)

- Users: `repA`, `repB` = Standard users each assigned `GTM_Offering_User` (via `PermissionSetAssignment` in `System.runAs` of an admin to avoid mixed-DML); `noVaUserA`, `noVaUserB` = Standard users assigned ONLY the test permission set (Read on `GTM_Link_Event__c`, `GTM_Saved_Configuration__c`, `GTM_Assessment_Request__c`, no `viewAllRecords`; required class access to the readers), owning A's and B's links respectively (the links' `OwnerId` = these users, so the "no-viewAll" readers are tested as the link owners); `guestLike` = Standard user with no GTM permission set (a real Guest-type user is not creatable in test context). Assert per 3A.1-3A.3; for readers assert hand-computed values per rep (stage counts, `recentViews`, engagement, activity list) equal own and exclude other; admin (`GTM_Offering_Admin`) sees the union.
