### 1A. Verified current state (read from code)

**Hole 1: `GtmStageActionsController` (`public without sharing`).**
- `getStageContext(String configId)` (@AuraEnabled cacheable=false): resolves id via `GtmLegacyConfigId.resolve`, reads `GTM_Saved_Configuration__c` (stage, Generated_URL__c) and, by dynamic SOQL, the latest `GTM_Assessment_Request__c` (`Requester_Name__c`, `Requester_Email__c`, `Company__c`) for that link. No owner check. Requester PII of any rep's link is readable by id.
- `advanceStage(configId, newStage)` (@AuraEnabled): `SELECT ... FOR UPDATE` then `update cfg` setting `Presentation_Stage__c`. No owner check. The update fires the record-triggered flow `GTM_Config_Send_To_Client`, which calls the `@InvocableMethod sendProposalEmails` and emails the client. So a non-owner can trigger a client email on another rep's link.
- `sendProposalEmails(List<SendEmailInput>)` is the flow's `@InvocableMethod` (flow references class+method by name: `flows/GTM_Config_Send_To_Client.flow-meta.xml`); it reads the latest request with an email and sends. It has NO @AuraEnabled exposure and no client-supplied id from a rep; its only caller is the flow. It must keep working when the flow runs, even when the updating user cannot see the request (see design note D1).
- Only LWC caller: `lwc/gtmStageActions/gtmStageActions.js` (wire `getStageContext`, imperative `advanceStage`). On wire error it shows "Could not load stage information."; on advance error it shows `err.body.message`, so an `AuraHandledException` with a friendly message renders cleanly. Also placed via the AR record flexipage `GTM_Assessment_Request_Record_Page` (that flexipage hosts `gtmArCasePanel`, not stage actions; stage actions is on the Overview/link surface).
- Existing test `GtmStageActionsControllerTest` runs as the test-runner admin only (no runAs).

**Hole 2: `GtmArCasePanelController.getCaseForRequest(Id requestId)` (`public without sharing`, `@AuraEnabled(cacheable=true)`).** Two hops: `GTM_Readout__c WHERE Assessment_Request__c = :requestId` (LIMIT 1, newest) then `Case WHERE Readout__c = :readoutId`; returns `CaseDTO{subject,status,createdDate}` or null. `without sharing` is deliberate because `GTM_Offering_User` has no Case object permission (class header; the license rejects the grant; see `GTM_Offering_User.permissionset-meta.xml` lines ~927-936 comment). So the Case read must stay elevated, but the ownership gate must be added in front of it. Caller: `lwc/gtmArCasePanel/gtmArCasePanel.js` on the AR record page.

**Hole 3: `GtmAgentGetConfigState` (`public without sharing`, `@InvocableMethod execute(List<Input>)`).** Reads `Config_Payload__c` from `GTM_Saved_Configuration__c WHERE Id = :resolvedConfigId` (id from `GtmLegacyConfigId.resolve(inp.configId)`) and returns company/industry/accent/counts/note, plus the framework industry list from `GTM_Page_Content__c` (id-free, shared taxonomy). Callers: (a) `GtmAgentProxyController.executeGetState` (line ~350; also `without sharing`) via the tool `get_gtm_config_state`, where the id is `input.config_id` from the MODEL if present, else the session's `configId`. That means a prompt-injected or confused model can point the tool at ANY link id: this is the real hole (not just a rep typing an id). (b) Agentforce invocable use (declared invocable; not referenced by any permset/profile in the repo, see 1C).
Zero-DML rule (AGENTS.md §1): satisfied today and stays satisfied; the fix adds only sharing context, no DML. `GtmAgentToolSurface` contract (no DML, JSON string return incl. errors, never throw) must hold: the proxy's `executeToolCall` already wraps in try/catch returning `{"error":...}`.

**Audit re-verification of `GtmSavedConfigurationController` (`public with sharing`, confirmed line 12).** Read from code:
- `setActive(recordId, active)` (line ~661): blank check, then `update new GTM_Saved_Configuration__c(Id=..., Active__c=...)` in try/catch(DmlException) -> friendly AuraHandledException. Non-owner: `with sharing` DML on a record the user cannot edit raises `DmlException INSUFFICIENT_ACCESS_OR_READONLY`, caught and mapped to "We could not update this link's status." PASS, no explicit assertion, no test.
- `regeneratePassword(recordId)` (~683): same pattern, returns the new password only on success. PASS by the same mechanism. NOTE: password is generated BEFORE the DML but returned only after it succeeds; verify the record's `Link_Password__c` is unchanged after a non-owner attempt.
- `deleteConfiguration(recordId)` (~1019): `delete new GTM_Saved_Configuration__c(Id=...)` with catch -> "...you may not have access to it." PASS. Test must assert the record survives.
- `saveConfiguration(SaveInput)` (~413): confirm in the Developer pass whether an existing-record `input.recordId` path exists (update by id); if it does, it needs the same non-owner test. The existing `getPassword` non-owner test (`GtmSavedConfigurationControllerTest` ~line 1088-1145) is the precedent and proves the harness (Standard User + `createRep`).
- Read-by-id methods `getConfiguration`, `hasLinkPassword`, `getPassword`, `getConfigurationCrmData`, `resendEngagementLink(Id)`, `generateRepDirectShareLink`: `with sharing`; only `getPassword` has a non-owner test today. Add non-owner tests for `getConfiguration` and `resendEngagementLink` (the latter sends an email) as regression guards.
- Weakness to note: these PASS verdicts rest solely on implicit `with sharing` + Private OWD + Edit/Delete grants. They fail open if anyone (a) grants `viewAllRecords`/`modifyAllRecords` on `GTM_Saved_Configuration__c` to `GTM_Offering_User` (currently absent; re-verified by the parent), (b) changes the class to `without sharing`, or (c) the role hierarchy gives a manager access (parent fork F5, unresolved, org data). Hence the requirement below to add tests, and (Architect decision F-B below) optionally a cheap explicit assertion. Do NOT convert these methods to an explicit pre-query unless the Architect decides; the tests are the mandatory piece.

### 1B. Design (Salesforce-native first; for Architect to ratify, not settled)

- **D1. `GtmStageActionsController` -> `public with sharing`.**
  - `getStageContext`: resolve id; query the link under sharing with a List (not a bare SOQL that throws `List has no rows`); if empty (non-owner, or nonexistent) return `new StageContext()` (identical to the existing "unresolvable id" contract, which the LWC already handles as "no data"). Only after the link is proven visible under sharing, read the latest assessment request through a private inner `without sharing` class (`ElevatedReads`, mirroring `GtmAssessmentListController.ElevatedReads`), because requests created before the owner stamp, or by queue, may be owned by someone other than the link owner and the rep must still see their own link's requester. The elevation is scoped to `Saved_Configuration__c = :provedVisibleLinkId`, so it cannot be steered to another rep's data. Architect may instead choose plain `with sharing` for the request read if a production check shows no request has `OwnerId != link owner` (see open fork F-A).
  - `advanceStage`: keep the `VALID_STAGES` check; query the link `FOR UPDATE` under sharing into a List; if empty throw `AuraHandledException('You can only change the stage of your own links.')` (friendly, no raw exception); then `update` (under `with sharing` a non-editable record also fails: catch `DmlException` -> same friendly message). Admin: passes via `GTM_Offering_Admin` View/Modify All. Rep on own link: passes via ownership + Edit grant. Rep on another rep's link: friendly error, record unchanged, NO flow fires, NO email.
  - `sendProposalEmails` `@InvocableMethod` stays on the outer class (flow binding unchanged: same class name, method name, `SendEmailInput` shape). Its body delegates the request read and `Messaging.sendEmail` to the inner `without sharing` class so the flow keeps working whichever user's context the flow update runs in (system-mode flow or a rep). It receives its `configId` from the flow record, never from a rep-supplied AuraEnabled parameter; document that in the class header. Do not change the single-send-point rule in the class header (no second send path).
  - Update the now-false class header ("Runs without sharing — config managers ... regardless of ownership").
- **D2. `GtmArCasePanelController`.** Gate first with sharing, elevate only the Case read. Suggested shape: outer class `with sharing`; step 1 query `GTM_Assessment_Request__c WHERE Id = :requestId` (typed SOQL on the request itself is fine; it is not the lookup field the stage class avoids) and `GTM_Readout__c` under sharing so the caller must have record access to the request or its readout (owner, admin, or `GTM_Readout_Triage` queue member via queue-owned records); if the request or readout is not visible return `null` (same as "no readout yet": the panel then renders its empty state, no error, no existence oracle); step 2 private inner `without sharing` class reads the `Case` by the readout id already proven visible. Keeps the class header rationale (no Case object grant) intact. Confirm `Case` OWD in org (org data, not in repo) is irrelevant because the Case read is elevated and keyed only on a gated readout id.
- **D3. `GtmAgentGetConfigState` -> `with sharing`** for the saved-config read: class-level `with sharing`; the `GTM_Page_Content__c` industry read (id-free shared taxonomy, no per-user secret) moves to a private inner `without sharing` `ElevatedReads` ONLY if the Architect wants the Agentforce invocable path (service/agent user with no page-content sharing) to keep listing industries; a rep already has page content read (OWD ReadWrite, User has Read), so for the GUS path plain `with sharing` works. A non-owner id yields an empty saved lookup and the tool returns the blank defaults (company empty etc.) and the industry list, never the other rep's payload; no exception (GUS tool contract: never throw, return JSON). Also recommended (small, belt-and-braces for the prompt-injection vector): in `GtmAgentProxyController.executeGetState`, ignore the model-supplied `config_id` and always use the session `configId` (the tool description says the model never needs to pass an id; the readout surface already does this by design: "the model is never given a readout Id to pass"). This is an in-scope one-line hardening; if the Architect prefers to leave the proxy untouched, `with sharing` alone closes the data leak. Zero-DML rule preserved in both.

Behaviour matrix after the fix (all three surfaces):

| Caller | `getStageContext` / `advanceStage` | `getCaseForRequest` | GUS `get_gtm_config_state` |
|---|---|---|---|
| Admin (`GTM_Offering_Admin`) | works for every link | works for every request with a readout+Case | reads any link's state |
| Rep on their own link | works (unchanged) | works (unchanged) | works (unchanged) |
| Rep on another rep's link | context: empty `StageContext` (no PII); advance: friendly `AuraHandledException`, no update, no flow, no email | `null` (empty panel), no Case data | blank defaults, no other rep's payload, no error |
| Guest / system | no guest path exists (class not in `GTM_Guest`); the ONLY system path is the flow's `sendProposalEmails`, kept working via the inner elevated class | no guest path | no guest path (`GtmAgentProxyController` is not in `GTM_Guest`) |
| `GTM_Readout_Triage` queue member | n/a for stage/GUS config; `getCaseForRequest` works for queue-owned direct-booking request/readout (the approved exception) | works via queue ownership | n/a |

### 1C. Findings that need Architect attention (verified, do not guess)

1. **Class access.** In the repo, NONE of `GtmStageActionsController`, `GtmArCasePanelController`, `GtmAgentGetConfigState` is granted in ANY permission set (`GTM_Offering_User/Admin`, Content, Guest) or in `profiles/Standard*.profile-meta.xml`. The LWCs `gtmStageActions` and `gtmArCasePanel` therefore only work for a rep today if class access exists in org data (profile/permset applied outside the repo), or for an admin with Author Apex/Modify All. This means (a) the audit's "any rep can" is plausible only if org data grants access, so QA/coordinator should confirm with a READ-ONLY metadata query (`SetupEntityAccess` on the ApexClass) before claiming exposure, but the fix is required regardless; (b) this piece deliberately does NOT add class access (it would widen who can call them; CLAUDE.md §6 mapping is permission-set work and belongs to sibling 4 or an explicit owner decision). State: permission sets: no change in this piece.
2. **Live-data risk for the elevated request read (F-A).** Requests created by the guest `submitRequest` are stamped with the link owner (precedent already in code), but any older pre-stamp request may be owned by the guest user. Under plain `with sharing` the owner's requester panel would go blank for those. Hence the inner elevated read scoped to a proven-visible link. Alternative is a coordinator read-only count `OwnerId != Saved_Configuration__r.OwnerId` (parent 3C style) to prove plain `with sharing` suffices. Owner/Architect choice.
3. **Role hierarchy (parent F5).** `grantAccessUsingHierarchies` default true means a manager above a rep passes the `with sharing` checks for that rep's links; unresolved, unchanged here. Tests must use two peer reps with no role (Standard User profile users, as in the existing `createRep`).
4. **Not-covered `without sharing` @AuraEnabled methods that take a record id and do not re-check ownership** (grepped `force-app/main/default/classes`, all `without sharing` top-level classes reviewed; NOT widened into this piece, reported only):
   - `GtmConfigurationReader.getPublicConfiguration(recordId)` (in parent audit? NOT listed there): `without sharing`, granted to Guest, `GTM_Offering_User`, `GTM_Offering_Admin`. Returns company, industry, offering, `Config_Payload__c`, stage of ANY active link by id. `Link_Password__c` is never selected. By design the link id is the bearer token (class header documents the trade and forces `Active__c` gating), so a rep with another rep's id reads what that link's prospect would see. Not a rep-to-rep secret in the same sense as requester PII, but it is an id-only read of another rep's link. Recommend: leave (guest path requires it), record as accepted; if the owner wants it tightened, a rep-only variant would be needed (design fork F-C).
   - `GtmPageContentController.savePresentation(recordId, key, value)`, `deleteContentRecord(recordId)`, `deleteSection(sectionId)`, `setSectionActive`, `saveSectionOrder`, and the other content mutators (class is `without sharing`, `GTM_Offering_User` has class access): update/delete `GTM_Page_Content__c`/`GTM_Page_Section__c` by client id with no ownership check. This is the parent's F3 content-scope issue (content is global, not rep-owned), already listed there; the parent audit named the class but did not call out these mutators. Owner decision F3 governs; not in this piece.
   - `GtmAssessmentRequestController.getOfferingHasConduit(Id assessmentRequestId)`: `without sharing`, id-only, returns a Boolean; already noted OK by the parent. Confirmed low risk.
   - `GtmReadoutPublicController.getPublishedReadout(token)`, `GtmReadoutCommentController.submitComment(token,...)`, `GtmAssessmentDraftController.resumeDraft/emailResumeLink(resumeToken,...)`, `GtmFormDraftController.getDraft/saveDraft/clearDraft(configId, visitorKey)`, `GtmLinkAuthController.*(recordId, ...)`, `GtmConfigurationStatusController.*`, `GtmLinkEventController.*`: all token/visitor-key gated guest paths, already in the parent audit; unchanged. `GtmFormDraftController.getDraft(configId, visitorKey)` returns prospect answers keyed by (config, visitorKey): a rep could read another rep's link drafts only by knowing a visitor key (not guessable); parent-covered.
   - `GtmLegacyConfigId.resolve`, `GtmLinkRecoveryController.recoverLink`: parent-covered (existence oracle / enumeration D5).
   - Apex non-AuraEnabled `without sharing`: `GtmAgentConfigActions`, `GtmAgentApplyConfigUpdate` (no DML issue here; `GtmAgentApplyConfigUpdate` publishes `GTM_Config_Update__e`, not a record write; it accepts no record id in the repo version read), `GtmAgentTone`, `GtmReadoutApprovalHandler`, `GTM_RecycleBinController` (`with sharing`). No new finding.
   - `GtmAgentProxyController.chat(sessionToken, configId, ...)` is `without sharing` and passes `configId` to the surface; after D3 it no longer leaks. Its other surface (`chatOnReadout`) asserts access itself (parent OK).
