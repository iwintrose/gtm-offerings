Findings that change the parent's assumptions (the Architect must read these first):

1. **Content editors have NO grant on `GTM_Offering_Feedback__c` and no access to `GtmFeedbackController`.** `GTM_Content_Manager`/`GTM_Content_Admin` contain neither. The class is granted only to `GTM_Offering_User` and `GTM_Offering_Admin`. Today an editor reads all feedback only because they are also assigned `GTM_Offering_User`/`GTM_Offering_Admin` (viewAll + ReadWrite OWD). The `gtmFeedbackQueue` LWC (`getOpenFeedback`, `respond`, `getPageTitles`) is not referenced by any tab or app metadata in the repo (placement is org/App Builder data; the Architect must confirm where it is surfaced). So the parent's F7 "check their grants" answer is: they do NOT currently have their own, and dropping `viewAllRecords` from `GTM_Offering_User` will blind any editor who holds only User + Content_Manager.
2. **`GtmFeedbackController.getFeedbackFor(offeringKey)` is deliberately NOT owner-filtered** (code comment: a rep seeing that someone already raised "the proof number is stale" is better served). `docs/backlog.md` D2 says the opposite ("BD sees their own; Content Manager sees all"). Making OWD Private changes the rep-visible behaviour to own-only (matches D2 and the owner rule, contradicts the class comment). `GtmFeedbackController` is `with sharing`, so it follows OWD automatically; `getOpenFeedback`/`countOpenFeedback` (Content Manager badge and queue) would return only the caller's own unless the caller has viewAll.
3. **Apex ignores object CRUD.** `GtmPageContentController` is `without sharing`, granted to `GTM_Offering_User`, and its write methods (`saveDrafts`, `publishPage`, `discardDrafts`, `savePresentation`, `saveContentRecord(s)`, `deleteContentRecord`, `createOffering`, `renamePage`, ...) contain NO permission guard (no custom permission, no `isUpdateable`, no `PermissionSet` check; grep-verified). So removing Edit/Delete on Page Content/Section from `GTM_Offering_User` only closes UI/API/flow/Data-loader paths; a rep who can invoke the `@AuraEnabled` method (or a crafted Aura call) can still write page content through Apex. `GtmPageSectionController` is `with sharing` but is NOT granted to `GTM_Offering_User` (only Content_Manager/Content_Admin), so section writes via that class are already blocked for reps at class-access level. The rep-facing LWCs import only read methods from `GtmPageContentController` (`getHomeSummary` in `gtmOverview`, `getOfferings` in `gtmInstrumentAuthor`, `getPageTitles` in `gtmFeedbackQueue`); all write imports (`saveDrafts`, `publishPage`, `deleteSection`, `createPage`, ...) come from `gtmContentManager`, `gtmContentHome`, `gtmFieldEditor` (Content Manager surfaces). Hence no rep flow needs Page Content/Section Edit/Delete.
4. **No rep-facing LWC reads Form_Draft/Feedback/Link_Event through the UI API.** LWC-to-object access is only via Apex (`GtmFeedbackController`, guest draft controllers). The only LWC files that mention the object names are `chooseIndustry`, `gtmConfigurator`, `gtmPageLayouts`, `gtmStory`, `offeringChooser` (Page_Content field/string references; the Architect greps to confirm none use `lightning/uiRecordApi`/`getRecord`/`lightning-record-form` on Form_Draft/Feedback/Link_Event). Apex readers of `GTM_Form_Draft__c` (`GtmFormDraftController`, `GtmAssessmentDraftController`, `GtmAssessmentRequestController` closing row, purge classes) are guest-facing and `without sharing` (system context, unaffected by user viewAll). `GtmHomeSnapshotController` reads `GTM_Page_Section__c` (read only; keep R).
5. **Lookup delete constraints:** `GTM_Link_Event__c.Saved_Configuration__c` = SetNull; `GTM_Assessment_Request__c.Saved_Configuration__c` = SetNull; `GTM_Form_Draft__c.Saved_Configuration__c` = Cascade (already). `GtmSavedConfigurationController.deleteConfiguration` does a bare `delete` under `with sharing` and turns any `DmlException` into "It may already be gone, or you may not have access to it." (a Restrict failure would display that misleading text).

### 1B. Decisions for this piece (recommended answers; F-numbers continue the parent)

- **P3 (F7) — Feedback OWD Private (Owner decision, RECOMMENDED yes).** Set `GTM_Offering_Feedback__c` `sharingModel` to `Private` (deploy is an UPDATE; Private is a tightening, allowed). Cascade the link's events and drafts: `GTM_Form_Draft__c` is already `Cascade`; change `GTM_Link_Event__c.Saved_Configuration__c` from `SetNull` to `Cascade` (confirm the platform accepts Cascade on this optional lookup; the Form_Draft field is the precedent; if the deploy rejects it, fall back to leaving SetNull and recording that events become unowned-by-link orphans, still owned by the rep, still owner-scoped by OWD). A trigger/Apex guard is NOT needed: Restrict is native and covers UI, API and Apex. Cascade-deleting events on link delete is destructive on Production data; owner must accept it explicitly. Also note deleting the parent link by ADMIN is likewise blocked by Restrict (admin must delete requests first) — say so in the runbook.
