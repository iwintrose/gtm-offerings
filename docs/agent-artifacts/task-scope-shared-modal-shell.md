# TASK SCOPE — ISSUE #shared-modal-shell

## 0. Investigation Summary (this session, read-only)

Catalogued every overlay-style LWC named by the stakeholder plus a couple more found while grepping for `scrim`. The real variation is wider than the two components already discussed, and it breaks into **three distinct families**, not one:

1. **Side-sheet overlays (the actual target of this issue)** — `gtmConfigWizard` and `gtmRepDirectPicker`. Both: fixed scrim + a right-hand sheet that slides in via `transform: translateX(...)`, toggled by a CSS class (`open`) rather than mount/unmount. They differ meaningfully:
   - Scrim transition: `gtmRepDirectPicker` uses `display:none`→`block` (no transition on the scrim itself); `gtmConfigWizard` uses `opacity: 0→1` with `transition: opacity .3s` (crossfade).
   - Sheet transition: `gtmRepDirectPicker` — `transform .2s ease`; `gtmConfigWizard` — a custom cubic-bezier over `.32s`.
   - z-index: `gtmRepDirectPicker` 9000/9001; `gtmConfigWizard` 89/90 (different stacking scheme entirely — a straight z-index carry-over risk if both existed on the same page, though today they never do simultaneously).
   - Positioning: `gtmRepDirectPicker` is always plain `position: fixed`, full viewport. `gtmConfigWizard` has a second mode (`standalone`) where the scrim/sheet's `top` is pinned to a measured Salesforce-chrome offset (`_measureChromeOffset()`, `gtmConfigWizard.js` lines 319–344), computed via a deferred `setTimeout(() => this._measureChromeOffset(), 0)` in `connectedCallback()` (lines 346–406). This offset calculation only works if the component is the literal first child of its mount container — both current consumers (`gtmConfigurator.html` lines 1–18, `gtmOverview.html`) carry a `KEEP THIS FIRST` comment enforcing this, added as a prior fix this session. This fragility is the concrete trigger for this issue.
   - Close/dismiss: both close on scrim click and an explicit `×` button; both dispatch a plain `close` CustomEvent with no payload. `gtmConfigWizard` additionally dispatches `done` (post-save, carries `recordId`/`generatedUrl`/`company`) and `configsaved` (autosave, mid-flow) — these are domain events, not shell concerns, and must stay owned by the wizard's own content, not the shell.
   - Progress UI: `gtmConfigWizard` has a clickable step-dot rail (`stepDots`) in its header area; `gtmRepDirectPicker` has none.
   - `gtmConfigWizard` is also driven by a public `isOpen` **getter/setter** (not a plain `@api` field) that does non-trivial seeding work on open (pulling in parent-loaded record values the first time the wizard opens for a known record — `gtmConfigWizard.js` lines 55–92). This behavior must not be disturbed by wherever `is-open` lives after migration — it is domain logic that must stay in the wizard, not move into a shell prop setter.

2. **Centered dialog/confirm modals (NOT part of this issue's target, but a second, already-duplicated pattern worth flagging)** — `gtmContentHome`, `gtmFieldEditor`, `gtmContentManager` each carry a byte-for-byte identical `.scrim { position:fixed; inset:0; z-index:100; background:rgba(20,20,24,.5); display:grid; place-items:center; }` + `.modal` block, used for small centered confirm/add dialogs (`role="dialog" aria-modal="true"`), toggled via `if:true` template mount/unmount (not a CSS class), with no scrim or sheet transition at all. This is real, visible duplication (three literal copies of the same CSS block) but it is a **different UX shape** (centered card, not a side sheet) from what the stakeholder is describing and is **out of scope for this issue** — flagged here as a strong follow-up candidate, not silently folded in, since conflating it would both delay the stakeholder's actual ask and force the shell's API to support a layout mode nobody asked for yet.

3. **Non-blocking FAB panels (also NOT part of this issue's target)** — `gtmFaqPanel` and `gtmAgentBubble`. Both are `position: fixed` corner launcher buttons that reveal a panel with `if:true` mount/unmount — no scrim, no backdrop, not modal (`aria-modal` is not set; underlying page stays interactive). Structurally and semantically unrelated to a scrim-blocking modal shell; including them would force the shell's contract to support "no backdrop" as a first-class mode for no real gain, since neither of them needs scrim/backdrop-dismiss behavior at all. Left out.

`gtmAssessmentQuestionnaire` has no modal/scrim of its own — it is the content hosted *inside* `gtmConfigWizard`'s sheet body (confirmed via its own CSS comment: "Hosted inside gtmConfigurator's overlay: the card supplies the frame"). It is a slot consumer, not a fourth overlay implementation, and needs no changes here.

**Conclusion:** the shared shell's required API surface is driven by family 1 only (`gtmConfigWizard` + `gtmRepDirectPicker`), but must be named/scoped so family 2 (centered dialogs) can plausibly build on the same base later, since re-litigating "is this the same component" a second time would be wasted work. This issue does **not** attempt family 2 or family 3.

## 1. Requirements Breakdown

- **Target Objective:** Stop every side-sheet overlay in this codebase from independently reinventing scrim/sheet CSS and open/close mechanics. Build one shared component (`gtmModalShell`) that owns: the scrim, the sheet's fixed positioning (with chrome-offset measurement as an *optional*, opt-in feature — never assumed), and the open/close transition. Leave all step/form/search internals, and all domain events (`configsaved`, `done`, `created`, etc.), owned by the child via slotted content. Migrate the **simpler** consumer, `gtmRepDirectPicker`, onto it in this same issue as the validation case. Migrating `gtmConfigWizard` (the harder consumer — chrome-offset mode, multi-step progress rail, the getter/setter `isOpen` seeding logic) is deliberately **not** done here; see §5 below for why and the explicit follow-up issue.
- **System Component Impacted:** LWC only (`force-app/main/default/lwc/`). No Apex, no Custom Metadata, no Experience Cloud route changes, no YAML instrument changes.

### Why split rather than do both consumers in one PR

This session's own precedent (issues #184, #102, rep-initiated-assessment) is to split substantial multi-part work rather than ship one large PR touching several independently-testable surfaces. Weighed explicitly against the risk that leaving `gtmConfigWizard` unmigrated might not satisfy the stakeholder's literal complaint (which was specifically about `gtmConfigWizard`'s "New engagement link" experience):

- **Reasons to split:** `gtmConfigWizard` is materially riskier to touch — it has 1205 lines of existing Jest coverage (`gtmConfigWizard.test.js`), the chrome-offset mount-order fragility already caused one incident this session (the `KEEP THIS FIRST` fix), and it is live in front of prospects in two different embedding contexts (`gtmConfigurator`, the Experience Cloud production surface, and `gtmOverview`, an internal Lightning tab) plus the `gtm-dev` "production, no staging" constraint from `CLAUDE.md` §Environment Configuration. Landing the shell + a low-risk consumer (`gtmRepDirectPicker`, no chrome-offset mode, only used from one place, no existing test suite to keep green) first validates the shell's contract against reality before the harder migration touches the component the stakeholder actually cares about.
- **Reason this alone does not fully satisfy the ask:** acknowledged explicitly — this issue, by itself, does **not** change `gtmConfigWizard`'s open/close feel at all, so it does not yet deliver the specific improvement the stakeholder asked for. This is deliberately NOT presented as "done" on the stakeholder's complaint. A second, explicitly-scoped follow-up issue is written alongside this one (see §5) so the `gtmConfigWizard` migration is a committed next step, not an open-ended maybe — the two-issue split is a sequencing decision, not a scope cut.

## 3. Plan Acceptance Criteria

- **Success Metric:**
  1. A new `gtmModalShell` LWC exists with a documented public API (props, slots, events — Architect to finalize exact names as a Contract-First doc under `docs/architecture/` per `CLAUDE.md` §4 before implementation):
     - Props: `is-open` (boolean), `title` (string, for an accessible header/`aria-labelledby`), a positioning mode prop that defaults to plain `position: fixed` and only opts into chrome-offset measurement when explicitly requested by the consumer (never assumed, unlike today's `gtmConfigWizard.standalone` conflating "no live page behind this" with "needs chrome-offset math").
     - Slots: a default/body slot for step or form content, plus a named slot for header extras (so a future `gtmConfigWizard` migration can project its step-dot rail without the shell needing to know what a step-dot rail is).
     - Events: `close` (scrim click or explicit dismiss control) at minimum. The shell must NOT emit or know about any domain event (`configsaved`, `done`, `created`) — those stay owned by whatever is slotted in.
  2. `gtmRepDirectPicker` is migrated to consume `gtmModalShell` for its scrim/sheet/open-close chrome; its own search/select/confirm body markup and JS logic (Apex calls, `_selected`, `_results`, etc.) are unchanged in behavior.
  3. `gtmConfigWizard` is **not** touched by this issue (confirmed via git diff scope at PR time — any change there belongs to the follow-up issue below).
  4. No existing consumer's user-visible behavior changes beyond the intended visual/positioning fix to `gtmRepDirectPicker` (which, per the stakeholder's own preference, should end up looking like it already does today — `display:none`→`block` scrim, `transform` slide, no chrome-offset dependency — so ideally this migration is visually a no-op and only removes duplicated CSS/JS, not a redesign).
  5. Existing Jest test suites continue passing. `gtmRepDirectPicker` currently has no dedicated Jest file — this issue must add one (it should not remain the only side-sheet overlay with zero coverage once it's the "reference" implementation of the new shell).
  6. New Jest coverage added for `gtmModalShell` itself: open/close state reflected in rendered markup, `close` event firing on scrim click and on an explicit close control, slot content projection, and the chrome-offset opt-in prop behaving as documented (present vs. absent).
  7. Per `CLAUDE.md` §4 "Contract First": the shell's schema/props/slots/events must be documented in `docs/architecture/` before implementation lands, not discovered from the code after the fact.

- **Target Test Target:** New `force-app/main/default/lwc/gtmModalShell/__tests__/gtmModalShell.test.js` (to be created by the Developer step) plus a new `force-app/main/default/lwc/gtmRepDirectPicker/__tests__/gtmRepDirectPicker.test.js` (also new) and continued passing of `force-app/main/default/lwc/gtmConfigWizard/__tests__/gtmConfigWizard.test.js` (must remain green and untouched, since `gtmConfigWizard` itself is out of scope here) and `force-app/main/default/lwc/gtmOverview/__tests__/gtmOverview.test.js` (`gtmOverview` mounts both `gtmConfigWizard` and `gtmRepDirectPicker` — must be checked for any coupling to `gtmRepDirectPicker`'s internal markup/classes that the migration could break, e.g. any test that reaches into `.rdp-scrim`/`.rdp-sheet` class names directly rather than through a public API).
